- **Never run bare `vite dev`.** The dev server is `server.ts`; Vite runs in middleware mode inside it.
- The dev server belongs in the user's own terminal, not an agent background shell — it is long-lived and browser-facing. When you need to see its output, ask the user to run `npm run dev:log` and read `dev-server.log`; only take the port yourself for a short, self-contained check, and free it afterwards.
- **`RepxDesigner.exe --serve` belongs in the user's terminal for the same reason, and a stronger one.** A process paints on the desktop of the session that created it, so an instance you start from an agent shell opens the designer where nobody can see it — and reports success all the way back to the browser. Ask the user to double-click it. See *Start it yourself, from your own desktop* in [`tools/RepxDesigner/README.md`](tools/RepxDesigner/README.md).
- **`npm run dev:log` is `node scripts/dev.mjs`, not `npm run dev` with a redirect.** It spawns the same `tsx server.ts` and tees the output, so the log exists only while that script is the thing running — a server started any other way writes no `dev-server.log`, however long you wait for one. It opens the file with `flags: 'w'`, so each run **truncates** the previous log and stamps a `=== npm run dev:log - <ISO> ===` header — check that timestamp before trusting what you read, and note ANSI codes are stripped on the way in, so the file is greppable while the terminal stays coloured.
- `scripts/build-server.mjs` bundles `server.ts` with esbuild, keeping `node_modules` external and baking in `NODE_ENV=production` — so the started server takes the static-file branch and the Vite import is dead code. `npm start` therefore requires `npm run build` first, and must run from the repo root (the static path is `process.cwd()/dist`).
- **`.env` does not contain a Gemini key and must not.** It holds `APP_URL` plus the optional `VITE_FORMA_MOCK`, and `server.ts` loads it via `import "dotenv/config"` — but the server has no key-bearing routes left, and `envPrefix: ['VITE_']` means a `GEMINI_API_KEY` set there reaches neither the server code nor the browser. Nothing is inlined into the client bundle. `.env*` is gitignored except `.env.example`, whose comments say the same thing.
- Run a single test file with `npx vitest run src/lib/repx.test.ts`, or a single case with `-t "<name>"`. Narrowing to one file buys clarity, not time — but the numbers this file used to give (~30s vs ~34s) were measured cold and are wrong by an order of magnitude. Re-measured 2026-08-20: the **first** `npm test` of a session took 52s, and the very next one 4.6s; a single file is ~5s either way, so warm, one file and all ten cost the same. Read a slow first run as a cold cache, not as a hang — and never quote a timing here that came from a cold run. **A cold cache can do worse than crawl: until 2026-08-28 it made the suite fail outright.** jsdom's entry loads synchronously, and cold it was measured at **113 seconds** in one process on this machine against 1.4s warm — while vitest gives a worker 60 seconds to report in (`START_TIMEOUT`, hardcoded in vitest's dist with no config option feeding it). Every worker died before starting, and all 25 files reported `[vitest-pool-runner]: Timeout waiting for worker to respond`, which reads as a broken pool or a broken install and is really a stopwatch. If you see that error, the suite is not broken and neither is your install: run it again. The environment split now keeps 20 of the 25 files away from jsdom entirely, which cut summed environment setup from ~66s to ~8s and took the cliff from 25 workers down to 5 — but it did not remove it, and the 442s-summed figure this file used to quote came from the era when every worker paid it. `README.md` carries the same figures, so re-measuring is a change to two files. **`--reporter=basic` no longer exists** — Vitest 4 removed it, and an unknown reporter name is treated as a module to import, so the failure is a `Failed to load custom Reporter from basic` / `Failed to load url basic (resolved id: basic)` stack trace with Vite frames in it, which reads like a broken config rather than a bad flag value. `vitest.config.ts` already sets `reporters: 'default'`; pass `--reporter=dot` for the terse output `basic` used to give. Verified on vitest 4.1.10. `vitest.config.ts` is deliberately separate from `vite.config.ts` — that one carries the "Do not modify" HMR block and is loaded by the dev server. Tests live beside what they test as `*.test.ts`; the config only picks up `src/**/*.test.ts`. See "Read this first" for what the suite does *not* cover.
- **There are three Vitest/Vite configs, and the rules suite uses its own.** `npm run test:rules` is `firebase emulators:exec --only firestore "vitest run --config vitest.rules.config.ts"` — the emulator wrapper is what supplies the Firestore instance, so `vitest run --config vitest.rules.config.ts` on its own has nothing to talk to. `tests/firestore.rules.test.ts` sits outside `src/`, which is why the default config never picks it up and `npm test` cannot run it by accident.
- **To run a single rules case, use a space-free regex — do not try to nest quotes.** The `-t` flag has to go *inside* the quoted command the emulator wrapper runs, and PowerShell 5.1 re-parses that string before `firebase` ever sees it, so the obvious `-t \"lets a user read their own report\"` arrives mangled (observed: `Script "… -t " lets a user read their own report\" exited with code 1`). `-t` is a **regex**, so `.` in place of each space sidesteps quoting entirely:

  ```powershell
  npx firebase emulators:exec --only firestore "npx vitest run --config vitest.rules.config.ts -t lets.a.user.read.their.own.report"
  ```

  Verified: `1 passed | 28 skipped`. A distinctive single word (`-t isolation`) works the same way and is shorter.
- `.claude/settings.local.json` carries a permission allowlist covering every command in the two blocks above — `npm run *`, `npm test`, `npm ls *`, `npx tsc *`, `npx vitest *`, `Get-Process`, `New-Item`, plus a handful of one-off probes left over from past sessions — so the documented checks run without a prompt. Note `npm test` needs its own entry: it is not `npm run test`, so `npm run *` does not match it. `dev-server.log` is gitignored by the blanket `*.log`, not by name.
- **`.antigravity/` is editor state, not project data** — a single ~22 MB `.pbtxt`. Nothing reads it and nothing builds from it. It is now explicitly gitignored (it matched no pattern originally, so a first `git add .` would have put 22 MB into every clone forever), but it is still on disk, so a recursive listing or a "what's in this repo" sweep will trip over it. Don't read it, don't index it, and don't count it as source.
- **`.gitignore` carries credential patterns that are a backstop, not permission.** `key.txt`, `*.key`, `*apikey*`, `*api-key*` and `secrets.json` are ignored so a key pasted into the working tree by mistake cannot be committed by a careless `git add .` — the same accident as the `envPrefix` leak, with fewer steps. They do **not** make the repo a place to keep a key: it belongs in the app's Settings dialog, which puts it in `sessionStorage` and never on disk (see *Where the user's key lives* in [`docs/notes/gemini.md`](docs/notes/gemini.md)). Also note `*.log` is what hides `dev-server.log` and `firestore-debug.log`, and `.env*` is ignored **except** `.env.example`.
- **`.firebaserc` is deliberately *not* ignored, and that is the point.** It names the deploy target (`forma-201ba`) and holds no credentials. Ignoring it is exactly how a fresh clone or a CI run deploys to whichever project the CLI last happened to select — see [`docs/notes/persistence.md`](docs/notes/persistence.md) for the time that went wrong. `.firebase/` (deploy caches, emulator exports) **is** ignored.
- `vite.config.ts` gates HMR on `DISABLE_HMR !== 'true'` and carries an explicit *"Do not modify — file watching is disabled to prevent flickering during agent edits"* comment. Leave that block alone. The `watch: { ignored: ['**/tools/**'] }` line beside it is load-bearing too: chokidar throws `EBUSY` on MSBuild's locked `bin/`/`obj/` files and takes the whole dev server down with it.
- Symbol names in this document are stable; line numbers are not. Grep for the identifier rather than jumping to a remembered offset — `src/App.tsx` has already grown past every line number an earlier revision of this file recorded.
