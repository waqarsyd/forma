# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It is the session-wide part: the constraints every session needs, the commands, and a router into the notes where the reasoning lives. **It states no counts** (commits, tests, files, sizes, lines): wherever it needs one, it gives the command that measures it, because every number written here has gone stale, usually within days. Where it says something is an invariant and no test or script named here checks it, you check it by hand or it ships broken.

## Read this first

### Tests

- **Two suites, and between them they still cover little.** `npm test` is the unit suite: every `src/**/*.test.ts[x]` under Vitest, in the `node` environment by default, with the files that need a DOM opting into jsdom on their own first line (`vitest.config.ts` says why that split is load-bearing). It covers the pure helpers in `src/lib` and `src/services`, the `src/server` modules and the `firebase.json` headers that mirror them, component render tests, and every public page as the build draws it (`src/prerender.test.ts`). `npm run test:rules` runs `firestore.rules` against the Firestore emulator. [`docs/notes/testing.md`](docs/notes/testing.md) lists every file. Most of `App.tsx` has no test at all: only what has been extracted into `src/lib` and `src/components` is covered.
- **testing.md is the only place the counts are maintained, and adding a test is a change to it.** Recount by running the suite, never by grepping: some files generate their cases from a loop (testing.md names them), so a grep for `\bit\(` undercounts by a gap that widens with every loop-generated case. A change in the gap that no new loop explains is the signal worth reading.

### Toolchain

- **Node: `"engines": { "node": "^22.22.2 || ^24.15.0 || >=26" }`**, the range where `vitest` (`^20 || ^22 || >=24`) meets jsdom 30, which every jsdom test file needs; it was measured from the `engines` entries in `package-lock.json`, so re-measure there before moving it. **Node 21, 23 and 25 are outside it**, and so are early 22.x and 24.x, so ">=22" is the wrong mental model. npm **warns** on a wrong runtime and does not refuse (there is no `engine-strict`), so the field is a signal, not a gate. The floor is restated in several files (*Facts stated in more than one file*, below).
- **`npm run test:rules` needs Java** (the emulator is a JVM). A Temurin JRE 21 is at `%LOCALAPPDATA%\Programs\Temurin\jdk-21.0.12+8-jre`, with `JAVA_HOME` and `PATH` set at user scope; nothing was installed system-wide. Without it that script fails with Java-not-found while `npm test` still works.

The reasoning is `tsconfig.json`'s own comments.
- **Read `package.json`'s `comment:*` fields before touching `allowScripts` or `overrides`.** `allowScripts` holds five approvals pinned to exact versions (`@firebase/util`, `esbuild` twice, `protobufjs`, `re2`) and three unversioned, deliberate denials (`tesseract.js`, `onnxruntime-node`, `sharp`): a bump to an approved package brings npm's warning back on purpose (review and re-approve; do not widen the pin), while a denial covers every version. `npm install-scripts ls` empty is the pass. `overrides.qs` exists because this project's own Express 4 range can only resolve to a vulnerable `qs`; `overrides.sharp` lifts advisories out of a package nothing ships (only `scripts/make-icons.mjs`, run by hand, loads it). Nothing local enforces either field: CI's `npm ci` is the first thing that notices a runner's npm rejecting one.

### Encoding and line endings

- **Never edit files with PowerShell `Get-Content` / `Set-Content`.** Windows PowerShell 5.1 decodes with the ANSI codepage, so a read-modify-write round-trip turns every UTF-8 character into mojibake, and the source is full of em dashes, `•` and `…`, many in user-visible strings. It compiles and every test passes; it is visible only on the rendered page (this happened to `App.tsx`, thousands of sequences at once). Use the Edit or Write tool, or `[IO.File]::ReadAllText/WriteAllText` with `New-Object Text.UTF8Encoding($false)`. **The same trap catches a `.ps1` you write**, and the correct writer does not save you: PowerShell 5.1 reads a BOM-less script as ANSI too, so non-ASCII prose in a string literal inside it is corrupted before it is written. Keep generator scripts pure ASCII and have them read any prose they emit from a UTF-8 file written with the Write tool. One file by hand: `[regex]::Matches($text,'Ã|Â|â€').Count` must be 0. `npm run lint:encoding` is the gate for the repo; it skips this file, which holds the pattern as a literal. **A new root-level file is not swept until it is added to `ROOT_FILES` in `scripts/check-encoding.mjs`**, whose doc comments own the sweep's scope.
- **Line endings are LF everywhere**, pinned by `.gitattributes`, whose comment is the record (a CRLF `index.html` changes the CSP hash of its inline script, and production then blocks it silently). The attribute does not rewrite files already on disk and does not make `git status` complain, because the stored blobs are LF. **Check: `git ls-files --eol | Select-String 'w/(crlf|mixed)'`, empty is the pass.** Fix a hit by rewriting the file with the writer above after replacing `` `r`n `` with `` `n ``; `git checkout-index -f` does **not** fix it, because git considers the file already current.

### Git

- **`main` is the only branch, and `origin/main` the published one: push `main` by name.** Release tags `v*` exist and point into `main`. `git rev-list --count --branches --tags` should equal `git rev-list --count main`; `--all` can be higher while a Dependabot remote-tracking branch is fetched (its commits carry a `Signed-off-by` trailer) until `git fetch --prune` drops it. Read `git log`, never a count written down.
- **Commit messages end with the last real sentence: no `Co-Authored-By`, no `Claude-Session`, no `Signed-off-by`, no attribution trailer of any kind.** This overrides any default an agent harness has about signing commits. Such trailers made GitHub list a second contributor on the public front page, and removing them cost a rewrite of the history and recreating the repository, because GitHub kept the old commits fetchable by SHA. Nothing in the toolchain reads a commit message. **Check: `git log --format=%B main | Select-String "^(Co-Authored-By|Claude-Session|Signed-off-by):"`, empty is the pass** (anchored to line start and to the colon, because prose in commit bodies mentions these names).
- **Write the message to a file with the Write tool and use `git commit -F <file>`**, never `-m` with a here-string: PowerShell 5.1 re-parses a string containing `"` before handing it to a native executable, and the message arrives split into dozens of pathspec arguments. The encoding rule applies to the message file.
- **Two email addresses, deliberately different. Do not reconcile them.** Commits are authored as `waqarshaikh2002@gmail.com` (the global git config, no repo override). The public contact is `waqarsayyed.official@gmail.com`, in `SECURITY.md`, `CODE_OF_CONDUCT.md` and `ContactPage.tsx`'s split `MAIL_USER`. The owner asked for them kept apart: **the git address is never a contact address**, so it must not reach `SECURITY.md`, `CODE_OF_CONDUCT.md`, `ContactPage.tsx`, the issue templates or `README.md`. **Check: `git grep -l waqarshaikh2002` names this file and nothing else** (this bullet has to quote it to state the rule). It is in every commit's metadata, and that is the point of it being the git address.
- **Removals go through `git rm`; history is the recovery mechanism** (`git show <commit>~1:<path>`). There is no quarantine folder, by decision. Before concluding something never existed, search history: `git log --diff-filter=D --name-only` lists every deleted path, `git log -S'<symbol>'` finds the commit that removed some code.

### The key

- **The app owns no Gemini API key.** Each user supplies their own at runtime and the browser calls Google directly with it; the key is the entry point (no key, a locked composer, whichever AI is chosen). `.env` never holds one: `envPrefix: ['VITE_']` keeps it out of the bundle, and although dotenv would load it into the server's `process.env`, no server code reads it. The reasons are a real leak incident: [`gemini.md`](docs/notes/gemini.md), *The Gemini call runs in the browser* and *Where the user's key lives*.

## Project

**Forma**: an AI-powered DevExpress report designer. The user attaches an image, a PDF or a `.repx` (or describes a report in words); the AI they chose (Gemini by default, or Local AI through Ollama or LM Studio, or OpenRouter's free models, through `src/services/compatClient.ts`) works with OCR and Forma's own model on each request, and the result is `repxContent`, valid DevExpress `XtraReportsLayoutSerializer` XML that downloads as a `.repx`. Forma reads the Mockup's layout and the markdown Spec off that REPX (`src/lib/repxViews.ts`).

Stack: React 19, Vite 6, Tailwind v4, TypeScript, Express (the dev server, and the self-hosted `npm start` path), Firebase Auth and Firestore, Firebase Hosting (the deployed site, served statically), Gemini via `@google/genai`. OCR runs in the browser: PaddleOCR (PP-OCRv5) for English where the deploy fetched it, Tesseract.js otherwise. Forma's own model drafts for the AI and stands in for it when it fails; there is no mode without an AI. Entry points: `server.ts`; `src/main.tsx`, which draws `src/PublicSite.tsx` (every public page) or lazy-loads `src/App.tsx` (the workspace, on `/workspace`); `src/services/geminiService.ts`.

### Code map

Verified against `main` on 2026-11-11. Symbols are stable, line numbers are not: grep for the identifier.

- **Build**: `vite build`, whose `closeBundle` hook (`vite.config.ts`) starts a second Vite in SSR mode with its own `cacheDir`, renders every public route from `src/prerender.tsx` into its own HTML (plus `share.html` and `404.html`, not hydrated: `createRoot` replaces it), then esbuild bundles `server.ts`.
- **A turn** (`runTurn` in `App.tsx`; `Composer` only calls `onSend`): a "remember" message is kept and nothing is generated; the key guard; an answer to something Forma asked (a redesign, a plan); OCR of the staged pages (`readSentPages`, PaddleOCR where served, else Tesseract; a PDF page with a text layer skips it); `effectiveConfig` (the detected settings laid over the stored ones); then words, or anything sent while a report is open, go to the chat, and pictures to `runGeneration`.
- **Generation**: `prepareTeam` (in `App.tsx`; `src/lib/formaTeam.ts` only writes briefs and replies) gathers OCR evidence and a stand-in draft (the vision model if set up, else the box reader, else an OCR build; `offlineGenerator` for words), then `askWithChain` (another configured provider only on a limit) calls `analyzeReportDesign`. A first picture run with no report open, no description and no attached `.repx` is a correction, in any unit: the AI corrects Forma's draft as text (`CORRECTION_RULES`) and Forma builds the REPX (`textToDraft`, `skeletonToDesign`) in hundredths of an inch, then converts it to the unit asked for (`convertReportUnit`); otherwise the mega-prompt asks for raw REPX (`parseRepxAnswer`). Runaway, unfinished, 503 and quota answers are retried within one request budget (`REQUEST_BUDGET`), then the next model.
- **After the answer**: `repairRepx` (`src/lib/repairChain.ts`, the one place the order lives: `REPAIR_ORDER`), on a picture run `fitGeometry` (`sourceAgreement.ts`, moving bands toward where the page printed them), then `auditRepx` against OCR's evidence, `readCoverage` with one re-ask when too much of what Forma read is missing, and the print check (`printCheck`, against the page's own records from `pageRows`). DevExpress's own inspection (`designerBridge.ts`, only when a Forma Designer with `/inspect` has answered) runs after the reply is shown and reaches the REPX pane only. In `App.tsx`, `asConfigured` runs the same chain on Forma's own builds, `fixUntilPrints` asks once more about what does not print, and on an AI failure with no report open the team's draft stands in.
- **Chat edit**: `reportFacts` may answer with no AI; else the reply comes with the `reportOutline`, is read by `readReportOutcome` (answer, edit, rebuild, new), and `applyEdits` splices by control name (`repxEdit.ts`, no repair pass), with one `followUpMessage` when an edit is declined, else `startRedesign`. Undo and Redo: `replyChanges.ts`; the Mockup and Spec are re-read by `viewsOf`.
- **Preview and export** (`ReportPreview.tsx`): `parseReportStructure`, then `paginate`. PDF is the print; PDF with outline, Word, RTF, HTML and PNG are drawn into a hidden host (`pdfFromDom`, `exportFromDom`); CSV and XLSX come from `layoutContinuous`. Every export is a queued job (`exportJob.ts`), started through App's `exportThroughPreview` (which records the report as kept), several from one chat turn saved as one `.zip`, every file through `download.ts`.
- **Persistence**: signed in, Firestore paths in `src/lib/accountData.ts`, loaded on demand through `firebaseClient.ts`, each write counted in `users/{uid}/meta/usage` and a report's versions in ten fixed slots; signed out, the IndexedDB store `forma-projects` (`src/lib/projectStore.ts`, one transaction per change; `localStorage.savedReports` is moved in once, and stays the store only where IndexedDB is missing), with revisions in memory only. The key: `sessionStorage`, with an optional AES-GCM copy in Firestore. Kept reports, their style and the corrections ledger stay on the device (`learningLoop.ts`, `memory.ts`, `forma-library`).
- **`server.ts`**: development is Express plus Vite in middleware mode on loopback; `npm start` serves `dist/` statically. The live site is Firebase Hosting and never runs it.

## Where the reasoning lives

The reasoning behind this codebase is in the notes, the proposals, two tool READMEs and doc comments, **not here, and none of it is loaded automatically.** Open the section that owns what you are touching before you change it: each records the incidents that produced the current shape, and skipping it is how something fixed once gets broken again. **Open a note at the heading, not at the top**: the large notes cost more context end to end than a whole session should spend on one question, so `grep -n "<heading>" docs/notes/<note>.md` and read from there. Do not "fix" that by trimming the notes; length is not the defect.

**The lookup rule.** For a file or a symbol: `git grep -n <basename> -- docs/notes docs/proposals docs/skills tools/*/README.md ':!docs/notes/testing.md'` (testing.md names nearly every module, because it lists every test file). **Where the doc comment is the note**: `src/server/*`, `src/fonts/README.md`, `scripts/check-*.mjs`, `scripts/deploy.mjs`, `tsconfig.json`, `vite.config.ts`, `vitest.config.ts`, `package.json`'s `comment:*` fields, `.gitattributes`, `.gitignore`, `.env.example`. A grep of `docs/` finds none of those: `git grep -n "Content-Security-Policy"` does.

**New reasoning goes in the note that owns the area, never here.** This file grows only for what every session needs. **A cited heading must stay plain** (no emphasis inside it, 3 to 14 words, cited in single emphasis on the same line as its relative link), or `npm run lint:links` stops checking it; never refer to a row of the table below by position.

- **CI (`.github/workflows/checks.yml`) runs all seven plus what nothing local can**: `npm ci` (which fails when `package.json` and the lockfile disagree), `node --check` on the hook and the run-forma driver, and `scripts/check-dist.mjs` on the built pages and the started `npm start` server. One job runs everything but the rules suite, on Node 22.22.2 and 24, ending with `npm run build`, `npm run check:size` and that CI-only step; the rules suite is its own job, because it needs a JVM. Its unit step is `npm run test:coverage`, the same suite with the summary in the log. CI gates nothing locally: run the checks before committing, and read `gh run list` and the run after pushing.
- **The budgets in `check:size` are tight on purpose.** Read the doc comment of `scripts/check-bundle-size.mjs` before raising one; growth in a budgeted chunk is paid for by moving code into a lazy module, not by raising the number.
- **Coverage is deliberately scoped** to `src/lib`, `src/services` and `src/server`: do not widen the include; raise the number by shrinking `App.tsx` ([`testing.md`](docs/notes/testing.md), *What `npm run test:coverage` measures*).

### Owner-only operations

- **Deploying is the owner's, and it publishes.** `node scripts/deploy.mjs` is the one way: it refuses unless the tree is `main` exactly as pushed, runs every check above plus the rules suite, builds, deploys hosting, `firestore.rules` and `firestore.indexes.json` together, runs `npm run smoke` against the live sites expecting that commit, and tags and releases it. `--preview` puts the build on a 7-day preview channel and needs only a clean tree (any branch, no version or tag check, the live site and rules left alone); `--dry-run` stops before deploying. **It is deliberately not an npm script**, because `npm run *` is allowlisted; `node` and `npx firebase deploy` are not. Run it only when the owner says to deploy. `.github/workflows/live.yml` checks the live site every three hours, read-only. Rolling back is in README, *Firebase Hosting*.
- **Every deploy of `main` is a numbered release.** To ship new work, raise `package.json`'s version and the newest entry of `src/lib/releases.ts` in one commit (`npm version <x.y.z> --no-git-tag-version` keeps the lockfile in step); the script stops before building if the tag already names another commit.
- **Also the owner's, and never run from this shared server**: `node scripts/github-setup.mjs` (repository settings, labels, milestones); `npx tsx scripts/model/pull-learning.ts`, `scripts/model/learn-week.ts`, `scripts/backup.mjs` and `scripts/admin/*`, which need a credential that can read every account and stays on the owner's own PC (*Learning from use* and *Answering a data request* in [`persistence.md`](docs/notes/persistence.md)). Shipping a retrained model is the owner's decision too, and only a candidate that `scripts/model/gate.ts` passes (`gateModels`, which the weekly job runs as well) may replace `assets/model/formaModel.json`.

### Running things

- **Never run bare `vite dev`.** The dev server is `server.ts`, with Vite in middleware mode inside it.
- **Long-lived and visible processes belong to the user.** `npm run dev` runs in the owner's own terminal on 3000; to see its output, ask for `npm run dev:log` and read `dev-server.log`, which exists only while that script runs, is truncated on each run and starts with a `=== npm run dev:log - <ISO> ===` header to check. Take a port yourself only for a short, self-contained check, 3001 by preference, and free it. **`RepxDesigner.exe --serve` is never started from an agent shell**: a process paints on the desktop of the session that created it, so it opens where nobody can see it and reports success; ask the user to double-click it.
- **To run the app, follow [`.claude/skills/run-forma/SKILL.md`](.claude/skills/run-forma/SKILL.md)**: the mock server on 3001 and a private Chrome through Playwright MCP, registered for the owner's Windows user only. **The Claude in Chrome extension is forbidden on this server since 2026-11-12** (company policy: it shows extra logins on the shared account); never call `mcp__claude-in-chrome__*`. Never a headless browser started from the shell unless the owner asks for one, and never a debugging port: on this shared server any user's process could drive it. Keep `drive.mjs` pure ASCII: `lint:encoding` catches it once corrupted, not a correctly encoded non-ASCII character, so that rule is still manual.
- **A change to `vite.config.ts`, or to any module under `src/lib` it imports (read its import block; adding a release is such a change), restarts Vite inside a running dev server, and a tab on it can then load blank with nothing in the console.** Restart your own server and reload; the owner's on 3000 needs the same restart, which is theirs to make, so tell them. If the console says `jsxDEV is not a function`, stop the server, delete `node_modules/.vite/deps` and start it again. **With two dev servers running (3000 and 3001 share that cache), stop both first and start them one at a time**: re-optimising both at once into one folder loads two copies of React (`Cannot read properties of null (reading 'useSyncExternalStore')`) and leaves `deps_temp_*` folders behind.
- **`npm start` needs `npm run build` first and must run from the repo root** (it serves `process.cwd()/dist`; the bundle bakes in `NODE_ENV=production`).
- **`.env` holds no Gemini key.** `.env.example` documents the variables there are (`VITE_FORMA_MOCK`, `VITE_FIREBASE_EMULATORS`, `PORT`, `HOST`, `HTTPS`); `.env*` is gitignored except that file. `APP_URL` was removed as read by nothing: do not restore it or read it.
- **Leave `vite.config.ts`'s HMR block** (*"Do not modify"*, file watching gated on `DISABLE_HMR`) **and `watch: { ignored: ['**/tools/**'] }` alone**: chokidar throws `EBUSY` on MSBuild's locked `bin/`/`obj/` files and takes the dev server down.
- `src/App.tsx` is several thousand lines and keeps growing: grep for a symbol, never trust a line number in this file or a note.

### Tests in practice

- **One file: `npx vitest run src/lib/repx.test.ts`; one case: add `-t "<name>"`.** Narrowing buys clarity; how much time it saves depends on the cache, and [`testing.md`](docs/notes/testing.md), *Running one file, and what that does not buy you*, says why no timing is written down.
- **If every jsdom file dies at once with `[vitest-pool-runner]: Timeout waiting for worker to respond`, nothing is broken and re-running will not help**: jsdom's cold load exceeds Vitest's worker-start timeout. Warm it in a process nothing is timing, `node -e "import('jsdom')"`, then run the suite. A timeout in only the first case of a file is a lazy loader paying its cold import inside that test's budget, not a slow test. Both are in [`testing.md`](docs/notes/testing.md), *A cold cache can look exactly like a broken install*.
- **The rules suite runs under its own config**: `firebase emulators:exec --only firestore "vitest run --config vitest.rules.config.ts"`. A single rules case needs a space-free regex to survive PowerShell's re-parsing ([`testing.md`](docs/notes/testing.md), *Running a single rules case: use a space-free regex*).

### Repository settings

- **`.claude/settings.json` is the committed permission allowlist**: `npm run *`, `npm test`, `npm ls *`, `npx tsc *`, `npx vitest *`, `New-Item *`, `Get-Process *`, which covers every check above and every `npm run` script. `npm test` and `npm start` are not `npm run test` / `npm run start`, so `npm test` has its own entry and `npm start` (a long-lived server) prompts, as the env-prefixed mock-server line may. Personal permissions go in `settings.local.json`, which is gitignored.
- **The pre-commit hook is opt-in**: `git config core.hooksPath .githooks` once per clone, `--no-verify` to bypass one commit. `.githooks/pre-commit.mjs` blocks files over 1 MB, backup and archive extensions, log files, copy-looking names, OS droppings and an assignment of a real-looking API key. Git here is MinGit, with no MSYS userland, which is why the logic is Node; if you rewrite it, verify it with a commit that should fail.
- **`.gitignore`'s credential patterns are a backstop, not permission**: `key.txt`, `*.key`, `*apikey*`, `*api-key*`, `secrets.json`, Firebase service-account keys (`*firebase-adminsdk*.json`, `service-account*.json`) and the backup's `forma-firestore-*.ndjson`. A Gemini key belongs in the app's Settings (`sessionStorage`); a service-account key belongs on the owner's own PC, outside the repository.
- **`.firebaserc` stays tracked**: it names the deploy target and holds no credential, and ignoring it is how a clone deploys to whichever project the CLI last selected. `.firebase/` is ignored.

## Structure conventions

These hold everywhere today, and nothing in the toolchain enforces them. `CONTRIBUTING.md`'s *Structure* section is the public copy.

- **`src/lib` is browser code; `src/server` is not.** `server.ts` imports `securityHeaders`, `appRoutes`, `bindHost` and `staticCache` from `src/server/`; no browser code may import from it (tests may). Those modules stay under `src/` because `vitest.config.ts` includes only `src/**/*.test.{ts,tsx}`: moving them out silently drops their tests unless the include widens in the same commit.
- **Naming under `src/`: `PascalCase.tsx` for React components, `camelCase.ts` for everything else**, with one exception, `src/vite-env.d.ts` (Vite's conventional name). Not every `.tsx` is a component: entry points, modules exporting collections (`icons.tsx`, `sections.tsx`, `infoPages.tsx`, `faqs.tsx`, `publicPages.tsx`, `docsCorpus.tsx`) and colocated `*.test.tsx` files are not; do not rename them. `scripts/` uses kebab-case for some entry scripts and root configs follow their tools' names. To count, `git ls-files | Where-Object { $_ -like '*.tsx' }` (a pathspec like `'src/**/*.tsx'` drops the files directly in `src/`).
- **Tests are colocated** (`*.test.ts[x]` beside the module); **`tests/` at the root is only for the emulator**, which is what keeps `npm test` from starting a JVM. A module can have a file in both.
- **No barrel files**, and **no `@` path alias**: every import is relative. An alias has to be declared in `tsconfig.json`, `vite.config.ts` and `vitest.config.ts` at once and actually used, or not at all.
- **Where new code goes**: a pure helper in `src/lib`, a server helper in `src/server`, a component in `src/components` (`landing/` for a landing-page figure). **A new top-level directory needs a stated reason**; the current set is what `git ls-tree --name-only -d HEAD` prints.
- **`docs/` holds the project's documentation prose**, apart from the root-level community files and the READMEs that live beside the code they describe (`tools/`, `src/fonts/`, `assets/pdf-fonts/`). `PRD.md` and `notes/` are current and maintained against the code; `design/DESIGN.md` is the design source of truth; `proposals/` holds what has not graduated into `notes/` (when one proves out, its reasoning moves into `notes/` and the proposal goes); `skills/devexpress-repx/SKILL.md` is what Forma measured about the REPX format, written for a person or a coding assistant working on a `.repx` outside the app (`scripts/repx.ts` is its command line); `audit/README.md` is a dated index of the audit identifiers (`ARC-001`, `PERF-002`…) that comments across the code cite, and owns their count. **`docs/media/` is the only place a screenshot may be committed**, and its README carries the capture and recapture rules.
- **Removal sites carry a comment dating the removal**; `git log -S'<symbol>'` finds the commit. The 2026-08-28 cleanup pass is recorded in its commit messages, `git log 2ce6e56..9a8163c`.
