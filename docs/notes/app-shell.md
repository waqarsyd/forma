# The app shell

Split out of `CLAUDE.md` on 2026-08-13, carried across unchanged at the time apart from heading levels and the cross-references, which name the note they point at instead of saying "above". **It has grown since, so do not read it as a snapshot of that date** — every note here has taken new material in the weeks after the split, and `git log -- docs/notes/` is the record of what arrived when. (This paragraph claimed the text was still unchanged until 2026-08-20, by which point all four notes had been edited four or more times.) It is incident history — the reason a thing is the way it is, which the code cannot tell you. **Nothing here is loaded automatically**: `CLAUDE.md` routes to this file, and reading its one-line summary of this area is not a substitute for opening it before you change that area.

## `src/App.tsx` is the whole app

It is several thousand lines (a figure that only ever grows — don't trust a number written here, and don't reintroduce one into this heading where it will silently rot). It holds the workspace, chat and config modal. The two components it used to define inline, `RepxViewer` (the XML pane, whose pure helpers were extracted to `src/lib/repx.ts` — see below) and `ReportMockup` (renders `layout` as absolutely-positioned divs), are their own lazy files under `src/components/` since 2026-11-06, moved unchanged to make room in the entry chunk.

**The chat's rules are in `src/lib/chatSession.ts` as of 2026-09-08, and the chat itself is staying where it is.** Five things were inline in `App.tsx` where no test could reach them: whether a turn is conversation or work, the history the model is actually sent, the two rewrites a retry performs, and the note count. They are pure functions now, with 21 cases — the table in [`testing.md`](testing.md) is
the authority for that number, and this said nineteen until 2026-09-08. Three details are worth keeping.

`ChatMessage` is **generic over both its result type and its attachment metadata** — `ChatMessage<DesignResult, PreviewMeta>`, aliased back to plain `ChatMessage` at the top of `App.tsx` so no use site changed. `DesignResult` lives in `App.tsx`, and a `src/lib` module importing from the component layer is the wrong direction; `savedReport.ts` had already solved this with `M` and `R` parameters it never looks inside. The metadata parameter is not decoration: the transcript hands `imageMeta` straight to `groupAttachments`, which groups by `uploadId` — exactly the field a "good enough" inline shape omits, so a structural minimum compiles in the module and fails at the call site. `ChatHistoryTurn` restates `ChatTurn` from `geminiService.ts` rather than importing it, for the same rule in the other direction: `lib` does not import `services`. The two are structurally identical, so the array is assignable with no cast and the compiler reports it at the call site if that ever stops being true.

**The history deliberately carries nothing but `role` and `text`, and that is the expensive one.** `images` holds base64 data URLs; sending whole message objects would re-upload every previously attached page on every subsequent chat turn, billed each time. It equally deliberately does **not** filter out a message carrying an `error`, or the assistant's own "Generation stopped by user." line — both are things that happened in the conversation, and hiding them produces a model answering as though they had not.

**The transcript render followed on the same day, as `src/components/ChatThread.tsx`, and the order it was done in is the point.** The markup had no coverage of any kind, so the component was written and its nineteen render cases were passing *before* `App.tsx` was switched over to it — extract-then-check would have been unverified by construction, which is the order that produced the bug `DataBinding.test.tsx` was added after. The test was then confirmed to have teeth by deleting the `!isAnalyzing` guard and watching the right case fail. Two checks agreed the swap changed nothing: the suite, and a real session whose screenshots came back **byte-identical** to the pre-extraction run at all three steps.

**The composer followed as `src/components/Composer.tsx`, in the same order and with the same result** — twenty-four cases passing before the swap, the screenshots byte-identical again, `App.tsx` down another 130 lines. Two of those cases exist for hazards the markup had only carried a comment about, and both were confirmed to fail when mutated. **The send button must be wrapped rather than handed its callback bare**: `onSend` is `handleGenerate`, whose first parameter is an optional prompt override, so `onClick={onSend}` passes React's synthetic click event as that override — truthy, so it generates against an event object instead of the typed prompt. The test asserts it is called with *no arguments*, which is what pins the wrapper. And **Enter sends while Shift+Enter must not**, or a deliberate line break fires the request. `fileInputRef` is passed in rather than owned, because `App.tsx` clears `.value` on it after an upload so the same file can be chosen twice running; owning it here would have broken that silently.

**Two real defects fell out of the extraction, and neither came from the suite.**

**Enter bypassed the send button entirely.** The button carried `disabled={!hasApiKey || isAnalyzing || isIngesting}`; the keydown handler on the input beside it carried nothing, so Enter sent regardless of what was already running — and `handleGenerate` had no re-entry guard, while `handleRetryMessage` had always had one. That asymmetry is what gave it away. Pressing Enter during a generation started a second one writing to the same progress state and the same `activePromptRef`; during a chat turn it started a second turn whose history came from a `messages` closure captured before the first reply landed, so the model was sent a conversation missing a turn. `isChatting` was not in the button's condition either, so that control was fully live throughout a chat turn. Fixed in both places — one `canSend` in the composer that the button *and* the keyboard read, and a guard in `handleGenerate` so it holds regardless of who calls. Five tests, written first and watched to fail.

**Then the fix broke focus, and only a pixel diff found it.** `.wb-box` draws its ring on `:focus-within`, so clicking send lights the composer because the *button* holds focus. The moment `canSend` included `isChatting`, that button began disabling itself mid-request — and a disabled element loses focus, which no browser gives back when it re-enables. Two screenshots that looked identical to the eye differed by 11,116 pixels, all inside the review column. **The same defect turned out to predate the change**: the button already disabled on `isAnalyzing`, so clicking send during a generation had always dropped the user to the top of the document. Sending now returns the caret to the field, which fixes both paths and is where the next keystroke wants to be anyway. Move focus *before* React disables the button, or there is nothing to move.

**The transcript is memoised, and the number is the argument.** Typing 22 characters into the composer with six notes on screen re-rendered every note on every keystroke — **264 note renders for one sentence**, each image-bearing note re-running `groupAttachments`, because the transcript is a child of the component that owns the composer's `prompt` state. Measured over CDP with a temporary counter, then again after: **264 → 0**. `ChatNote` is `memo`'d on its message, which is safe because messages are immutable. The hazard that introduces is a row keeping the *first* callback it was handed, whose closure holds the transcript as it was then — so the callbacks are read through a ref, and a test proves a retry reaches the newest handler. Confirmed by mutation: a comparator that ignores the callbacks fails exactly those cases.

**The designer probe is throttled on focus as of 2026-09-08, and the reason is the comment three lines above it.** Re-checking when the tab regains focus is deliberate — starting the companion happens outside the browser, so a mount-only ping leaves the button missing when the user switches back. But a refused connection is logged by the browser itself and no `catch` can suppress it, so someone alt-tabbing while they work produces one `ERR_CONNECTION_REFUSED` per switch. Four consecutive logs sent in from real use had those lines outnumbering everything else in the console, which is precisely the failure the effect's own comment already warned about: *a predictable error on every page load is noise that hides the unpredictable ones.* A focus re-check needs 30 seconds since the last one (`shouldRecheckDesigner`). Nobody launches a Windows desktop app and returns to the tab inside half a minute, so nothing that mattered was traded away.

**And the mount ping was narrowed the same day, by the same argument one step further.** The effect had already been scoped from "every page" to "the workspace"; but the workspace opens *empty*, and the button is disabled until a report has XML to open — so it was still probing before anything could use the answer. It now waits for `hasRepxToOpen`. Nothing degrades while unprobed: `designerReady` only picks the tooltip and decides whether a click sends to a running designer or launches one, and `false` takes the launch path, which is the correct fallback regardless. Measured over CDP with `performance.getEntriesByType('resource')` rather than the console — **a refused connection is logged by the browser's network stack, not through `console.*`, so it never appears in the driver's `console.txt` and cannot be counted there.** Empty workspace: 0 probes. After a generation: 1.

**The conversation can be exported (2026-11-05)**, as Gemini exports a chat: a download icon beside the search in the Chat head writes "<report> - chat.md" (`conversationMarkdown` in `lib/chatSession.ts`): the report's name, then each message under who said it and when, Forma's replies as written since they are Markdown already, the person's words as a quote so a heading or a list typed in a message stays text, and pictures counted rather than embedded. Read in the browser and saved by it; nothing is uploaded. Checked in the owner's Chrome in mock mode with the download caught in the page, so no file was saved to the owner's machine.

**ChatGPT's keyboard shortcuts (2026-11-05)**, beside the sidebar's Ctrl+B in the same keydown handler: **Ctrl+Shift+O** (Cmd+Shift+O) a new report, which saves the last one first as the New report button does; **Shift+Esc** the cursor to the chat box from anywhere; **Ctrl+Shift+C** the last of Forma's replies on the clipboard, said beside Save. `chatShortcutOf` in `lib/shortcuts.ts` reads the exact combination and nothing else held, never mid-composition; the handler is a ref assigned beside `showPlate` (`chatShortcutRef`), as the tools' runner is, so the effect never holds a stale one. A browser keeps some combinations for itself (Chrome's Ctrl+Shift+C can open its inspector), as it does for ChatGPT, which documents the same one; Copy under a reply is the way that always works. The New report button's tooltip names its shortcut. Checked in the owner's Chrome in mock mode: Shift+Esc focused the box and Ctrl+Shift+O emptied a 23-message conversation into a new report; Ctrl+Shift+C was not pressed there, as it would have replaced the owner's clipboard.

**A tab that finished something unseen says so (2026-11-05).** A report built, an edit made or a reply written while the person was in another tab puts "✓ Report ready — Forma" or "✓ Reply ready — Forma" in the tab's title (`readyTitle` in `lib/routes.ts`, `announceReady` in `App.tsx`), and the route's own title returns on the first `visibilitychange` back; the route effect stays the title's only writer the rest of the time, and a visible tab is never touched. Checked in the owner's Chrome by overriding `document.hidden` in the mock-mode tab: the reply set the ready title, and coming back restored "Workspace — Forma". **Since 2026-11-07 (agent audit item 63) a question waiting and a request that failed say so too** ("? A question for you — Forma", "! Request failed — Forma"): one effect reads how a turn ended when it ends, from the newest request's `requestState`, where five success paths each called `announceReady` and nothing else changed the title, so a tab waiting on the person looked idle.

**When a message was made, and what a reply cost (2026-11-05)**, quiet beside its icons and so shown as they are: "Today, 10:42 · 23.4k tokens". The time is read off the message's id (`messageTime` in `lib/chatSession.ts`; `nextMessageId` starts with the time, and saved messages from before it are the bare time), so old conversations have it without a field; the cost is the report's `usage`, which App hands the thread as `usageOf`, so a reply that built nothing shows the time alone.

**The box floats over the conversation (2026-11-05)**, at the owner's request, measured first on Gemini with REA: a signed-out throwaway browser asked for a 30-line list, and the screenshot showed the list running on behind the box, lines faint beside and below it, and no band or line under the conversation. Forma does the same. The composer measures its own height into its column as `--composer-h` (a ResizeObserver, since the box grows with a long message, staged files and notices) and overlaps the foot of `.wb-thread` by exactly that, over a fade from clear to nearly the column's ground; the box stays opaque. The thread pads its foot by the same height, so its last message still scrolls clear of the box (36px, measured). The way back to the latest message keeps `bottom: 4px`: sticky positioning measures from inside that padding, and adding the height there too put it some 90px high.

**No orange edge on the chat box or the search field when focused (2026-11-05)**, at the owner's request: focus darkens the edge to `--rule-strong` and, on the box, lifts the shadow, as ChatGPT's box does. It was the accent. Focus stays plainly visible, which is what the box's no-outline rule relies on.

**The box's attach button is a plus (2026-11-05)**, at the owner's request, as ChatGPT's and Gemini's are at the left of their boxes: "Add photos and files" (ChatGPT's words) opens the same file picker the paperclip did, and the paperclip icon went with it.

**A message can be spoken (2026-11-05)**, as ChatGPT's and Gemini's boxes take one: a microphone beside the send button, offered only where the browser has speech recognition (`SpeechRecognition`, Chrome's and Edge's `webkitSpeechRecognition`), writes what it hears into the box after whatever was typed, in the browser's language, as it is heard, and stops at a pause or when pressed again. Nothing is installed or paid for. It needed the site's `Permissions-Policy` to give the microphone to the page itself (`microphone=(self)`, never `*`) where it had been off for everything; `securityHeaders.ts` says why and what it costs, `hostingConfig.test.ts` held `firebase.json` to it, and `securityHeaders.test.ts` checks that no frame gets it. In Chrome the audio is heard by Google and in Edge by Microsoft, which is the browser's doing and only after the press; the browser asks before the first. Not clicked in the owner's Chrome, since it would have asked them for the microphone; the Composer's test drives a fake recogniser.

**What is typed and not sent survives a reload (2026-11-05)**, as a ChatGPT draft does: `prompt` is read from and written to `sessionStorage` (`forma:draft`, 300 ms after the last keystroke), per tab as the key is, because this may be a shared machine and an unsent message is the person's words. Sending, New report and signing out empty the box and so the draft. **Since 2026-11-07 (agent audit item 69) a draft per project**, as ChatGPT keeps one per chat (`lib/composerStore.ts`, `forma:drafts`): opening a project shows the words left in its box, New report starts empty, a report's first save moves its words to its id, deleting a project drops its draft and signing out drops them all. Files attached still stay in the box when another project is opened, as they did: they are not kept over a reload either.

**A button takes a reader scrolled up back to the latest message (2026-11-05)**, as ChatGPT and Gemini show one: a round arrow, sticky at the foot of `.wb-thread`, shown only while the reader is away from the bottom (`away`, set only when it changes so scrolling does not re-render the thread every frame). Its negative top margin cancels its own height and the column's gap, so it appearing does not change the scroll height it depends on; for a second after it is pressed, the smooth scroll on its way down does not bring it back.

**The transcript follows the conversation as of 2026-09-08, and it had not since the port.** Reported from real use: once the transcript outgrew the column every reply landed below the fold and had to be scrolled to by hand. `App.tsx` had carried a `messagesEndRef` and a `scrollIntoView` effect since before the 2026-08-12 rebuild — but that rebuild replaced the markup with the artifact's, which has no sentinel div, so the ref attached to nothing and the effect ran against `null` on every message for weeks. **Neither the type checker nor the unused sweep can see this**: the ref and the effect reference each other, so both look live. `git log -S'ref={messagesEndRef}'` names `674f4cd` as the commit that took it, which is the port itself.

The follow now lives in `ChatThread`, which owns `.wb-thread` — the element with `overflow-y: auto` — and the dead ref and effect are gone from `App.tsx` rather than reattached. **The half that makes it bearable is `pinned`**: scrolling up to re-read an earlier answer must not be undone by the next reply arriving, so the position is recorded on every scroll and the follow only fires when the reader was already at the bottom. The 40px slack matters — a fractional `scrollTop` from a trackpad or a zoomed page otherwise reads as "not quite at the bottom" forever and the thread silently stops following. `scrollTop` is assigned rather than `scrollTo({ behavior: 'smooth' })`, because a streamed reply updates many times a second and successive smooth scrolls queue up and lag behind the text they are meant to follow. Verified live at 14 notes: content 1,319px in a 745px column, `distanceFromBottom` 0, newest note fully visible.

**Removing that markup orphaned four imports** — `IconArrowUp`, `IconDoc`, `IconPaperclip` and `groupLabel` — which `npx tsc --noEmit --noUnusedLocals` caught and nothing else would have. That is the same class of leftover as `MobileNav` when `LandingPage` came out, and it is the reason the unused sweep is on the check list rather than being folded into `npm run lint`.

`ChatThread` owns `.wb-thread` and takes the generation progress card as `children` (since 2026-11-04 that is Forma's working dots; see *The workspace is as clean as a chat app*). The card is generation state — the ring, pause and stop, the elapsed-time explanation — and pulling it in would have meant ten props about a job the transcript has no opinion on; passing it through keeps the emitted DOM identical to the markup it replaced, which is what made the byte-identical comparison possible. **The `!isAnalyzing` guard on the thinking placeholder is the subtle one**: a message the assistant judges to be a real build request runs the chat turn *and then* falls through to generation, so both flags are true together for a moment, and without it the placeholder sits above the progress card claiming a second job. `handleGenerate`'s branch and the composer are still in `App.tsx`.

**Do not turn the chat into its own page or route.** It reads like the obvious tidy-up — every other surface is a page — and it would break the product. The chat is the control surface for the report: a refinement turn sends the previous `layout` and `repxContent` so the model edits the existing report rather than starting again, and an attachment on a message *is* the request to build. A separate page is either severed from the report it operates on, or a duplicate of the whole result pipeline. Splitting it as **code** is worth doing; splitting it as a **surface** is not.

**All six page-level surfaces now live in `src/components/`**: `LandingPage`, `FeaturesPage`, `DocsPage`, `ContactPage`, `LoginPage` and `LegalPage` (added 2026-08-15, serving `/terms` and `/privacy` — see below), alongside `MobileNav`, `UserAvatar`, `AccountDialog` and `Logo`. `src/components/landing/` is **the marketing design system, not the home page's private folder** — the name is historical. Two tiers live there: `sections.tsx` (the reveal wrappers, `SectionHead`, `Eyebrow`, `Stat` and the `H2`/`LEDE`/`BODY` type scale), `icons.tsx` and `SheetRuler` are shared furniture — `LandingPage` and `FeaturesPage` both build on them and `SiteHeader` pulls `IconSun`/`IconMoon` from `icons.tsx`; while `HeroScanner` (the scan → detect → type sequence), `VaultFigure` and `StepFigures` really are home-page-only figures. Build a new marketing surface out of the first tier rather than restating its markup, and add new icons to `icons.tsx` rather than starting a second set. (This bullet used to read "landing-page-specific by design; nothing else imports them", which was already untrue of `icons.tsx` and stopped being true of the rest when the Features page was rebuilt on 2026-08-11.) The five pages that mount the chrome take the same props — `onEnterWorkspace`, `onSignIn`, `onSignUp`, `user`, `logOut`, `isDarkMode`, `setIsDarkMode` — and pass them straight through to it; `LegalPage` adds `doc` on top, to choose which of the two documents it renders. `LandingPage` was extracted on 2026-08-09; it had been inline while its three siblings were not, which is why header fixes kept having to be applied to it separately. Note that pulling it out orphaned `MobileNav`'s import in `App.tsx`, since the landing page was its only consumer there — the unused sweep catches that class of leftover.

**`DocsPage`, `ContactPage` and `LoginPage` were rebuilt on 2026-08-11, and each rewrite corrected something that had stopped being true.** The visual work is the smaller half; do not reintroduce any of these:

- **Docs** told readers Forma "operates using a shared developers API key" and that their own key was "stored securely within your browser's local state (`localStorage`)". The app owns no key, and that `localStorage` entry is *purged on boot* — describing plaintext on disk as secure was the worst line in the repo. It also put `overflow-hidden` on `<main>` while the sidebar used `sticky`; **an overflow ancestor silently disables sticky**, so the docs nav scrolled away. Nothing above that `<aside>` may set overflow.
- **Contact** displayed `support@forma.com` over a `mailto:` pointing somewhere else, linked Github/Discord/LinkedIn all at `/`, and — the serious one — its `catch` block set the success state, so a failed send told the sender "we've received your message" while dropping it. A rejected request must reach the failure state; there is no path from `catch` to `sent`. The address is now assembled from two halves at click time and never appears in the markup, and the form carries an off-canvas honeypot.
- **Login** kept its logic (that part was already careful) and lost its surface: a blurred ring pulsing behind the submit button on an endless loop, a "Verified Stack" badge asserting a guarantee nobody made, Privacy/Terms pointing at `/`, and two `rounded-xl` buttons — the only place in the app that broke the everything-is-a-pill rule.

**The home page has an announcement dock (2026-08-14)** — `src/components/landing/AnnouncementDock.tsx`, a 44px disc in the bottom-right corner that opens the product's notes, modelled on the corner launcher pattern Dribbble uses. Since 2026-11-07 its notes are the releases marked `announce` in `lib/releases.ts`, and it ends with "Read the changelog" (see *The changelog is a page of its own*). It is lazy since then too: imported eagerly by `LandingPage`, it put every release note into the entry chunk (+13 kB, 99.5% of its budget); lazy, the entry fell to 652,525 B and the notes are one shared 12.8 kB chunk. Five things to know before touching it:

- **Home only.** It is a first-visit surface. `/features`, `/docs` and `/contact` are reference material people arrive at on purpose, and the workspace already carries a rail, a review column and a status bar — a disc floating over a tool someone is working in is one thing too many. Verified absent on all four — and the durable form of that check is that `AnnouncementDock` is imported by `LandingPage` alone, which is why `/terms` and `/privacy`, added later, inherited the rule without anyone applying it.
- **Bottom-right, and the right has nothing else in it.** It shipped bottom-left first and had to dodge `SheetRuler` (`fixed left-0 w-11` from `xl` up) with an `xl:left-16` offset — 44px of ruler plus the 20px inset. Moved to the right on request the same day, which is also the corner the reference uses; the offset went with it, and the panel anchors `right-0` because leftwards is the only direction with room.
- **Opening is what marks the notes read**, not a dismiss button: the dot exists to get the panel opened once, and a badge that survives being read is a badge people learn to ignore. The newest id goes to `localStorage['announcementsSeenId']`, and every `localStorage` access is guarded — a locked-down profile makes every visit a first visit, which is the right way to fail.
- **The entries live in `src/lib/announcements.ts`, newest first, and must describe the shipped app.** This is the one surface where the product talks about itself to someone who has not used it, so a note about something not actually there costs more than no note. `unseenCount()` is tested: an unrecognised stored id counts everything as unseen rather than nothing, because showing a stale dot is a smaller failure than never showing one again.
- **A note goes stale because the event happened, not because the note broke — and nothing checks that.** The dock carried *"Soon, I'll be open-sourcing the project… stay tuned"* for a day after the repository went public on 2026-09-09. It was true when written, it still rendered perfectly, every test passed, and the front page told each new visitor that a thing was coming which had already arrived. **So shipping a milestone is a change to `announcements.ts`**, in the same way the version list is a change to seven files and a rail button is a change to `docs/media/`. When the entry is superseded rather than wrong, add the new one above it and keep the old: read together, *"Going open source"* and *"It's done"* are a better story than either alone, which is why the pair is what shipped. **Give the new entry a genuinely new `id`** — reusing one leaves the unread dot unlit for everyone who read the original, because "seen" is remembered by id and nothing else. Each entry's `date` is displayed on the title line from 2026-09-10, styled as body text (`font-normal` is required, or the span inherits the heading's `font-semibold` and the date reads as part of the title); it stays a plain ISO string because it is simultaneously the sort key the newest-first test pins.

**`HeroScanner`'s page is drawn in report units, and that is load-bearing (2026-08-14).** `PAGE` is 850 × 1100 — the same units `LocationFloat` and `SizeF` carry — and five rectangles (`PICTURE`, `TITLE`, `BILL_TO`, `TABLE`, `TOTAL`) hold the controls in those units. The page is laid out from them and the typed XML is built from them; percentages exist only as the `px()` / `py()` output.

**The outlined "detected" regions and their coordinate captions are gone**, removed on request the same day. They covered the document they were pointing at, and once the page was properly typeset they were the only thing still making the figure read as a diagram rather than a scan. The sweep and the XML carry that story without annotating over the invoice. The rectangles stayed — they are geometry, not decoration.

It was three sets of numbers that disagreed, in a figure whose entire subject is coordinates being read correctly. The picture region was captioned `160,90` — 8.2% of the page — and drawn 14.2% tall; the table declared `SizeF="770,124"` (11.3%) and was drawn across 27.4%; the total was captioned `570,770` and drawn at 61.8%, 74% instead of 67.1%, 70%. **Every box asserted a number it did not honour.** Nobody would have caught it by looking, which is exactly why it is worth keeping the derivation: a caption cannot drift from its own geometry when it is generated from it.

**The second pass was about size and weight, and those numbers are worth keeping too.** The page was 212 × 274 inside a 273 × 474 pane — 200px of dotted background, 58% of the column's height — while the code pane beside it ran edge to edge; the document that is the subject of the figure was the smallest thing in it. Padding 22 → 16 and a 212 → 248 cap put the sheet at 240 × 311 and lifted the scale from 0.25 to 0.28 px per report unit, which is what makes the ruled table read as a table. **The rest of the slack was the code column, because that is what sets the card's height** — the page cannot grow past its own column's width, so every XML line beyond the sheet's height is dotted bed around it. Folding each element name onto its `<ItemN` line, which is how anyone actually reads REPX, took 23 lines to 18 without dropping an attribute; nothing may exceed ~42 characters there, because the pane wraps at that width and a wrapped line costs the same as a written one. Card 516 → 416, slack 82 → 32 a side, the sheet at 83% of its column. The `<pre>` also carries a `min-h` equal to the finished block, since the pane grows a line at a time while the XML types and the card — and the hero beside it — used to step taller eighteen times during the animation; measured after the change, the card holds 416 from first frame to last. The overlay was toned down in the same pass — fill from `--accent-wash` to `secondary-container/[0.07]`, captions from 12px to 5.5px — before being removed outright, which is the honest reading of that work: each step made the annotation quieter until the answer turned out to be *no annotation*. **The third pass threw the bars away, and that is the one that mattered.** The page had been grey rectangles standing in for words — "geometry rather than art", defensible in the abstract and wrong for this figure. A hero whose whole job is to say *this reads real documents and writes real files* cannot show a placeholder: bars read as unfinished, and unfinished reads as *does this actually work?* — which is exactly how it was reported. It is now typeset: an issuer block, invoice number and date, bill-to and ship-to, four line items with descriptions, quantities and amounts, subtotal, VAT, a filled total row, payment terms and a footer. The type is small because it is at **true scale** — 850 units shown 240px wide is 28px to the inch, so 10pt body copy really is ~4px, which is what a document thumbnail looks like and why it now reads as a page rather than a wireframe of one. Sizes are `cqw` against the sheet's own `container-type: inline-size`, so every glyph scales with the page instead of pinning itself to a pixel size the sheet may not have.

Three things clipped when the text went in, all fixed by giving glyphs the inset a real control has: amounts right-aligned to the 810 margin were cut by the table's own right border (they end at `CELL_RIGHT`, 790, now), and both the heading and every address line in the bill-to block lost its first character to the detected box's left border (inset 10 units). Text sitting exactly on `LocationFloat` renders *under* the box that marks it — a label's glyphs begin a few units inside its bounds, as they do in print.

**Replay was a dead control on any machine that prefers reduced motion, and Windows is one of them.** `run()` short-circuited to the finished state whenever `useReducedMotion()` was true — including a run the user had just asked for by clicking. Measured with the media feature emulated: after a click, the typed length stayed at its final 502 characters across eight samples, while the identical click under `no-preference` reset it to 0 and re-typed. **Chromium reports the preference whenever Windows' "Show animations in Windows" is off, which is the default on Server editions**, so this was not an edge case — those visitors never saw the animation at all and the button did nothing when they asked for it. `run(force)` now separates the two: arriving at the page still animates nothing under the preference, and a click animates regardless, which is the standing exception in WCAG's guidance for user-initiated motion. `animating` (per-run) replaced `prefersReduced` at all four use sites — the sweep, the box delays, the chip delays. Note the handler must be `() => run(true)`; passing `run` directly would hand it the click event as `force`, which is truthy by accident rather than intent.

**`SheetRuler`'s scroll marker must not paint while it is behind `SiteHeader`, and `HEADER_CLEARANCE` is what stops it.** The rule carries a live marker — a 2px `bg-secondary-container` bar with a `y 0000` chip riding it, positioned by scroll progress. At scroll 0 that puts **solid brand orange at 0,0 of the viewport**, and the header is `sticky top-0 z-50` with `backdrop-filter: blur(16px) saturate(1.5)` over `bg-surface/[0.84]` — so the header does not hide the marker, it *smears* it. Shipped that way, it painted a shapeless orange stain into the top-left corner of every page the rule renders on (all six marketing pages), on every load, before any scrolling, and was reported as "an orange background showing somewhere in all the pages" — which is exactly how an unplaceable smudge reads. **A translucent blurred header is not an occluder:** anything drawn under one has to hide itself rather than rely on being covered.

The fix is a fade, not a deletion. The marker was cut entirely on 2026-08-27 and asked for back the same day — it is the one piece of chrome on these pages that is live rather than decorative, and losing it to fix a corner artefact was the wrong trade. It now fades out below `HEADER_CLEARANCE` (76px — the header's 69px plus daylight, and there is no shared token, so a change to the header's height is a change here too) and fades back in the moment it clears. Note what that costs: on a long page the marker travels a fraction of the viewport per screen of scroll, so it stays hidden for roughly the first 8% of the page. That is the intended behaviour, not a bug to "fix" by lowering the threshold.

**The marker's readout must be derived from its position, never computed alongside it — three coordinate systems met in this one small component and two of them were wrong.** The tick labels are a *viewport* scale: a major every 96px, printed as `(y / 96) * 100`, so viewport y 384 reads "400". The marker's `top` is a *fraction of the document* mapped onto the viewport height. The chip used to be a third thing again — `(window.scrollY / 96) * 100`, the document's *absolute* scroll offset — so the number printed on the chip and the number printed on the rule beside it could only ever agree at zero. Measured across six pages at four scroll positions each: **0 of 22 agreed, worst by 8,669 units on `/docs`**, where the chip read 9,509 on a rule whose largest label is 900. Nothing threw and nothing looked broken, because every number was correct in a system the other two were not using — the same failure mode `reportGeometry.ts` exists to prevent in the report pipeline, on a different surface. `units` is now derived in the render from `top` using the *same expression the tick labels use*, which makes disagreement unrepresentable rather than merely fixed; the same measurement now reads 24 of 24 with zero drift. If you ever move it back into the scroll handler, you have reintroduced the bug.

**It cannot be reused in the workspace, and this is why.** It is `fixed inset-y-0 left-0` and driven by `window.scroll` plus `document.body.scrollHeight`. The workspace is a `height: 100vh` frame whose scrolling happens *inside* panes, so the component would pin to the viewport's left edge — over the rail, not the bench — with a marker that never moves because the window never scrolls. A static decorative copy was considered and rejected: the marketing ruler earns its place by actually reading out scroll position in report units, and a fake one on a surface whose sheet is drawn at a computed `scale` would imply a measurement it cannot make.

**`ReportMockup` is a scaled pixel sheet, not a responsive layout.** Every coordinate from `layout` is multiplied by `0.96` and set as an absolute `left/top/width/height`; the page cannot reflow, so a `ResizeObserver` measures the viewport and applies `transform: scale()` to the whole sheet, with an outer stage div sized to the post-scale footprint so nothing overlaps. Everything inside the sheet is drawn against the **theme-invariant `--paper` / `--on-paper` / `--paper-accent` / `--paper-accent-soft` tokens** — all four deliberately identical in `:root` and `.dark`, since a rendered report must look the same in both themes. Using `bg-card`/`text-foreground` or any other flipping token inside the sheet is a bug, not a shortcut. That was not hypothetical: the chart bars used `bg-primary/40` and the gauge arc `border-t-primary`, and `--primary` **does** flip (`#FF5E00` → `#FF6C1A`), so a generated report quietly changed colour with the app theme. `--paper-accent` exists so there is a correct token to reach for instead of a literal.

**Do not wrap `ReportMockup` in a frame — it draws its own.** Border, radius, shadow, max-width and the grey inset around the page are all inside the component. The canvas used to wrap it in a second panel with its own border, shadow, rounding and `bg-paper`, which stacked white-then-grey-then-white with two borders and two shadows. The call site is now just `<ReportMockup … />` inside the scrolling canvas.

**The Mockup draws a repeated heading row once, and the layout still carries it twice (2026-09-06).** The `layout`'s PageHeader section holds the column headings, and the detail table repeats them as its own first row — so the mockup drew "Item Description / Amount" twice, a few units apart, on every report of that shape. It was reported as a mockup bug and it is one, but **the duplicate in the data has to stay.** `recordCountFromLayout` counts the detail table's rows and subtracts one for the heading, so deleting the row costs a record in the Preview and says nothing; and the prompt asks the model for every row it can see, *including* the header row, because the layout describes the SOURCE document rather than the report. Editing it to suit a renderer would make the pane lie about what came back. So the rule is in the renderer: [`src/lib/mockupRows.ts`](../../src/lib/mockupRows.ts) returns the detail tables whose first row an **earlier** section already drew, keyed by section and element index, and `MockupTable` skips it. Narrow on purpose — earlier only, so a totals table below does not license dropping a row above it; cell-for-cell equality, so a heading that was never repeated stays; never the last remaining row, so a one-row table cannot render empty; and blank rows never match each other. When nothing is duplicated nothing changes, which is what makes it safe on real reports rather than only on the mock. The last case in `mockupRows.test.ts` asserts the record count is untouched, so a later "simplification" that moves this into the data fails there. **Since 2026-11-05 a new report's layout is read off its REPX** (`lib/repxViews.ts`; *The AI writes the REPX, and Forma reads the rest off it* in [`gemini.md`](gemini.md)): the Mockup is the bands as designed, the heading in its Page header and one row in a Detail section named as printing once per record, so there is no duplicate for this rule to find. It stays for reports saved before then, whose layout the AI wrote.

**`checkRepx` now measures the geometry as well as the structure** (2026-08-26). It used to pass anything that parsed, had the right root and contained a `<Bands>` — which is exactly why it passed the margin bug described under *The units audit* in [`gemini.md`](gemini.md), where every control was an inch out and the right-hand column fell outside the printable width. Structure was all it ever looked at.

The check reads `PageWidth`/`PageHeight`/`Margins` off the root and, per band, compares each control's `LocationFloat` + `SizeF` against the printable area and the band's own `HeightF`, plus the bands' total against the page. Warnings name the control (`"amountTotal" runs to 820 across, past the 650-unit printable width`) because a count is not actionable and the name is what makes it findable in the designer.

Three things about it are deliberate and should survive any edit:

- **A geometry problem never sets `ok: false`.** `ok` gates Export and Open in designer; a control fifty units too wide still opens perfectly well, and refusing to export it would be a worse failure than the one being reported. Warnings are a separate field, and the REPX pane gets a third badge state — neither green (which hides the finding) nor red (which says the file is broken when it is not). A test asserts the export stays enabled.
- **Only controls directly inside a band's `<Controls>` are measured.** Anything nested inside another control is positioned relative to *that* parent, so measuring it against the page would invent failures; table rows and cells carry `Weight` and no `LocationFloat` at all. Checking less and being right is the trade.
- **No page size means no warnings.** Nothing to measure against is not the same as everything being wrong.

`RepxViewer` is dependency-free, and its three pure helpers now live in **`src/lib/repx.ts`** (moved out of `App.tsx` so they could be unit-tested without importing the app, pdf.js and Firebase into a test run — `src/lib/repx.test.ts` covers them): `formatXml()` re-indents (safe here only because DevExpress REPX is attribute-based with no meaningful text nodes — do not reuse it for general XML), `tokenizeXml()` returns **tokens rather than an HTML string** so the XML renders as React text nodes and can never be injected as markup, and `checkRepx()` runs a `DOMParser` pass asserting the document parses, that the root is `XtraReportsLayoutSerializer`, and that `<Bands>` exists. That check is the only thing standing between a malformed generation and the user discovering it when DevExpress refuses the file. `copyText()` stays in `App.tsx` (it touches the DOM directly) and falls back to a hidden textarea plus `execCommand` because `navigator.clipboard` is undefined outside a secure context — the same LAN-over-HTTP case that `isVaultAvailable()` guards (*Where the user's key lives* in [`gemini.md`](gemini.md)).

It used to be white in light mode with a hardcoded `dark:bg-[#0d1117]` twin. **Handwriting, researched (2026-11-04).** The owner asked for a free model to be researched and built only if usable. Tesseract's LSTM data is trained on print and reads handwriting poorly, so this is a second model, not a setting. What was found, from the model cards:
- **TrOCR-small-handwritten** (Microsoft, fine-tuned on the IAM English handwriting set): an MIT-licensed ONNX conversion (`Xenova/trocr-small-handwritten`) runs in the browser through Transformers.js. Quantized, its encoder is 23.1 MB and its merged decoder 40.5 MB, about 64 MB against OCR's 7, plus ONNX Runtime's WebAssembly. It reads **one text line at a time**, so Tesseract's line boxes would crop the lines and TrOCR read the ones Tesseract read at low confidence. English only; the TrOCR paper reports a character error rate near 4% on IAM's held-out lines.
- **DE·HTR** (Apache-2.0, ONNX Runtime Web): German only, also line by line.
- Nothing free covers Arabic, Hindi or Urdu handwriting in a browser.

Sources: [the model card](https://huggingface.co/microsoft/trocr-small-handwritten), [its ONNX files](https://huggingface.co/Xenova/trocr-small-handwritten/tree/main/onnx), [DE·HTR](https://huggingface.co/naeyn/de-htr-web-v2).

**Measured, then built (2026-11-04), after the owner said "yes download TrOCR and test it".** In a scratch project outside the repository (`forma-model-data/trocr-test`), TrOCR-small (quantized) and Tesseract with Forma's own English data read the same lines:

| lines | Tesseract | TrOCR | TrOCR where Tesseract's confidence is below 70 |
|---|---|---|---|
| 60 real handwritten (IAM validation, MIT on Hugging Face) | 47.4% of characters wrong | 10.1% | 10.6% |
| 40 report entries in Windows' handwriting fonts | 3.4% | 10.1% | 3.6% |
| 20 printed (Arial, Times New Roman) | 0.0% | 4.3% | 0.0% |

TrOCR was fine-tuned on IAM, so its own column there is a best case; the point is the last column, which keeps print exact and takes four fifths of the errors out of real handwriting. About 0.2 s a line in Node, one to two seconds in the browser. The owner chose to serve it from Forma's own site, opt-in, over a CDN, knowing a first download (about 88 MB) counts against the free hosting quota. How it is built:
- `lib/handwriting.ts` reads again the lines Tesseract read below 70 (`HANDWRITING_BELOW`), each cut from the page with a fifth of its height above and below and half at the sides, and puts back what TrOCR read as one word over the line at confidence 60, not flagged and no more than that. `recognizePage` calls it when a page reads as English with enough lines left unsure (`looksHandwritten`) and the site serves the model (`handwritingServed`), since the evening of 2026-11-04; a switch in Settings did until then. A model that will not load leaves Tesseract's reading.
- **Every file from this site.** The model is served at `/handwriting/models/` from `vendor/handwriting/`, which `npm run fetch:handwriting` fills from one pinned commit of the model repository, every file checked against its SHA-256, and git ignores; a build without it (CI's) has no model, and OCR then keeps Tesseract's reading. ONNX Runtime's glue and WebAssembly are imported as URLs of Vite's own copies: Transformers.js points the runtime at cdn.jsdelivr.net otherwise, which the production CSP blocked in the owner's Chrome, and handwriting then fell back to Tesseract with nothing on screen. No CSP change was needed: same-origin scripts, `'wasm-unsafe-eval'` and `blob:` workers were already allowed.
- `check-bundle-size.mjs` counts the 90.6 MB apart, like the OCR data, with the two model files optional since CI builds without them; onnxruntime-node and sharp, which Transformers.js brings for Node, have their install scripts denied. **Forma works out the settings and the language itself** (2026-11-04). The owner's rule: a user is not asked what the input already says. The Report configuration dialog asked for the DevExpress version, the page size, the unit, a header and footer, right to left, a stored procedure, OCR languages and handwriting. All of those choices are gone; the dialog is *Settings*, and holds the AI connection, Forma's memory, and a short *Worked out for you* list of what the last request decided and why.
- **The settings** come from `lib/autoConfig.ts`, per request, in this order: an uploaded `.repx` or the report being refined (its `SerializerVersion`, `ReportUnit`, `PaperKind`, `RightToLeft`, and a stored procedure out of the data source DevExpress keeps base64-encoded); a PDF page's size in points, or a picture's shape when it is a whole page; the words, typed or read ("on A4", "EXEC dbo.Sales", text mostly in an Arabic or Hebrew script); the version and unit learned from the last report the user brought, which are the only fields `reportConfigStore` keeps now; and last the paper of the user's region. `App.tsx` works them out before a request and again once its pages are read (`detectFor`), and every path that makes a report reads `effectiveConfig()`; batch works them out per file and keeps nothing, since three files run at once.
- **The header and footer were worse than redundant.** Their defaults went into every prompt as "Include Company Logo: No" and "Include Page Numbers: Yes", overruling the very source being reproduced. They are gone from the prompt as well as the dialog: a header and footer are reproduced from the source, or asked for in words.
- **The language of a picture** comes from `lib/ocrScript.ts`. Every page is read in English first. A confident reading is Latin script, and French, German or Spanish function words in it send the page round again with that language. An unsure one has its widest garbled lines (English below 40) probed with Arabic, Urdu and Hindi as rectangles of the page; a script that beats English by 12 on average and on two thirds of the lines wins, and the page is read again with it and English. Measured on the owner's bilingual certificate: rectangles put Arabic at 58.8 against English's 32.7, while cut-out crops scored 50.0 against 46.8, because a crop has no resolution and Tesseract guesses one per crop (269 to 789 dpi). The probe reads were 98 s while each sent the enlarged canvas; with the page encoded once at its own size they are 11 s, and the whole page reads as Arabic in about 31 s in the owner's Chrome (English 9.6, probes 11.0, Arabic 10.7). Tesseract's own script detection was not used: it needs the legacy engine and a 10 MB model on every first OCR.
- **Handwriting** is tried when a page reads as English with two lines and a quarter of them still unsure, and only where the site serves the model, which is now asked with a HEAD request that must answer JSON: a site that rewrites unknown paths to its index answers a missing file with HTML and a 200.

Four things the first run in the owner's Chrome found, on a two-page scan built from DevExpress's own PNGs of s54a and s23-gen. Each is now a rule with a test.

- **The ReportHeader band, not Detail.** The Preview repeats Detail once for each record it previews, and counted the cross-tab's rows as records, so the two-page scan printed as eight pages. A ReportHeader prints once whatever the data. `RepxProbe render` printed the same layout on either band identically: two pages, every text where it was laid out. The audit's `band-taller-than-page` now measures a band by its tallest piece between page breaks, since that is what DevExpress printed.
- **Rows must line up to be a table.** The chart's bar values, printed in columns, sat close above the cross-tab and were read as one table with it. A row now joins a table only when at least two of its texts overlap the row above's across, with at most one left over on either side. Text on a picture, such as a value on a bar, is never a cell.
- **A table's font comes from its widths.** On the cross-tab, 28 of 34 word boxes were as tall as their cells, taking in the grid lines, which read as 24.5pt for text printed at 9.75. Each cell takes the smaller of its height's and its width's estimate (`fontFromWidth`), and the table their median: 9.5pt.
- **A label is as wide as Arial prints it.** The scan's serif is narrower than the Arial the report names, and a label that does not grow clips: the Preview printed "Customer 0". A label now takes the wider of its ink and its text measured in Arial, plus a little.

The CSP gained `'wasm-unsafe-eval'` for this, and nothing else: see `securityHeaders.ts`.
**File intake is now a single path.** `handleFileChange` (picker) and `handleDrop` (drag-and-drop) both call `ingestFiles()`, which loops `ingestFile()` per file. These were two near-identical copies that had to be edited in lockstep; that duplication is gone and must not come back. (A parallel `files: File[]` state also used to exist; it was write-only — set in four places, read nowhere — and has been removed.)

Intake produces **two** outputs, deliberately kept apart:

- `previews: string[]` — image data URLs only. Everything downstream depends on this staying image-only: the thumbnail strip, `sourceRect` logo cropping, and the `images` field persisted on saved reports.
- `attachmentTexts: TextAttachment[]` — text recovered *from the files themselves*. Each entry carries the **same `uploadId` as its page images**, plus `file` and an optional `page`; display is derived from those and never stored pre-formatted.

**The text side is where `.repx` accuracy comes from.** A digital PDF already contains every string and its exact position; rasterizing and asking the model to read it back out of pixels throws that away. `extractPdfPageText()` pulls it via `page.getTextContent()` and converts it into the report's own grid — **hundredths of an inch, origin top-left** — so the model can use the numbers directly. Two conversions matter, and nothing checks either one: PDF points are 1/72" (`PT_TO_REPORT_UNITS = 100/72`, which maps a 612×792pt Letter page exactly onto the 850×1100 report grid), and PDF y is a **baseline measured from the bottom**, so `yTop = pageHeight - (baselineY + height)`. Get either wrong and every coordinate is silently off.

`MAX_TEXT_ITEMS_PER_PAGE` (400) caps extracted strings per page so a dense page cannot flood the prompt — and unlike the page cap, **this one is silent**: it `break`s out of the loop with no `uploadNotices` entry, so a very text-heavy page loses its tail with nothing surfaced to the user. If accuracy is missing from the *bottom* of a busy page, check this before blaming the model.

The prompt's **SOURCE PRECEDENCE** block tells the model this extracted text is exact and outranks the page image for strings and positions, while the image remains authoritative for borders, fills, logos and visual structure. Keep those two halves in sync.

- **Data files (2026-11-05)**: a CSV, TSV, JSON, text, SQL, Excel (`.xlsx`) or Word (`.docx`) file becomes a text attachment (`lib/dataFiles.ts`), where until then it was "not a supported type" and a report's data had to be pasted into the message as a fenced block. A table, from a CSV, a TSV, a JSON array of records or the first worksheet of a workbook, is given as **DATA SOURCE** with its columns named as the report's fields and the first `MAX_ROWS` (25) rows as CSV, the rest counted; SQL is a DATA SOURCE as written, and text or a Word document a **DOCUMENT**, the person's words, cut at 12,000 characters with a notice. Read in the browser like everything attached: `.xlsx` and `.docx` are zip archives, read by its `unzip` with the browser's own `DecompressionStream`, so no library was added. A file that cannot be read says why in the composer's notice line. It is a text attachment like a `.repx`, so with words or alone it goes to a generation. Checked in the owner's Chrome in mock mode: a CSV attached as a chip with no notice.
- **PDF**: up to `MAX_PDF_PAGES` (8) pages, each rendered at `PDF_RENDER_SCALE` (2.5, ~250 DPI) *and* text-extracted. Pages beyond the cap produce a user-visible notice rather than vanishing — page 1 used to be the silent hard limit. The canvas is **filled white before rendering** (pdf.js draws onto transparency; JPEG has no alpha, so skipping this turns the page black) and the result goes through `optimizeImageDataUrl()`, which matters now that 2.5 can exceed the edge cap. A PDF with no text layer is a scan: that is detected and reported, not treated as a failure.
- **Images**: `readAsDataUrl()` then `optimizeImageDataUrl()`, which caps the long edge at `MAX_IMAGE_EDGE` (2048) and re-encodes as JPEG. Anything already under both that cap and `REENCODE_THRESHOLD_BYTES` is untouched; it returns the original on any failure and never returns a larger payload than it was given, so it can only help. The cap is deliberately generous — lowering it trades real fidelity for speed.
- **`.repx`**: read with `file.text()` as a real string, validated with `checkRepx()` (the same check the REPX viewer uses) and attached as text. It used to be base64-relabelled `text/plain` and never decoded — 33% larger for no benefit, and impossible to validate before spending a request.

**One dropped file is one chip, and until 2026-08-26 that was only half true.** The images collapse through `groupAttachments` and always did; the text layer did not, so a three-page PDF drew one thumbnail chip *and three more* reading "invoice.pdf · page 1 text", "· page 2 text", "· page 3 text". That is the complaint the grouping exists to prevent, arriving through the door nobody had closed — the user sees the product having torn their file into pages. Text from an upload that produced images is now part of that upload's chip and is not listed again (`textGroups` filters on the `uploadId`s present in `previewMeta`); what remains in the second row is genuinely text-only — a `.repx`, or a PDF whose pages all failed to rasterise — and it is grouped by the same rule so the defect cannot re-open from that side. Verified over CDP: a 3-page PDF yields exactly one chip carrying a "3 pages" badge, and a `.repx` still yields its own.

Two consequences of the same confusion went with it, and both were worse than the chips:

- **`removeFile` dropped the images and left the text behind.** Once the text had no chip of its own that was unobservable — a PDF the user had visibly taken back was still being sent to the model, with nothing on screen left to remove it with. It now takes the `uploadId` and clears both lists. (The natural check is the good one: remove the chip and the text row must not appear, since with the images gone nothing would suppress it any more.)
- **`MAX_ATTACHMENTS` (12) counted rows, not files.** An 8-page PDF spent 8 image slots plus up to 8 text slots, so a single upload could overrun a cap the notice describes in files — "you can attach up to 12 items", said to someone who attached one. `stagedUploads` counts distinct `uploadId`s instead. Five 3-page PDFs (15 images + 15 texts) now stage without a notice, which is the case that used to fail at the second one.

Unsupported files, oversized files (`MAX_FILE_BYTES`), and the `MAX_ATTACHMENTS` cap all surface through `uploadNotices`. Dropping a `.docx` previously matched no branch and did nothing at all, with no feedback.

**Attachments are not always images.** `analyzeReportDesign` takes `AttachmentPart[]` — a union of `{inlineData}` and `{text}` — and text parts are ordered **first** so exact strings are in context before the page images. Anything that reasons over attachment counts must consider both lists: `handleGenerate`'s chat-vs-report routing, its empty guard, and the send button all check `previews.length === 0 && attachmentTexts.length === 0`. A `.repx`-only upload has no images at all, and checking `previews` alone would wrongly route it to chat.

pdf.js is wired at module scope with a Vite-specific import — `import pdfWorker from 'pdfjs-dist/build/pdf.worker.mjs?url'` assigned to `pdfjs.GlobalWorkerOptions.workerSrc`. The `?url` suffix is what keeps the worker out of the main bundle; swapping it for a CDN string or a bare import breaks PDF intake at runtime, not at build time.

`previews` are split back into `{inlineData: {data, mimeType}}` parts at request time inside both `handleGenerate` and `handleResume` — duplicated again, once for the initial run and once for resume.

**Export** goes through `downloadDesign`: it prefers `result.repxContent` (Blob as `application/xml`, filename `<title>.repx`) and silently degrades to `result.content` as `.txt` when the model returned no XML. The `.repx` filename is the report title with whitespace collapsed to underscores.

**Progress is real once output starts; cancellation is real throughout.** The request is streamed — `analyzeReportDesign` calls `ai.models.generateContentStream` and accumulates chunks, taking an optional 6th argument `onProgress` that fires (throttled to ~120ms) with `{chars, percent, elapsedMs}`. The response is a single schema-constrained JSON object, so it still cannot be *parsed* until the last chunk lands; what streaming buys is a progress bar driven by output actually received rather than a timer inventing percentages. `percent` is asymptotic (`1 - e^(-chars/EXPECTED_RESPONSE_CHARS)`) and deliberately caps at 95 — only the parsed result reaches 100, so the bar can never claim completion early. `EXPECTED_RESPONSE_CHARS` only shapes the curve; being wrong makes the bar move faster or slower, never wrong.

**The reduced-motion handling is the load-bearing part, and it is not the obvious one.** `workspace.css` ends with a blanket `.wb-root * { animation: none !important }`, so every keyframe in that card — including the spinner it replaced — is dead for anyone with the preference set, which on **Windows Server is the default**, i.e. the machine this is developed on. The design is therefore built so nothing important is carried by motion: the arc advances because output arrived rather than because a keyframe looped, so under the preference it snaps to each new value instead of easing, and still moves. One exception is re-enabled by name in that block: a slow opacity breathe on a blurred disc behind the mark, chosen because it changes luminance and nothing else — no translation, rotation or scale — and because a card that can sit for two minutes with an honestly-pinned ring is otherwise indistinguishable from a crash. The orbit is *not* exempted: it rotates, and it means nothing. Verified over CDP by reading `animationName`/`animationPlayState` under both media values — `no-preference` gives breathe + orbit running and a 0.25s arc transition, `reduce` gives breathe running, orbit `off`, transition `0s`.

The card's geometry is set by the review panel, not the window: at its 340px default the first attempt wrapped the heading and cut the stage sentence to "Extracting layout…". The sentence now spans the controls' column and is clamped to two lines at a **fixed** height, so the card cannot change size as the stage text changes and jog the transcript beneath it. Measure any change to it at 340px.

`App.tsx` still starts the old 2.5s `setInterval` because model detection and the upload genuinely produce no signal. `handleStreamProgress` **clears that interval on its first call** and takes over — both handlers share the one callback so they cannot drift.

**The bar can never go backwards, and two mechanisms are what guarantee it.** `PRE_STREAM_CEILING` (14) clamps everything the simulated interval may claim, so the pre-stream phase cannot outrun what the stream will report on its first real chunk — without it the interval could sit at 30% while the first chunk honestly said 6%, and the bar would visibly retreat. `Math.max` against the previous value is the second half: a lower percent is discarded rather than rendered. `handleStreamProgress` then floors the stream at `PRE_STREAM_CEILING + 1` so the handover is always a step forward. Both are shared by `handleGenerate` and `handleResume` for the same anti-drift reason as the callback itself. If you add any new progress writer, route it through `src/lib/generationProgress.ts` — calling `setProgress` with a bare object is the bug.

**All of the above moved out of `App.tsx` and this paragraph did not follow it for a while, so mind the names.** The rules now live in [`src/lib/generationProgress.ts`](../../src/lib/generationProgress.ts) under test (22 cases), and the state is a single `GenerationProgress` object rather than a loose percent. The mapping from the old names, which no longer exist anywhere in the source: `advanceProgress` → the `Math.max(state.percent, …)` inside `tickSimulated` and `applyStreamProgress`; `setAnalyzingProgress` → `setProgress`; `analyzingProgress` → `progress`. `PRE_STREAM_CEILING` survived the move unchanged and is exported from that module. What is left in `App.tsx` is wiring: stop the interval, fold the chunk in — its own doc comment above `handleStreamProgress` says so. The `finally` blocks and `handlePause`/`handleStop` all null-check `loadingIntervalRef.current`, which is required now that the stream nulls it mid-flight. Pause and stop abort a per-run `AbortController` whose `signal` is threaded into `analyzeReportDesign` as the 5th argument and handed to the SDK via `config.abortSignal`, tearing down the in-flight fetch. Two consequences worth knowing: the SDK's abort is **client-side only**, so Google may still finish and bill for the generation; and a cancelled call rejects with a `DOMException` named `AbortError` that `geminiService.ts` deliberately rethrows unwrapped, so callers can distinguish cancellation from a real model error. Both `handleGenerate` and `handleResume` guard on `signal.aborted` in their `catch` and `finally` blocks — pause leaves `isAnalyzing` true so the resume path can re-issue the request, while `handleStop` resets the workspace itself.

**The REPX audit is a count in the status bar, and it blocks nothing.** [`src/lib/repxAudit.ts`](../../src/lib/repxAudit.ts) asks what is still wrong with a report *after* every repair pass has run, and it exists because on 2026-09-04 three defects reached the user while the app reported success: the tables were discarded on load, the page numbering was dropped, and the report had no Detail band. By its own lights it had succeeded — the XML parsed, the mockup drew, the spec read well. **Do not restate the checks here.** Why each one exists is that file's own doc comment, and how each was measured against DevExpress is in [`gemini.md`](gemini.md), where the measurement sections keep ending "`repxAudit.ts` gained two checks from this". This paragraph owns only the part neither of them covers: where it runs, and what the user is shown.

**It runs in three places, and only one of them is visible.** `geminiService.ts` calls it last on the finished artifact and writes the result to the **console** — `console.error` / `warn` / `log` by severity, then every finding as `[code] message`. `App.tsx`'s `runOneBatchFile` calls it per batch file so a row can carry its own `errors`/`warnings` counts, which is the point of running forty files: knowing which of the forty are worth opening. And a `useMemo` over `result.repxContent` and `result.layout` produces the one the user sees.

**Since 2026-11-04 it is a box in the REPX pane, not a count in a bar**: `N REPX warnings` with every finding listed under it (`data-audit` in `RepxViewer`), silent when clean, the status bar having gone (see *The workspace is as clean as a chat app*). The same day `App.tsx` stopped importing it eagerly: the pane's box, the batch run and the description repair loop each load `lib/repxAudit.ts` when they need it, which took 32,264 bytes off the entry chunk every visitor downloads. Until the module arrives the box shows nothing, as for a clean report. The record of the bar follows. **What the user sees is a count and nothing else.** One `<span>` in the workspace status bar, beside the bound-fields readout, **silent when the audit is clean** — which is the common case, and the reason it can sit in a bar rather than in a panel. `wb-bad` if there is any error, `wb-warn` otherwise, reading "2 REPX errors, 1 REPX warning". The full text of every finding is in the `title` tooltip and in the console; the bar has room for a number. Findings carry a stable `code` precisely so a future caller can filter on it without matching prose, and nothing does that yet.

**Nothing is gated on it, and that is deliberate rather than unfinished.** A warning means the file opens and is a worse report than it should be, which is the user's call to make — they asked for a report and got one. An error means a repair *declined*, which is worth knowing and still not worth withholding the file over. If you are tempted to block export on `audit.errors`, the argument against is in the file's *Errors versus warnings* comment; the argument for would have to be a new one.

**The `layout` argument is what makes the vaguest finding the most specific**, and it is the reason the audit takes two artifacts instead of one. "There is no Detail band" is true of a certificate, where it is correct. "The mockup drew a 12-row grid and there is no Detail band" is a defect. The two artifacts come out of one response and describe one document, so where they disagree one of them is wrong — and that is checkable in a way neither is alone. It is also why the band-count mismatch is worth reporting at all: the band count shown in the UI comes from the `layout`, while the file the user exports is the REPX. The argument is optional, because a report loaded from an old save may not have one and the structural checks are worth running either way.
