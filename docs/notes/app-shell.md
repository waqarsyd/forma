# The app shell

Split out of `CLAUDE.md` on 2026-08-13. The text is unchanged from when it lived there, apart from heading levels. It is incident history — the reason a thing is the way it is, which the code cannot tell you. **Nothing here is loaded automatically**: `CLAUDE.md` routes to this file, and reading its one-line summary of this area is not a substitute for opening it before you change that area.

## `src/App.tsx` is the whole app

It is several thousand lines (a figure that only ever grows — don't trust a number written here, and don't reintroduce one into this heading where it will silently rot). It holds the workspace, chat and config modal, plus two components still defined inline: `RepxViewer` (the XML pane, whose pure helpers were extracted to `src/lib/repx.ts` — see below) and `ReportMockup` (renders `layout` as absolutely-positioned divs).

**All five page-level surfaces now live in `src/components/`**: `LandingPage`, `FeaturesPage`, `DocsPage`, `ContactPage` and `LoginPage`, alongside `MobileNav`, `UserAvatar` and `Logo`. `src/components/landing/` is **the marketing design system, not the home page's private folder** — the name is historical. Two tiers live there: `sections.tsx` (the reveal wrappers, `SectionHead`, `Eyebrow`, `Stat` and the `H2`/`LEDE`/`BODY` type scale), `icons.tsx` and `SheetRuler` are shared furniture — `LandingPage` and `FeaturesPage` both build on them and `SiteHeader` pulls `IconSun`/`IconMoon` from `icons.tsx`; while `HeroScanner` (the scan → detect → type sequence), `VaultFigure` and `StepFigures` really are home-page-only figures. Build a new marketing surface out of the first tier rather than restating its markup, and add new icons to `icons.tsx` rather than starting a second set. (This bullet used to read "landing-page-specific by design; nothing else imports them", which was already untrue of `icons.tsx` and stopped being true of the rest when the Features page was rebuilt on 2026-08-11.) The four marketing pages take the same props — `onEnterWorkspace`, `onSignIn`, `onSignUp`, `user`, `logOut`, `isDarkMode`, `setIsDarkMode` — and pass them straight through to the shared chrome. `LandingPage` was extracted on 2026-08-09; it had been inline while its three siblings were not, which is why header fixes kept having to be applied to it separately. Note that pulling it out orphaned `MobileNav`'s import in `App.tsx`, since the landing page was its only consumer there — the unused sweep catches that class of leftover.

**`DocsPage`, `ContactPage` and `LoginPage` were rebuilt on 2026-08-11, and each rewrite corrected something that had stopped being true.** The visual work is the smaller half; do not reintroduce any of these:

- **Docs** told readers Forma "operates using a shared developers API key" and that their own key was "stored securely within your browser's local state (`localStorage`)". The app owns no key, and that `localStorage` entry is *purged on boot* — describing plaintext on disk as secure was the worst line in the repo. It also put `overflow-hidden` on `<main>` while the sidebar used `sticky`; **an overflow ancestor silently disables sticky**, so the docs nav scrolled away. Nothing above that `<aside>` may set overflow.
- **Contact** displayed `support@forma.com` over a `mailto:` pointing somewhere else, linked Github/Discord/LinkedIn all at `/`, and — the serious one — its `catch` block set the success state, so a failed send told the sender "we've received your message" while dropping it. A rejected request must reach the failure state; there is no path from `catch` to `sent`. The address is now assembled from two halves at click time and never appears in the markup, and the form carries an off-canvas honeypot.
- **Login** kept its logic (that part was already careful) and lost its surface: a blurred ring pulsing behind the submit button on an endless loop, a "Verified Stack" badge asserting a guarantee nobody made, Privacy/Terms pointing at `/`, and two `rounded-xl` buttons — the only place in the app that broke the everything-is-a-pill rule.

Placeholder links are tagged **`data-needs-url`**; `grep data-needs-url src/` lists every one still waiting for a real destination. Do not "fix" them by inventing a URL. Contact and Login carry theirs in their own markup, but `SiteFooter` adds the attribute **programmatically** to any link whose `href` is a bare `#` — the maker column's placeholders were invisible to that grep until it did, which is worse than not having the convention at all. A footer column therefore needs no hand-tagging; anything else does.

**`SiteHeader` and `SiteFooter` are the single copy of the marketing chrome, and hand-editing a page's own header is how the last drift happened.** The same markup used to be pasted into all four pages; when the home page was rebuilt against the approved design the other three kept a 16px-taller bar, no backdrop blur, a 120px single-row footer instead of the four-column one, and `--secondary` (`#a04100`, a dark brown) as their accent instead of the sheet's `#fe6b00`. They now render `<SiteHeader active="…" />` and `<SiteFooter />`, so there is one copy to change. `SiteHeader` owns the profile-menu state and its click-outside handler — extracting it orphaned a `showProfileMenu` / `profileMenuRef` pair plus four imports in each of the three pages, which the unused sweep found.

`SiteFooter` takes **two** optional column lists, and each one also picks the grid ratio. `onThisPage` is the home page's five section anchors; `maker` is the contact page's maintainer profile links. `maker` → `1.6fr_1fr_1fr_1fr`, `onThisPage` → `1.7fr_1fr_1fr_1fr`, neither → three columns at `1.7fr_1fr_1fr`. Both ratios come from the approved designs for those two pages, so they are measured values rather than taste. A page that passes neither still gets exactly the three-column footer it had before, because a page with no anchorable sections should not render an empty heading. Everything else in the footer — the brand block, Product, Elsewhere and the sign-off — is the same everywhere.

**The tagline and the descriptor are different lines with different jobs, and the descriptor is duplicated into `index.html` by hand.** The *tagline* is "Show it. Build it. Ship it." — the hero `<h1>` in `LandingPage.tsx` and, in mono at `0.2em` tracking, the `SiteHeader` lockup. It works there because the hero lede sits directly underneath to explain what "show it" means. It does **not** work in a search result or a link preview, which have no lede, so the *descriptor* carries those: `<title>Forma — Screenshot to DevExpress .repx</title>` plus `description` / `og:*` / `twitter:*` in `index.html`. **The three description tags in `index.html` (`description`, `og:description`, `twitter:description`) are byte-identical to each other, and all three are a condensed form of the hero lede in `LandingPage.tsx`. Two further restatements live outside the app entirely: `description` in `package.json` — which is what npm and a GitHub repo page render — and the opening line of `README.md`. That is six places making one claim in three different lengths, so change them together.** The lede is the longer original ("a photo, a PDF, or an existing `.repx` … Three artifacts, one request."); the tags trim it to fit the ~155 characters Google renders. (Before this existed the title was a bare `Forma`, there was no description tag at all, and a pasted link rendered as a naked URL.) Three details are deliberate:

- **`og:image` is root-relative (`/logo.png`), not absolute.** Open Graph asks for absolute, but the only host value this project has is `APP_URL` in `.env`, which is **not** `VITE_`-prefixed and therefore never reaches the client — `envPrefix` allowlists `VITE_*` only, for the reasons in *The Gemini call runs in the browser*. A literal host would be wrong on every other deployment, and Vite's `%VITE_*%` HTML replacement leaves the placeholder **text** in the output when the variable is unset, shipping a visibly broken URL. Root-relative resolves against the page origin in Slack, Facebook, X and LinkedIn, and degrades to no preview image rather than a wrong one. Do not "fix" it by hardcoding a domain.
- **The preview image is `public/og-card.png`, a purpose-built 1200×630 card, and it is generated rather than drawn.** `twitter:card` is `summary_large_image` because there is now an asset with the right aspect ratio to fill it (it was `summary` while the only image was the 256×256 square mark, which the large layouts letterboxed). `og:image:width` / `:height` are declared so a scraper can lay the card out before the download finishes, and both `og:image:alt` and `twitter:image:alt` carry the same sentence.

  The source is **`assets/source/og-card.html`** — outside `public/` for the same reason as the full-resolution logo PNGs, since anything in `public/` is copied verbatim into `dist/` and the generator is not something to ship. Regenerate with one command, no script and no dependencies:

  ```powershell
  & "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe" --headless --disable-gpu --hide-scrollbars --force-device-scale-factor=1 --window-size=1200,630 --virtual-time-budget=8000 --user-data-dir="$env:TEMP\edgeshot" --screenshot="$PWD\public\og-card.png" "file:///$($PWD -replace '\\','/')/assets/source/og-card.html"
  ```

  **It must be `--headless`, not `--headless=new`** — the new headless mode ignores `--screenshot` and exits successfully having written nothing, so the old file silently survives and looks like a successful regeneration. (Verified equivalent: this one-liner and a CDP `Page.captureScreenshot` with an explicit 1200×630 clip produce **byte-identical** output, same SHA-256.)

  **Two things fail silently and yield a plausible-looking wrong card, so look at the result rather than trusting the exit code.** The card pulls Hanken Grotesk and JetBrains Mono from Google Fonts; with no network the wordmark and headline render in the fallback sans and the card is off-brand while still looking deliberate. And the logo is referenced as a `file://` sibling (`../../public/logo.png`), so a move or rename gives a blank square, not an error. The card's palette values are **literals copied from the `.landing` block** in `src/index.css`, because it renders outside the app with no access to the tokens — if the sheet's accent or ink changes there, change them here too.
- **The title is per-route, and `ROUTE_TITLES['/']` must stay byte-identical to the `<title>` in `index.html`.** `ROUTE_TITLES` is a module-scope map in `App.tsx` and `applyRoute` assigns `document.title` from it — one writer, at the single point every route change already passes through (boot, `navigate()`, and back/forward), so no second writer can disagree about the same tab. `index.html` still carries the `/` title because scrapers do not run this code and because it is what paints before the bundle loads; a difference between the two would rewrite the title a moment after first paint for nothing. **Change one, change both** — the same duplication rule as the theme bootstrap. Page name leads and the brand trails (`Docs — Forma`), because tab strips truncate the end. An unrecognised path falls back to `/`, matching what the route effect's `default` branch renders. `src/lib/router.ts` is deliberately still title-free: it holds routing mechanics, not copy.

**All four marketing pages carry the `landing` class on their root**, not just the home page. It is what supplies the design's palette and the 1180px measure; without it a page falls back to the app's tokens and to `--spacing-container-max: 1440px`, and its header and footer then run wider than its own content. `DocsPage` and `FeaturesPage` also had `max-w-6xl`/`max-w-7xl` with `px-6` on their inner containers, which sat ~6px off the shared measure — those now use `max-w-container-max` / `px-margin-desktop` like everything else.

Expect to work inside `App.tsx` for workspace features; prefer extracting new surfaces into `src/components/` rather than growing it.

**The in-app `DebugConsole` was removed on 2026-08-09, and bringing it back would reintroduce a real hazard.** It was a log viewer that captured output by **monkey-patching `console.log/error/warn/debug` at boot**, and that patch was the direct cause of two bugs: `JSON.stringify` on a cyclic argument threw *at the caller's `console.log` line* rather than inside the panel, and writing to React state synchronously from inside the patched console produced "Cannot update a component while rendering a different component" whenever any library logged during render. Browser DevTools does the same job without owning the global console — `console.log` is native again, confirmed by checking `/native code/` against `String(console.log)`.

Removed with it: the `DebugLog` type, the `logs`/`isDebugOpen` state, `MAX_DEBUG_LOGS`, the patching effect, the menu entry, and the `handleRunDiagnostics`/`handleCheckSystemHealth` actions. **Nothing was lost from the telemetry**: the timing breakdown, token usage and model resolution all go through plain `console.log` in `geminiService.ts` and remain fully visible in DevTools. `elapsedTime` is unrelated and stays — it is real wall-clock around the request, shown on the progress card.

**Finding unused code:** there is no ESLint, and `tsconfig.json` enables neither `noUnusedLocals` nor `noUnusedParameters`, so dead code accumulates silently and `npm run lint` will not tell you. Run `npx tsc --noEmit --noUnusedLocals --noUnusedParameters` to see it without editing the config. As of 2026-08-09 that sweep is **completely clean**, so treat *any* hit as newly introduced. (It previously reported two, both in `FeaturesPage.tsx`. `heroInView` marked a visibility gate that was never wired; the looping hero animation it was meant to gate had since been reduced to static dots, so there was nothing left to gate and it went. The unused `idx` map parameter went with it. The gate that was actually missing is now on the bento grid's scanning laser — see `bentoInView`.)

**The workspace was rebuilt on 2026-08-12 by porting an approved artifact, and `src/workspace.css` is that port.** The brief was explicit — replicate the design pixel-for-pixel, treat the artifact as the single source of truth, do not adapt it "for consistency with the rest of the app" — so the file is arranged to keep that promise checkable rather than merely claimed:

- **The bulk of it is a verbatim block**, produced by a selector-only transform: every class gained a `wb-` prefix, and the artifact's own token, reset and `body` rules were dropped because `.sheet` and Tailwind's preflight already supply them. Every *declaration* inside it is byte-identical to the published artifact. **Do not hand-tune a value there.** Changes belong in the PREFLIGHT COMPENSATION block at the top, where they stay visible as deviations.
- **That top block is the complete list of intentional differences**, each with a comment recording what broke without it. Two matter most. Tailwind's preflight sets `line-height: inherit` on form elements, which made every pill 3px taller than the artifact's (measured 33 against 30), so `.wb-root button, input, select, textarea { line-height: normal }` puts it back. And the artifact's `.wb-shell` used `min-height: 100vh` with implicit rows, so nothing bounded the panes — `.wb-thread`, `.wb-list` and `.wb-bench-body` all declare `overflow: auto`, which needs a bounded height to do anything. That was invisible in a page whose content was fixed and happened to fill the viewport; with real content it failed in both directions, leaving a 283px dead band under the status bar when empty and pushing the bar off-screen when full. `height: 100vh` plus `grid-template-rows: minmax(0, 1fr) auto`, with `min-height: 0` on the three columns, is the fix.
- **Reduced motion is scoped to `.wb-root`.** The artifact's own rule was a global `* { transition: none !important; animation: none !important }` — harmless in a standalone page, app-wide poison in an imported stylesheet. Headless Chromium reports `prefers-reduced-motion: reduce`, so importing the file silently changed the rendering of `/docs`. **Nothing in this file may select outside `.wb-root`**, and that includes anything you add.

**The shell is a three-column grid with no top header at all** — `56px` rail, `340px` review column, `minmax(0, 1fr)` bench, and the status bar spanning `grid-column: 1 / -1` beneath all three. It replaced a header-plus-drawer arrangement, which retires several rules recorded here earlier: there is no `h-[68px]` bar to keep matched with `SiteHeader`, no `md:w-80 lg:w-96` chat pane (the column is a fixed 340px), and no `CanvasStatusBar` component — the bar is markup in the shell, rendered once, which was the whole point of consolidating the two copies that used to sit inside each branch. **`mobilePane` is gone as well**, with the forced flip to `canvas` on a finished result: the artifact carries no mobile tab arrangement, and inventing one would not have been a port. `.dot-grid` stays deleted, but the workspace no longer uses `.sheet-grid` either — the artifact draws its own ground.

**The rail is the whole navigation.** `railPanel: 'review' | 'projects' | 'history'` chooses what the second column shows, and `aria-current="true"` paints the selected target. That is also why the signed-out account slot is a plain rail button and not the accent disc: the disc is simultaneously the avatar treatment *and* the selected-section treatment, so using it for "not signed in" made an empty workspace look logged in and asked for a sign-out. The mark at the top is an `<a href="/">`, matching `SiteHeader` on all five marketing pages — the artifact drew a plain `<img>`, which left the workspace with no route back to the site.

**The three result views are derived, not stored.** The artifact has a single `plate: 'proof' | 'spec' | 'xml'` switcher where the app has two independent state variables, and the port kept the app's state rather than the artifact's shape:

```ts
const plate = activeTab === 'ui' ? 'proof' : specView === 'repx' ? 'xml' : 'spec';
```

`showPlate()` writes back to whichever of `activeTab` / `specView` the target implies. Deriving instead of adding a third variable is what stops the switcher and the pane disagreeing.

**Known, and deliberately not fixed here:** `.wb-kicker` sits at 3.02:1 in light and 3.75:1 in dark, under AA's 4.5:1. It resolves to `--ink-faint`, which is app-wide and predates the port, so raising it in this file alone would put the workspace out of step with the five marketing pages over a problem all six share.

**`SheetRuler` cannot be reused in the workspace, and this is why.** It is `fixed inset-y-0 left-0` and driven by `window.scroll` plus `document.body.scrollHeight`. The workspace is a `height: 100vh` frame whose scrolling happens *inside* panes, so the component would pin to the viewport's left edge — over the rail, not the bench — with a marker that never moves because the window never scrolls. A static decorative copy was considered and rejected: the marketing ruler earns its place by actually reading out scroll position in report units, and a fake one on a surface whose sheet is drawn at a computed `scale` would imply a measurement it cannot make.

**`ReportMockup` is a scaled pixel sheet, not a responsive layout.** Every coordinate from `layout` is multiplied by `0.96` and set as an absolute `left/top/width/height`; the page cannot reflow, so a `ResizeObserver` measures the viewport and applies `transform: scale()` to the whole sheet, with an outer stage div sized to the post-scale footprint so nothing overlaps. Everything inside the sheet is drawn against the **theme-invariant `--paper` / `--on-paper` / `--paper-accent` / `--paper-accent-soft` tokens** — all four deliberately identical in `:root` and `.dark`, since a rendered report must look the same in both themes. Using `bg-card`/`text-foreground` or any other flipping token inside the sheet is a bug, not a shortcut. That was not hypothetical: the chart bars used `bg-primary/40` and the gauge arc `border-t-primary`, and `--primary` **does** flip (`#FF5E00` → `#FF6C1A`), so a generated report quietly changed colour with the app theme. `--paper-accent` exists so there is a correct token to reach for instead of a literal.

**Do not wrap `ReportMockup` in a frame — it draws its own.** Border, radius, shadow, max-width and the grey inset around the page are all inside the component. The canvas used to wrap it in a second panel with its own border, shadow, rounding and `bg-paper`, which stacked white-then-grey-then-white with two borders and two shadows. The call site is now just `<ReportMockup … />` inside the scrolling canvas.

**Routing is real paths** — `/features`, `/docs`, `/contact`, `/login`, `/signup`, `/workspace`, and `/` for the landing page. It was `window.location.hash` until 2026-08-09, which showed a `#` in the address bar on every page and a bare `/#` on the home page.

`src/lib/router.ts` is the whole implementation and there is still no router library: `currentPath()`, `navigate()`, and `onRouteChange()` over ~40 lines. Three things about it are load-bearing:

- **`pushState` fires no event.** Only the back/forward buttons emit `popstate`, so `navigate()` dispatches a custom `forma:routechange`; `onRouteChange` subscribes to both. Calling `history.pushState` directly instead of `navigate()` will move the URL without re-rendering.
- **Deep links depend on the server.** Vite runs with `appType: "spa"` in development and `server.ts` has an `app.get('*')` fallback in production, so `/features` returns index.html. On a host without that fallback, every deep link 404s — which is the reason hash routing existed in the first place.
- **Links are plain `<a href="/...">`.** One delegated click handler in `App.tsx` intercepts them, so anchors stay right-clickable and middle-clickable. Modified clicks, `target="_blank"` and downloads are left to the browser.

`migrateLegacyHashUrl()` rewrites an old `#features` bookmark to `/features` via `replaceState` (no extra history entry), strips a bare trailing `#`, and drops unknown fragments. It runs at boot *and* on `hashchange`, because a legacy link followed from inside the app is a same-document change that never remounts. Note a bare `#` reports `location.hash === ''`, so that case has to be read off `href`.

Any new page needs a branch in the route effect *and* a `setLastViewPath` update if it should be restorable after login.

Two pieces of view state shape the result pane: `activeTab: 'spec' | 'ui'` switches between the markdown spec and the `ReportMockup`, and `specView: 'spec' | 'repx'` chooses between the markdown write-up and `RepxViewer` inside the spec tab — that tab was named "Specs & REPX" from the start but rendered only the markdown until the viewer was added. Both are still the storage; the rebuilt workspace presents them through the derived `plate` described above, so read that before adding a third.

`RepxViewer` is dependency-free, and its three pure helpers now live in **`src/lib/repx.ts`** (moved out of `App.tsx` so they could be unit-tested without importing the app, pdf.js and Firebase into a test run — `src/lib/repx.test.ts` covers them): `formatXml()` re-indents (safe here only because DevExpress REPX is attribute-based with no meaningful text nodes — do not reuse it for general XML), `tokenizeXml()` returns **tokens rather than an HTML string** so the XML renders as React text nodes and can never be injected as markup, and `checkRepx()` runs a `DOMParser` pass asserting the document parses, that the root is `XtraReportsLayoutSerializer`, and that `<Bands>` exists. That check is the only thing standing between a malformed generation and the user discovering it when DevExpress refuses the file. `copyText()` stays in `App.tsx` (it touches the DOM directly) and falls back to a hidden textarea plus `execCommand` because `navigator.clipboard` is undefined outside a secure context — the same LAN-over-HTTP case that `isVaultAvailable()` guards.

**The REPX pane is dark in *both* themes**, on `--code-bg` / `--code-rule` / `--code-ink` / `--code-ink-faint`, matching the code blocks on the docs and features pages. It used to be white in light mode with a hardcoded `dark:bg-[#0d1117]` twin. The consequence is that **nothing inside that pane may use a token that flips**: `XML_TOKEN_CLASS` therefore carries the former dark-mode syntax colours *unconditionally* (no `dark:` variants), and the line-number gutter and row hover are fixed values. Adding a `dark:` variant back would light the text up against a background that never lightened.

**File intake is now a single path.** `handleFileChange` (picker) and `handleDrop` (drag-and-drop) both call `ingestFiles()`, which loops `ingestFile()` per file. These were two near-identical copies that had to be edited in lockstep; that duplication is gone and must not come back. (A parallel `files: File[]` state also used to exist; it was write-only — set in four places, read nowhere — and has been removed.)

Intake produces **two** outputs, deliberately kept apart:

- `previews: string[]` — image data URLs only. Everything downstream depends on this staying image-only: the thumbnail strip, `sourceRect` logo cropping, and the `images` field persisted on saved reports.
- `attachmentTexts: TextAttachment[]` — text recovered *from the files themselves*.

**The text side is where `.repx` accuracy comes from.** A digital PDF already contains every string and its exact position; rasterizing and asking the model to read it back out of pixels throws that away. `extractPdfPageText()` pulls it via `page.getTextContent()` and converts it into the report's own grid — **hundredths of an inch, origin top-left** — so the model can use the numbers directly. Two conversions matter, and nothing checks either one: PDF points are 1/72" (`PT_TO_REPORT_UNITS = 100/72`, which maps a 612×792pt Letter page exactly onto the 850×1100 report grid), and PDF y is a **baseline measured from the bottom**, so `yTop = pageHeight - (baselineY + height)`. Get either wrong and every coordinate is silently off.

`MAX_TEXT_ITEMS_PER_PAGE` (400) caps extracted strings per page so a dense page cannot flood the prompt — and unlike the page cap, **this one is silent**: it `break`s out of the loop with no `uploadNotices` entry, so a very text-heavy page loses its tail with nothing surfaced to the user. If accuracy is missing from the *bottom* of a busy page, check this before blaming the model.

The prompt's **SOURCE PRECEDENCE** block tells the model this extracted text is exact and outranks the page image for strings and positions, while the image remains authoritative for borders, fills, logos and visual structure. Keep those two halves in sync.

- **PDF**: up to `MAX_PDF_PAGES` (8) pages, each rendered at `PDF_RENDER_SCALE` (2.5, ~250 DPI) *and* text-extracted. Pages beyond the cap produce a user-visible notice rather than vanishing — page 1 used to be the silent hard limit. The canvas is **filled white before rendering** (pdf.js draws onto transparency; JPEG has no alpha, so skipping this turns the page black) and the result goes through `optimizeImageDataUrl()`, which matters now that 2.5 can exceed the edge cap. A PDF with no text layer is a scan: that is detected and reported, not treated as a failure.
- **Images**: `readAsDataUrl()` then `optimizeImageDataUrl()`, which caps the long edge at `MAX_IMAGE_EDGE` (2048) and re-encodes as JPEG. Anything already under both that cap and `REENCODE_THRESHOLD_BYTES` is untouched; it returns the original on any failure and never returns a larger payload than it was given, so it can only help. The cap is deliberately generous — lowering it trades real fidelity for speed.
- **`.repx`**: read with `file.text()` as a real string, validated with `checkRepx()` (the same check the REPX viewer uses) and attached as text. It used to be base64-relabelled `text/plain` and never decoded — 33% larger for no benefit, and impossible to validate before spending a request.

Unsupported files, oversized files (`MAX_FILE_BYTES`), and the `MAX_ATTACHMENTS` cap all surface through `uploadNotices`. Dropping a `.docx` previously matched no branch and did nothing at all, with no feedback.

**Attachments are not always images.** `analyzeReportDesign` takes `AttachmentPart[]` — a union of `{inlineData}` and `{text}` — and text parts are ordered **first** so exact strings are in context before the page images. Anything that reasons over attachment counts must consider both lists: `handleGenerate`'s chat-vs-report routing, its empty guard, and the send button all check `previews.length === 0 && attachmentTexts.length === 0`. A `.repx`-only upload has no images at all, and checking `previews` alone would wrongly route it to chat.

pdf.js is wired at module scope with a Vite-specific import — `import pdfWorker from 'pdfjs-dist/build/pdf.worker.mjs?url'` assigned to `pdfjs.GlobalWorkerOptions.workerSrc`. The `?url` suffix is what keeps the worker out of the main bundle; swapping it for a CDN string or a bare import breaks PDF intake at runtime, not at build time.

`previews` are split back into `{inlineData: {data, mimeType}}` parts at request time inside both `handleGenerate` and `handleResume` — duplicated again, once for the initial run and once for resume.

**Export** goes through `downloadDesign`: it prefers `result.repxContent` (Blob as `application/xml`, filename `<title>.repx`) and silently degrades to `result.content` as `.txt` when the model returned no XML. The `.repx` filename is the report title with whitespace collapsed to underscores.

**Progress is real once output starts; cancellation is real throughout.** The request is streamed — `analyzeReportDesign` calls `ai.models.generateContentStream` and accumulates chunks, taking an optional 6th argument `onProgress` that fires (throttled to ~120ms) with `{chars, percent, elapsedMs}`. The response is a single schema-constrained JSON object, so it still cannot be *parsed* until the last chunk lands; what streaming buys is a progress bar driven by output actually received rather than a timer inventing percentages. `percent` is asymptotic (`1 - e^(-chars/EXPECTED_RESPONSE_CHARS)`) and deliberately caps at 95 — only the parsed result reaches 100, so the bar can never claim completion early. `EXPECTED_RESPONSE_CHARS` only shapes the curve; being wrong makes the bar move faster or slower, never wrong.

`App.tsx` still starts the old 2.5s `setInterval` because model detection and the upload genuinely produce no signal. `handleStreamProgress` **clears that interval on its first call** and takes over — both handlers share the one callback so they cannot drift.

**The bar can never go backwards, and two mechanisms are what guarantee it.** `PRE_STREAM_CEILING` (14) clamps everything the simulated interval may claim, so the pre-stream phase cannot outrun what the stream will report on its first real chunk — without it the interval could sit at 30% while the first chunk honestly said 6%, and the bar would visibly retreat. `advanceProgress` is the second half: it is the *only* way `analyzingProgress` is written, and it takes `next > prev ? next : prev`, so a lower value is discarded rather than rendered. `handleStreamProgress` then floors the stream at `PRE_STREAM_CEILING + 1` so the handover is always a step forward. Both are shared by `handleGenerate` and `handleResume` for the same anti-drift reason as the callback itself. If you add any new progress writer, route it through `advanceProgress` — `setAnalyzingProgress` directly is the bug. The `finally` blocks and `handlePause`/`handleStop` all null-check `loadingIntervalRef.current`, which is required now that the stream nulls it mid-flight. Pause and stop abort a per-run `AbortController` whose `signal` is threaded into `analyzeReportDesign` as the 5th argument and handed to the SDK via `config.abortSignal`, tearing down the in-flight fetch. Two consequences worth knowing: the SDK's abort is **client-side only**, so Google may still finish and bill for the generation; and a cancelled call rejects with a `DOMException` named `AbortError` that `geminiService.ts` deliberately rethrows unwrapped, so callers can distinguish cancellation from a real model error. Both `handleGenerate` and `handleResume` guard on `signal.aborted` in their `catch` and `finally` blocks — pause leaves `isAnalyzing` true so the resume path can re-issue the request, while `handleStop` resets the workspace itself.
