# Forma's MCP server

Written on 2026-11-24, when the server's first phase was done: a stdio server in `src/mcp` and six tools, none of which calls an AI. Its second phase came the same day: two tools that make and revise a report with the user's own AI (*The AI tools make and revise a report with the user's own AI*, below). It was built in waves from a design audited the day before (17 agents, 74 findings), and the finding ids cited below (PROTO-1, SEC-3, GAP2-1 and the rest) are that audit's, in `DevFiles/forma-audit/mcp-2026-11-23-findings.md`, with the loop's state and the owner's decisions in `DevFiles/forma-audit/mcp-2026-11-23.md`; PS-1 to PS-10 and T1 to T10 are the review of the third wave. This note owns the Node side of Forma: the server, the one command a host runs, the stdout rule, the folders and paths a tool may use, what a tool returns, and where all of it differs from the browser. The web app's own path is [gemini.md](gemini.md) and [app-shell.md](app-shell.md). **Nothing here is loaded automatically.**

Generation through the server is built since 2026-11-24 (the MCP work's waves 6 to 9): `generate_report` makes a report from words and files and `revise_report` changes one, each with the AI the user set up in the server's environment, under the workspace's rule that an AI must be set up to start (§2.5 of the [PRD](../PRD.md)). The command line's `generate` and a database's schema are still to come, and nothing public may describe them as available (*What comes next, and whose step each is*, below).

## What the server is, and why it is not generation server-side

Forma's MCP server is a program the user runs on their own computer, from a clone of the repository. Their AI host (Claude Code, Visual Studio 2022's Copilot, VS Code, Claude Desktop, any MCP client) starts it and talks to it over its stdin and stdout, and nothing else talks to it: it opens no port, has no hosted origin, and nothing of it is built into `dist/`, so the live site never runs it and a deploy never sends it. It was asked for in discussion #1 on GitHub; on 2026-10-28 the owner welcomed it for after the command line, and on 2026-11-23 chose it first, on one Node core that the command line will reuse.

[`docs/PRD.md`](../PRD.md) section 6 rules out moving generation server-side, and the server does not break that rule, for the reason the rule exists. A server holding every user's key would be custodian of every user's third-party credential, the exposure section 5 records as resolved. This process is the user's own program, started by their own host on their own machine; it holds only that user's files and, for its two AI tools, that user's key, read from that process's own environment. No other user can reach it, because it has no listener: a server on 127.0.0.1 would be reachable by everyone signed in to the PC, which is what Forma Designer had to be guarded against (section 5). So a remote transport for it is out of scope too, and `boundaries.test.ts` refuses any listener in `src/mcp` and requires `serveStdio` in its entry (SEC-12).

Replacing the browser's direct call to the AI with MCP stays out of scope for the reasons section 6 gives. The server is the other direction: other programs calling Forma.

## The host runs one command, from a clone

The command is `node <clone>/src/mcp/run.mjs`, with the clone's full path, from any working folder. `run.mjs` is plain JavaScript that registers tsx's loader, resolved from the clone's own `node_modules`, and imports the entry, `stdio.ts`. It names the clone's own `tsconfig.json` for that loader, as both worker threads do, because tsx otherwise applies the one in the folder the host started it in, the user's project, whose `paths` reach every package Forma's sources import (each bare specifier, zod and the SDKs among them, whatever its `include` says; no relative import) and whose compiler settings reach those sources when that project's tsconfig takes the clone in, as a CI job's checkout inside it can (tsx 4.23.15 applies them only to the files a tsconfig includes; CLI-8 of the command line's design audit, `DevFiles/forma-audit/cli-designer-2026-11-24-findings.md`; `stdio.test.ts` starts the server from a folder whose `tsconfig.json` sends zod to a stub that throws). Three forms came before it, and each failed:

- **The tsx CLI** (`node <clone>/node_modules/tsx/dist/cli.mjs <clone>/src/mcp/stdio.ts`), the first form documented, runs two processes: the CLI spawns the server as a child and listens on a named pipe for its own messages, parsing each frame unguarded. The process the host started had opened a listener, and one malformed frame from any process of the same Windows user ended it (PS-8, measured in the wave-3 review). Registered as `run.mjs` does it, tsx opens no listener; `stdio.test.ts` checks that the process it spawned is the server itself.
- **`npm run -s mcp`.** `npm run mcp` writes npm's banner to stdout, where only protocol messages may go (DOC-2), which is why the plan moved to `-s`, and `-s` does remove the banner. It still failed: a host starts the server in the user's project, so npm runs the `mcp` script of the nearest `package.json`, the user's own (PS-9), and on Windows npm is `npm.cmd`, which a host cannot spawn without `cmd /c` (T5). `npm run mcp` stays as a developer's command in the clone, never a host's.
- **`npx tsx`.** Outside the clone it fetches an unpinned tsx, because npx assumes yes when stdin is not a terminal.

**There is no bundle.** The design had `npm run build:mcp` writing `dist/forma-mcp.mjs`, and the audit found three things wrong with it (PROTO-2, DOC-1, TST-1): esbuild could not bundle the pipeline as `build-server.mjs` bundles `server.ts`, Firebase Hosting publishes everything in `dist/` on both sites, where the file would also break `check:size`, and every `npm run build` empties `dist/` first. So the server runs from the clone through tsx, and tsx is a devDependency: the clone needs a full `npm ci`, and `npm ci --omit=dev` leaves a server that cannot start. `package.json`'s `comment:mcp` says why its two dependencies, `@modelcontextprotocol/server` 2.4.0 and zod 4, are pinned exactly and why the v1 SDK already in the tree is not used.

The command is restated in every copy the Facts table of `CLAUDE.md` lists for it: `run.mjs`, `stdio.ts`, `CLAUDE.md`, `README.md`, the Docs page, `/self-host`, the PRD (§2.5, §3 and §6), `SECURITY.md`, `CONTRIBUTING.md` and this note. `stdio.test.ts` spawns exactly it, from a folder outside the clone, so the code side is held; `publicClaims.test.ts` holds the Docs article, the README section and `/self-host` to it and refuses an npm or npx form there; the PRD, `SECURITY.md`, `CONTRIBUTING.md`, `CLAUDE.md` and this note are kept by hand.

## stdout is the protocol, and nothing else writes there

On stdio the spec says a server must not write anything to stdout that is not an MCP message, and Forma's pipeline was written for a browser, where logging is free. `geminiService.ts` calls `console.log`, `console.info` and `console.debug` on every generation, Node sends all three to stdout, and Tesseract.js's workers reach the parent through `process.stdout.write` (PROTO-1). One stray line between two messages and the host drops the connection.

So the entry's first act, before anything else is loaded, is `installStdoutGuard` (`stdoutGuard.ts`): its only static import is the guard, and everything else is imported dynamically after it, because static imports run before the body. The real stdout is kept for one Writable, `protocolOut`, which only the SDK's transport is given. Every other write, every console method and stdout's `end` go to stderr, with any key taken out on the way (a host keeps a server's stderr in its logs, Claude Desktop in `mcp-server-<name>.log`). An unhandled rejection is logged and the server keeps serving, since Node 24 would otherwise exit and Claude Code marks an exited stdio server failed until someone presses Reconnect; an uncaught exception is logged and the process exits non-zero, because Node's own docs say a process is not safe to resume after one.

What the guard cannot cover was measured in the wave-3 review (PS-7): a synchronous write to file descriptor 1, a child process that inherits this one's stdout (spawned with its stdio inherited, or forked), and `process.stdout.end(chunk)`, whose last chunk goes through the stream's internal write rather than the property the guard replaced. The last is now covered; the first two are refused by `boundaries.test.ts` in `src/mcp` and in every module it can load. `stdio.test.ts` spawns the server with a test-only switch that writes through every route the guard covers, keys included, and reads stdout line by line for anything that is not JSON-RPC.

Start-up is kept light for a related reason (PROTO-10): no pipeline module is imported on the thread that answers the host at all, since the report tools' work runs in a worker thread that loads each module when a job first needs it (the section on that thread, below), so the server answers its first request in well under a second. Claude Code's docs say it may skip asking a stdio server for the newer protocol for seven days, for example after the server exits when asked.

## Both protocol eras, from one factory

MCP's revision of 2026-07-28 broke with the 2025 revisions: no initialize handshake, `server/discover` instead, and capabilities in each request's envelope. Hosts are on both. `serveStdio`, from the SDK's v2 package, serves both from one factory, `createFormaServer`, which it may call more than once for a connection, so the factory registers everything and keeps no state beyond its own connection.

**The era is the connection's, never the request's** (PS-1). The first version read it from each request's envelope, and a 2025-era client that put the 2026-07-28 keys in its `_meta` was then treated as modern: `forma_status` misreported it, and the server asked for its roots in a way the SDK's legacy shim either refuses or turns into a `roots/list` with no timeout. `eraOf` (`toolShape.ts`) reads the revision the connection negotiated.

**The tool list never changes after start-up**, and the server says so (`tools.listChanged: false`): Visual Studio resets every approval a person gave to a server's tools when the server says its list changed (GAP3-5), so a tool switched on or off later would cost every approval. The two tools that need an AI are listed always and refuse without one, rather than appear once one is set up.

## The folders a tool may use

A tool reads and writes the user's files only inside the folders in effect (the server's own cache in Forma's folder aside, and tsx's in the temp folder: *What Node makes a report with*, below, its paragraph on Forma's folder), taken in this order, the first that answers winning (`roots.ts`):

1. `FORMA_MCP_ROOTS`, full paths separated by `;` on Windows and `:` elsewhere, set in the server's entry in the host. While it is set it is the only source, so a mistake in it refuses every file tool in words that name the entry, rather than falling through to a folder nobody chose.
2. The client's roots, when the client declared that it has them. Claude Code's docs say it answers with the folder it was started in and every `--add-dir` folder; other hosts may answer with the open solution or workspace. Whether Claude Code's newer runtime answers the 2026-07-28 form of the question on a plain tool call is not yet measured, which is one reason the third source stays.
3. `CLAUDE_PROJECT_DIR`, which Claude Code sets for the servers it starts.
4. None: every file tool refuses, and the message gives each host's recipe (`noRootMessage`), which `forma_status` also returns.

The design had only the first and third, and the audit found that only Claude Code would then have a folder (GAP3-1): Visual Studio 2022, VS Code and Claude Desktop set no `CLAUDE_PROJECT_DIR`, and Visual Studio documents no variable for the open solution. Roots are deprecated in the 2026-07-28 revision, with the twelve months the spec keeps a deprecated feature, and they are the one source those hosts may send; VS Code's default Copilot harness does not promise them, so its recipe sets `FORMA_MCP_ROOTS`.

**Asking for roots is gated by hand, because the SDK does not gate it the same way in both eras** (GAP3-2, measured). On a 2025-era connection the SDK sent `roots/list` to a client that had declared no roots, and a client that never answers then holds the tool call for the SDK's 60-second default. On a 2026-07-28 request, asking a client that did not declare roots fails the whole call (-32021), and `getClientCapabilities()` is undefined there, so the request's own envelope has to be read. So a 2025-era connection is asked only when its initialize capabilities name roots, with a 5-second timeout, and the answer (or the failure) is kept until the client says its list changed; calls made in parallel share the one request, since Claude Code runs read-only tools side by side and each used to send its own and wait its own 5 seconds (PS-10). A 2026-07-28 client is asked through an `input_required` result only when its envelope declares roots. A failure to list never fails the tool; it moves on to `CLAUDE_PROJECT_DIR`.

**Some folders are refused as roots, whatever their source.** A whole drive; the home folder or any folder holding it, such as `C:\Users` or `/home` (PS-3: only the home folder itself was refused at first, so `C:\Users` let a tool reach every profile); a dot-folder such as `.git`, `.claude` or `~/.ssh`, and any folder inside `.git`, `.ssh`, `.gnupg` or `node_modules` (PS-4: the rule that keeps tools out of dot-folders only looks below a root, so a root that was one switched it off). A folder further inside another dot-folder is kept, so a Claude Code worktree under `.claude/worktrees` works, with its own `.git` and `.claude` still refused below it. A client's root is converted from its `file:` URI with `fileURLToPath`, never by slicing the string: building it from `new URL(u).pathname` gives `X:\C:\...` on Windows, a reported host bug.

**Each root is held twice** (PS-2): as the host or the user spelled it, and as it really is once links are followed. Comparing a path as spelled against the root's real path refused every path spelled the user's way under a junction, a subst drive or an 8.3 name.

## Full paths only, judged before the disk is touched

A path argument must be fully qualified: `G:\Reports\invoice.repx` on Windows, `/home/me/reports/invoice.repx` elsewhere (`paths.ts`). Nothing is resolved against a root, the server's working folder or the home folder, because an MCP server cannot see the shell its host's model ran `cd` in (GAP2-1): a relative name resolved against `CLAUDE_PROJECT_DIR`, as Claude Code's docs suggest, opens a different file of the same name at the root, and a repair then writes its output beside the wrong file with no error. The forms a model on Windows actually writes were measured in the audit: `path.win32.isAbsolute('/g/DevFiles/x.repx')` is true while resolving it gives `G:\g\DevFiles\x.repx`, `/c/Users/...` lands on the current drive, `~/x.repx` becomes a folder literally named `~`, and `G:x.repx` is relative to the drive's current folder. Each is refused, and where the intended path can be worked out (a Git Bash `/g/...` path, a `file:` URL, `~`) the refusal hands it back, never acts on it (GAP2-3). This departs from Claude Code's own Read tool, which accepts all of them, on purpose.

The order of the checks is the security of it:

1. **The string, raw, with no file-system call.** A UNC path in any spelling (`\\host\share`, `//host/share`, the mixed `/\host`, and the Git Bash slip `//g/...`, all UNC to Windows) is refused here (GAP2-2), because a realpath of one opens an SMB connection, which sends the Windows sign-in to answer it. So are device names, a `:` after the drive letter (an alternate data stream) and a name ending in a space or a dot.
2. **A lexical check against the roots**, so a path spelled outside them never reaches the file system. `paths.test.ts` proves it with a file system that records every call (T1: the first version had one that threw when touched, inside checks that catch what throws, so the test could not fail).
3. **Every existing component lstat'd from the drive down**, which never follows the component itself. A link's target is read as written and refused when it names another computer, never followed to find out (PS-6): a directory symlink to a share, which a cloned repository or an extracted archive can carry, would otherwise be followed by the first lstat below it.
4. **`realpathSync.native`** on the nearest existing ancestor, and the result checked against the roots' real paths. The extension is judged again on the real path, so a link named `x.repx` leading to any other file is refused (PS-5). A hard link is a file in its folder by the file system's own meaning and is read as one: making one takes access to the file already, and refusing every file with a second name would refuse what backups hold. That is out of these checks' scope, and `paths.ts` says so.

A tool never reads from or writes into a dot-folder or a dot-file, never writes into `node_modules`, and never opens a file named as credentials (the patterns `.gitignore` keeps out, and `.env*`, `.mcp.json` and `firebase-applet-config.json`; since the wave-8 review, W8C-5, the files a .NET project keeps its connection strings in, `appsettings*.json` and `local.settings.json`, and a `connections*.txt`, which `generate_report` would otherwise send to the AI as data). It reads at most 20 MB, the web app's own limit for one file. A file is never replaced unless the call asks (only `repx_edit` can), and that holds at the moment of writing, not only when it was checked: the bytes go to a temporary file, which is then hard-linked to its name, since a link fails when the name exists where a rename would silently replace it, on Windows too.

Every function takes the platform's path module and the file-system calls it may make, so the Windows rules run on CI's Linux runners as well as here (TST-4), and the roots themselves pass the same full-path test before any file-system call.

## What a tool returns

Every tool goes through `defineTool` (`toolShape.ts`), so each rule holds for all of them rather than for the ones someone remembered:

- **All four hints are set.** The spec's defaults are destructive and open-world, so a tool that set only `readOnlyHint` would advertise itself as both. Claude Code runs `readOnlyHint` tools in parallel, so a read-only tool keeps no shared state. `repx_audit` and `repx_outline` are read-only and idempotent; `repx_repair` and `repx_pdf` write a new file and never replace one, so a repeat finds the same bytes and says `unchanged`, which makes them idempotent and not destructive (PROTO-6); `repx_edit` can replace a file when asked and an `add` made twice adds two labels, so it is destructive and not idempotent (GAP3-5).
- **The result is a file and a summary, never the XML or the PDF** (PROTO-5). The text stays under 40,000 characters, below the 50,000 at which Claude Code saves a result to a file instead of showing it.
- **The same data twice**: `structuredContent` for the hosts that read it, and the same JSON in the text under a one-line summary, because a host on an older revision may hand its model only the text (GAP3-5: the SDK sends structured content to every revision, and nothing promises the model sees it).
- **Text read from a file is data.** A report made by someone else controls its strings, and the host's model may have a shell. Such text is returned only under `fromFile`, each string clipped and its whitespace folded, with a note beside it that it is data, never instructions; never in a summary, a description or an error (SEC-6).
- **Errors are results, in plain words**, keys taken out, under 2,000 characters; a refusal is written for the model and says what to do instead. Any other error's message goes to stderr only, and the result says an internal error stopped the tool (the wave-4 review's REV4-2): a library's message can quote the file it was reading, as a regular expression built from a report's `Ref` once quoted the report, so it was a way around `fromFile`.

`toolList.ts` is the list in its order, each tool's name, whether it is read-only and whether it needs an AI, as a pure module with no SDK import, so a test of the pages can read it without starting a server (DOC-5). `formaServer.test.ts` holds the registered tools and their hints to it, and `publicClaims.test.ts` holds every name, and which need an AI, to the Docs page's article and the README.

## The report tools run the web app's own modules

`repx_audit`, `repx_outline`, `repx_repair`, `repx_edit` and `repx_pdf` (2026-11-24, the fourth wave) each run the module the web app runs, so a fix there reaches both: `auditRepx`, the chat's `reportOutline`, `repairRepx` in `REPAIR_ORDER`, the chat's `applyEdits`, and the draft PDF that `scripts/repx.ts` drew, moved to `src/lib/draftPdf.ts` so the script and the tool share it. The chat's edit words and its list of edits moved into `src/lib/editLanguage.ts` for the same reason: the chat's prompt interpolates them, and its text was compared byte for byte before and after the move. `repx_edit` takes every edit the chat makes but `data`, which needs a database layout the server does not hold, and its schema is checked by `tsc` against the chat's own type, so an edit field added there fails to compile until the tool has it. `forma_status` says what the server is and which folders are in effect.

What reading a report means here, in `reportFile.ts`:

- **The stored database login comes out first, on every read** (SEC-3), through `withoutStoredLogin`, the check the web app's intake runs on an uploaded `.repx`, moved into `repxSqlDataSource.ts` so both share it. The host's model is an AI too, so a login must never reach it. Every result says `loginRemoved`, and a file whose connection was stored with more than its name is never written over in place, since writing it would take that out of the developer's file.
- **Wherever DevExpress stored it** (the wave-4 review's REV4-1, measured). The first version read only the first `ComponentStorage` and found an item by its `Ref`, built into a regular expression. DevExpress 20.1.3's `SaveLayoutToXml`, run headless by the reviewer with no database, writes a `SqlDataSource` in two more places: in `ObjectStorage`, for a source assigned to `report.DataSource` in code and never added to `ComponentStorage`, and in an embedded subreport's own `ComponentStorage`, inside its `ReportSource`, which comes before the root's. The first kept its password in every file the tools wrote; the second did too, while every result said the login was gone, and the outline named the subreport's source as the report's. So every `Base64` value in the file is read now, on any element, in any attribute order and either quote, and one that decodes to XML with a `<Connection>` is rewritten by its position; no pattern is built from the file, so a `Ref` such as `0(` can no longer break the read or make it run for seconds (REV4-2). The result is then read again, and a login still found there (in a connection left open, say) refuses the report: nothing is returned or written from it. The web app's intake shares the change, and sends no part of such a report. A JSON data source's stored credentials are not taken out yet: whether DevExpress 20.1 writes them into a `.repx` is still to be measured with `RepxProbe` (SEC-3).
- **A file that is not well-formed XML is refused** before any pattern reads it (`xmlShapeProblem` in `reportFile.ts`, one pass over the text), with the line and column where it breaks and never its words: the review measured malformed files of a few kilobytes, a run of unclosed tags, on which the outline and the audit grew with the cube of the size. A document type is refused too (a layout never declares one, and its entities are what an expansion attack uses), and so is nesting more than 256 deep. A truncated report is refused with the rest, so `repx_audit` does not audit one: the refusal says where it stops.
- **A `.vsrepx` is read as a `.repx`**: it is the same serializer XML, Visual Studio's working file for a report class (GAP1-2). Written as a `.repx`, Visual Studio's working-file mark is neutralised as DevExpress's own converter does it (its `Key` and `Value` become `Skip`), because DevExpress says its loader refuses a marked file from 20.2.4 on; that is a pass in `REPAIR_ORDER`, so the web app's chain runs it too and it acts only on a report that carries the mark. A `.vsrepx` is written only from a `.vsrepx`.
- **A `.vsrepx` written back is checked against its Designer file** (GAP1-3): the report class's `.Designer.cs` or `.vb` beside it looks controls up by name, and a layout that lost one of those names would leave that field null when the report runs. Where the Designer beside the file written looks one up, `repx_edit` writes nothing and the result says why; `repx_repair` writes all the same, with a notice naming the names.
- **A report written as C# or VB code is refused by its name, never opened** (GAP1-1), in words that say how to save a `.repx` from it, or that name the `.vsrepx` beside it. DevExpress's docs say its current Visual Studio designer stores a layout as code by default; that was read from a search summary, because the page itself refused a direct fetch, so it is recorded as unconfirmed.
- **A report's own code is kept by a repair**, as generation keeps a user's: the audit names it.

The REPX skill, `docs/skills/devexpress-repx/SKILL.md`, is served as the resource `skill://devexpress-repx/SKILL.md` through the SDK's skills extension, with a preface of the server's own after its frontmatter (`skillResource.ts`, PROTO-11 and GAP2-5). The skill's command lines use relative names, which are right in a shell in the clone; a model reading it through the server would copy them into tool arguments, which refuse anything but a full path, so the preface says so with one Windows and one POSIX example, and the file itself keeps its relative links for `npm run lint:links` to check.

## A report costs one call, never the server

The report tools read files someone else made, with modules written for a report a person is looking at in a browser tab. The wave-4 review (REV4-3) measured what that cost on one thread: a well-formed 1.3 MB report of 12,000 overlapping labels ran the server out of memory, and the process ended with every tool in it, so the host lost Forma until someone reconnected; malformed files of a few kilobytes held the thread for minutes, while no other request was answered, `forma_status` included, and a cancellation changed nothing. The 20 MB limit on a file bounds neither.

So a tool's work runs in a worker thread (`workerPool.ts`, which starts `worker.mjs`, which runs `pipeline.ts`), and the thread that answers the host only judges paths, reads and writes files and shapes results:

- **Bounds**: 512 MB of heap, a 4 MB stack and 30 seconds a call (`PIPELINE_LIMITS`). Passing one, or the call's cancellation, ends that worker, and the call gets a refusal in plain words (or the wrapper's "Stopped"); nothing is written, and the server goes on. The reviewer's 12,000 labels now get the memory refusal in about four seconds, with `forma_status` answered meanwhile; the malformed files are refused by the shape check before any pattern runs.
- **One worker kept idle**, unref'd so it never holds the process open; calls made at once each get their own, since Claude Code runs read-only tools side by side. A worker that failed in a way that is not a refusal is ended, never reused.
- **The worker's stdout and stderr are its own** (`stdout: true`, `stderr: true`), read by the pool and sent to the server's log on stderr: otherwise Node pipes a worker's stdout into the process's own, where only protocol messages may go. `boundaries.test.ts` refuses a `Worker` started without that.
- **tsx again**: a new thread starts with none of its parent's loaders, so `worker.mjs` is plain JavaScript that registers tsx itself, as `run.mjs` does; `stdio.test.ts` runs the report tools through the real launcher and its worker.
- **Where it is measured**: v8 coverage does not follow a worker, so `pipeline.ts`'s jobs also run in the tests' own thread (`inThread` in `testClient.ts`); `reportTools.test.ts` runs every tool through the real worker too, and holds the deadline, the memory limit and the cancellation with workers of its own that never answer or never stop allocating.

## What it sends, and what it never reads

**Only the two AI tools make a request, and only to the AI set up.** The report tools call no AI, need no key and make no network request. The modules they load are the web app's, and some of them can reach the network: `agentEdit.ts` imports `repxTranslate.ts`, which loads `geminiService.ts` lazily inside the function that translates a report, and no report tool calls that function. `generate_report` and `revise_report` reach the AI set up in the server's environment and nothing else: Google's Gemini API, through the client every Gemini call in `src` is built with (`geminiClientOptions`, pinned to Gemini's address since the MCP work's wave 1, so no environment variable can move it: [gemini.md](gemini.md) — *The Gemini call runs in the browser, not on the server*), OpenRouter's address, or a Local AI server on this computer, which the server refuses to start the AI tools with when its address is anywhere else (*The AI tools make and revise a report with the user's own AI*, below). A Node process has no Content Security Policy, so nothing but the code bounds where it could send anything (DOC-6): `legalDisclosure.test.ts` follows every import `src/mcp` makes, into `src/lib` and `src/services`, and fails on a host the privacy policy does not name. OCR reads its languages from the installed packages and PaddleOCR's models from `vendor/paddle`, never a CDN (*What Node makes a report with*, below).

**No telemetry, no learning events, no error reports.** What the web app learns from (Settings → Learning) and the error reports a person can turn on are the browser's, recorded through the workspace and under a signed-in account ([persistence.md](persistence.md) — *Error reports, only when asked for*); nothing in `src/mcp` records an event, and the server has no account. What a tool returns goes to the host and from there to the AI behind it, under that host's own terms (SEC-11), and what the AI tools send goes to the AI the user set up, under that provider's terms; the privacy policy says both.

**No `.env`.** The entry never loads dotenv: a `.env` in the folder a host starts the server in is the user's project's business, and a `GEMINI_API_KEY` meant for something else must never be spent by Forma (SEC-9). Within `src/mcp` only the entry reads the environment: `FORMA_MCP_ROOTS`, `CLAUDE_PROJECT_DIR`, the AI's variables (`AI_ENV_NAMES` in `aiSettings.ts`) and its test-only switch. `boundaries.test.ts` holds both, and that nothing outside `src/mcp` reads a key from the environment beyond the five reads already decided. `.env.example` says the server reads none of that file.

## The AI tools make and revise a report with the user's own AI

`generate_report` and `revise_report` (2026-11-24, the MCP work's wave 8) run the web app's own generation, so a fix there reaches both. `generate_report` takes a description, files, or both: under `files` a picture or scan, a PDF, a `.repx` or `.vsrepx` to start from, a Word or Excel template, an SSRS or FastReport report, and under `data` alone the data files whose columns become the report's fields, so a `.json` or `.txt` reaches the AI only when it is passed as data (SEC-5), with any `password=` or `pwd=` in its text taken out first, as the intake takes one out of an SSRS definition (`withoutPasswords` in `repxIntake.ts`, the wave-8 review's W8C-5, which the workspace's own data files go through too). It runs `makeReport` with Node's parts (*What Node makes a report with*, below) and writes a new `.repx`: `output` when given, else `<first file>.generated.repx` beside the first file. `revise_report` is stateless (PROTO-9): the file is the report, opened as every report tool opens one, its stored login out first; a plain question is answered from the report's facts with no AI, and anything else takes the chat's own path, the outline to the AI through the free chain, `readReportOutcome`, then `applyEdits` by control name with App's one follow-up pass, or a redesign through `makeReport` with the report open. The result goes to a new `<name>.revised.repx`, and the file sent is never changed, so keeping it is the undo. The chat's export, the designer, sample rows and Undo have no equivalent and are said so; a translation runs only when the words ask for one. Both write `.repx`, never `.vsrepx`, with Visual Studio's working-file mark neutralised, and never replace a file. A result names the file, the AI that answered and, when the free chain asked another on a limit, its switch note in the notices, which the app shows as a privacy fact (SEC-11); when Forma's own draft stood in, the result says so and which, with the AI's error under `fromFile`.

**The gate is the workspace's** (owner decision OD6, PROTO-8). The AI chosen must be ready, by the web app's own `aiReady`: Gemini with its key, OpenRouter with its key and model, or Local AI with its server and model, and nothing else beside it. Without one both tools stay listed and refuse before any path is judged, in `SET_UP_AI`'s words, why, and the variables to set in the host's entry (`notReadyMessage`). `forma_status` does not report the AI's state; the refusal and one line on stderr at start-up say it.

**The settings are the server's environment, read in its entry alone** (NODE-12, SEC-9, DOC-4). The entry copies these by name and hands them to `readAiSettings`, which reads nothing itself:

- `FORMA_GEMINI_KEY`, a Gemini key;
- `FORMA_OPENROUTER_KEY` and `FORMA_OPENROUTER_MODEL`, an OpenRouter key and the model it answers with;
- `FORMA_LOCAL_MODEL`, and `FORMA_LOCAL_URL` when the server is not Ollama's default `http://localhost:11434/v1`: a model on the user's own computer through Ollama's or LM Studio's OpenAI-compatible endpoint;
- `FORMA_PROVIDER` (`gemini`, `openrouter` or `local`), which one designs. Left out, the one set up is chosen; with more than one set up and none chosen, both tools refuse rather than guess, because guessing Gemini or OpenRouter for someone who also set up a model on their own computer would send their report off it. Another AI set up beside the one chosen is the free chain's next on a limit, as in the app, and never after Local AI ([own-model.md](../proposals/own-model.md) — *Local and free models, and the free chain*);
- `FORMA_MODEL`, a Gemini model to answer with, never probed; `FORMA_LOCALE`, the locale the paper follows when nothing in the request says it;
- `FORMA_MCP_MOCK`, `1` or `true` for the mock invoice in place of the AI's answer. It replaces the answer only: an AI must still be set up (there is no mode without an AI), so a test sets a stand-in key, and a result then names the mock as what answered.

The key's name is Forma's own, so a `GEMINI_API_KEY` or `GOOGLE_API_KEY` set for another tool is never spent here; the entry deletes both, and Google's three Vertex AI switches, from its own environment before anything loads the Gemini SDK, which would otherwise fall back on them by itself (DOC-4), and deletes Forma's two key variables once copied, so no worker thread inherits them: each job carries its settings. A Local AI address must be this computer's (SEC-11): `localhost`, `127.0.0.1` or `[::1]`, any port, over http or https, with no user name or password. In the browser only the site's CSP keeps Local AI on the computer; a Node process has none, so an address on the network would send a report off it in clear text while the result still said "Local AI". Anything else refuses both tools in plain words until it is corrected; allowing an address on the network is the owner's decision.

A value that is only a reference, `${FORMA_GEMINI_KEY}`, `${env:NAME}`, `$NAME` or `%NAME%`, is taken as not set and refuses both tools, saying it arrived unexpanded (`UNEXPANDED`, the wave-8 review's D2). Claude Code's documentation says that when a variable is not set it "uses the unexpanded ${VAR} text as-is", so a user who set the key in the wrong place or skipped opening a new terminal sent the reference itself to Google as the key, failed as an invalid key, and found the cause redacted from the error, since the reference was long enough to count as a secret. No refusal repeats any other value it judged (W8C-4): an address that does not parse and a `FORMA_PROVIDER` that names no AI are said wrong without being quoted, because a key pasted under the wrong name would otherwise be repeated to the host's model and its log.

**Where the key then lives** (SEC-8, GAP3-4). The website's statements are about the website: there a key is held in `sessionStorage`, never written to disk in readable form, with an encrypted copy only on request ([gemini.md](gemini.md) — *Where the user's key lives*). The server is the other case, and the pages say so where they say the rest. It reads the key from its own environment, which the host builds from the server's entry, so the key is stored readable on the user's computer: in the host's configuration file (Claude Code's `~/.claude.json` for local and user scope, Visual Studio's `<solution folder>\.vs\mcp.json`, out of source control only where the solution's `.gitignore` ignores `.vs/` (the README says to check with `git check-ignore`), or its `%USERPROFILE%\.mcp.json` for every solution, VS Code's `~/.copilot/mcp-config.json`, Claude Desktop's `claude_desktop_config.json`), or, through a `${FORMA_GEMINI_KEY}` reference where the host expands one (Claude Code in every scope; the Copilot file's `${NAME}`), in the user's own environment, wherever that is kept. The recommendation is the reference, in a file of the user's own (local or user scope), the value set once in the user's environment without typing it on a command line, which the shell's history and an agent's transcript keep ([gemini.md](gemini.md) — *The fidelity benchmark* says the same of `FORMA_BENCH_KEY`), then the host restarted. Never a literal key in a file a project commits: Visual Studio's `<solution folder>\.mcp.json`, a workspace-root `.mcp.json` and Claude Code's project scope are each documented for source control, and Visual Studio's standard `.gitignore` ignores none of them. Forma's pre-commit hook refuses a key in an MCP configuration only in a Forma clone that turned the hook on, never in the user's own repository. Claude Desktop's file is per user and never in a solution, but it is reported (in issues, not its documentation) to expand no `${...}`, so a key there is written as it is. Not yet tried, and left for the run in each host: whether Visual Studio's `inputs` prompt with `password: true` keeps a key out of the file. The Windows Credential Manager is not offered, the owner's call (SEC-8).

**One key scrubber** (SEC-7). `lib/keyRedact.ts` holds the patterns the error reports, the problem report, the stdout guard and the server share. `KEYS`, the error reports' and the problem report's, takes out both Gemini key forms, OpenRouter's `sk-or-v1-`, another provider's `sk-`, `pk-` or `rk-` key and a bearer token. The server and its guard take out `FORMA_KEYS`, the first three alone (the wave-8 review's W8C-2): its results and log lines name files and carry a report's text, and with the generic forms a file named `sk-customer-invoices-2026.repx` came back as `(a key).repx`, a file that does not exist, and "the bearer instrument" lost a word. It holds no other key to protect: it reads no Local AI token, and a key of another provider inside a file it reads is in the user's own file. `redactorFor` also takes out the literal values of the keys the server was given, so a key in a format the patterns do not know is still caught by its value; a Local AI token is never read, so none is handed over. The entry hands the guard its key values (`addSecrets`), `GEMINI_API_KEY`'s and `GOOGLE_API_KEY`'s too, before anything can print them, and from then on every result, every error and every line on stderr passes through it. Keys come out before anything is cut short, never after (W8C-1): a key cut in two is neither its value nor a whole key's shape, and an error quoting a key past the 200-character clip of text under `fromFile`, or past the 300-character cut the work's thread used to make, sent the key's first characters out. A failure inside the AI call becomes a refusal ("No change was made: ...", "No report was made: ..."), its first line only, its keys taken out, then cut to 300 characters.

**One at a time, progress, and a stop** (OD7, PROTO-3, PROTO-4, PROTO-7). One AI call runs in the whole process, whichever connection asked (`oneAtATime` in `generator.ts`): one report can spend a free day's requests, and the spec asks a server to rate-limit its tools. A second call waits and is told "Waiting for the report before it to finish." through its progress, when it asked for progress; a host that did not hears nothing while it waits, and the wait counts against that host's own cap. One cancelled while it waits never runs. A `generate_report` call that waits holds its words and the paths it was sent, not its files: its job is made, the files read, only once it has its turn (`JobSource`, the wave-8 review's W8C-6), and the files' bytes are then moved to the work's thread rather than copied. Approval is the host's own permission prompt, so no tool asks for a person on every call. Progress goes out only when the request carried a `progressToken`: each stage owns a fixed range, the value only rises, a beat every 15 seconds of silence keeps a host that counts silence from giving up, at most one a second within a stage while each stage's start is sent at once, and none after the result. A cancellation reaches the generator, which ends the work's thread at once, so no request goes out after it and nothing is written; `writeOutput`'s temporary file is removed. stdin closing ends the generator and the process. The AI tools' thread is their own (`genWorker.mjs`, started by `generator.ts`), with 2 GB of heap and a 15-minute deadline (`GEN_LIMITS`), since one report may cost six requests and the fidelity benchmark recorded single runs of four minutes; one is kept idle between calls, unref'd, with Forma's models read. Its stdout and stderr are its own, read into the server's log through the scrubber.

**A host's own cap still applies** (GAP3-3). Claude Code's docs give a stdio server 30 minutes of silence, which the beat keeps open, and say a per-server `timeout` is a hard limit progress does not extend (its default is about 28 hours). Claude Desktop on Windows reportedly ends any call at about four minutes, with no setting, and cancels it: Forma then stops at once and writes nothing, the owner's choice between that and finishing a report nobody is waiting for. A host that stops waiting without cancelling still gets the file written, and every file the two AI tools write is named on stderr too, so it can be found there. Visual Studio and VS Code document no tool-call timeout; neither was measured.

**What the workspace has and the server does not**: a Local AI vision model or page reader, the memory and its house font, the report library, kept reports, a shared database and sample rows, learning events and handwriting. `revise_report` sends the AI no Docs articles, which the web chat sends, since `docsCorpus` is a components module that `src/mcp` may not reach.

## Where it differs from the browser

| | The web app | The MCP server |
|---|---|---|
| Who starts it | A person opens a page | The person's AI host runs `node <clone>/src/mcp/run.mjs` |
| What bounds its requests | The CSP's `connect-src` | Its code: only the two AI tools make one, to the AI set up; the Gemini client is pinned to Gemini's address, and Local AI to this computer |
| Where the key lives | `sessionStorage`, with an encrypted copy only on request | The server's environment, from the host's entry: readable on the computer, in the host's configuration file or the user's environment |
| Which files it sees | What the person attaches | Only files inside the folders in effect, by full path |
| What it gives back | A download, through `download.ts` | A file written beside the input or where the call names, never replacing one unless asked |
| A stored database login | Taken out of an uploaded `.repx` at intake | Taken out on every read, before anything sees the text |
| Code in a report | Removed from a generated report unless the person's own report had it | Kept by a repair, and named by the audit |
| Who chooses an edit | The chat's AI, from the person's words | The host's model through `repx_edit`, in the chat's edit language, or the user's own AI through `revise_report` |
| How many reports at once | One per tab, Batch one at a time by default | One AI call in the whole process; a second waits |
| Learning, memory, the library, error reports | As Settings says | None |
| Text from a file | Shown on the page | Returned under `fromFile`, as data |
| Where it runs | Any browser | Node in the project's range, from a clone with a full `npm ci` |

The draft PDF is the one output that is not the web app's: `scripts/repx.ts` drew it before the server existed, laid out by the Preview's engine with no data, in the standard PDF fonts, the first line of each text. It is a draft for checking where things fall, not the PDF the Preview exports.

## What Node makes a report with

Since 2026-11-24 (the MCP work's wave 7) `src/mcp/nodeGeneration.ts` assembles every part the core is handed, in Node, and runs `makeReport` with them (`make`); `nodeMakeReport.test.ts` runs it end to end, the AI stood in, on a picture and two PDFs drawn in the test. Since wave 8 the AI tools run it in their own worker thread (`genJobs.ts`, run by `genWorker.mjs`). Since wave 10 the fidelity benchmark makes each report with the same parts and its own `ask` (finding NODE-9), so what it scores is what `generate_report` ships, and every difference below is one it measures too; its doc comment lists them for a reader of the benchmark, and [gemini.md](gemini.md) — *The fidelity benchmark* has the parity gate the move was held to.

**`make` must never run on the thread that answers the protocol.** pdf.js parses and draws a PDF on the thread that calls it, and nothing bounds what a small PDF asks of it. The wave-7 review (NODE7-PDF-HEAP, each case in a process of its own from an empty folder) measured a 611 KB one-page PDF whose one stream holds 20,971,520 `cm` operators ending the process in about 67 seconds, V8's heap out of memory (exit 134, beyond the stdout guard's handlers), a 1 MB PDF inflating to 1 GB taking 42 seconds at 2.4 GB with the event loop stalled up to 13.8 seconds at a time, and eight pages of it still running at the 180-second deadline. On the protocol thread one such attachment stops the server answering every client, cancellation included, or ends it. The same PDF in a `worker_threads` worker with `resourceLimits: { maxOldGenerationSizeMb: 512 }` ended that worker out of memory after 31 seconds with the host alive at 484 MB, so the AI tools run `make` in such a worker, with 2 GB of heap and a deadline sized for a generation, 15 minutes (`GEN_LIMITS` in `generator.ts`), not `workerPool.ts`'s 30 seconds; `resourceLimits` bounds V8's heap alone, not ArrayBuffers or native memory, which is why the deadline and the picture budget below stand beside it. A stop reaches the intake: `makeReport` hands the request's signal to `ingestFile`, which takes no file in once stopped, stops a PDF between its pages and destroys its document (`withNodePdf`), but cannot interrupt pdf.js inside a step.

What it reads with, and where that differs from the browser:

- **Files.** `lib/repxIntake.ts` draws on what it is handed (`Drawing`): the browser's OffscreenCanvas and DOM in `lib/browserIntake.ts`, moved there unchanged, and @napi-rs/canvas in `nodeIntake.ts`, so straightening a scan, the `MAX_IMAGE_EDGE` downscale and the redraw of a type the AI does not take are one piece of code (NODE-2), and a fix to one is a fix to both: wave 10's parity gate found the straightening laying a straight form on its side, in Node and in the browser alike (`lib/deskew.ts`, [app-shell.md](app-shell.md) — *Foreign reports, templates and crooked pages at intake*). A PDF is opened with pdf.js's legacy build, its worker given as a file URL and run in the same thread, and the standard fonts, character maps, colour profiles and wasm decoders taken from the installed pdfjs-dist, so a PDF that names Helvetica without embedding it still draws. A File built from a path is typed by its extension, as a browser types a dropped one. `checkRepx` reads a report itself where there is no DOM (`readXml` in `lib/repx.ts`), where every `.repx` was told "This XML could not be checked." A picture is decoded only when its header (PNG, JPEG, GIF, WebP or BMP) names a size within `MAX_PICTURE_PIXELS`, 100 million, and its pixels are let go once it is drawn: the review measured a 257 KB PNG 46,000 pixels square costing 2.1 GB to decode, and two 40,000-pixel ones taken in one after the other peaking at 3.2 GB, native memory no heap limit bounds (NODE7-PICTURE-MEMORY). One past it, or of another kind, goes as it came where the AI takes its type and is told where it had to be drawn, and OCR does not read it; a 48-megapixel photograph and an A3 page scanned at 600 dpi are inside it.
- **OCR.** The browser's rule, in one place for both (`lib/ocrRead.ts`): English by PaddleOCR when `vendor/paddle` holds the three pinned models, each checked by SHA-256 against `scripts/fetch-paddle.mjs`'s pins, through onnxruntime-node (`nodePaddle.ts`, the reader the measuring scripts now share); by Tesseract otherwise, and for a page outside PaddleOCR's script; then the page's own language (NODE-5, owner decision OD2 as revised). Tesseract's languages come from the installed `@tesseract.js-data` packages, which the lockfile pins, gathered into Forma's folder, each checked against the installed file before a worker starts: no fetch step and never a CDN (NODE-10, TST-7). Every worker starts with `cacheMethod: 'none'`, so the working folder is neither read for a `./eng.traineddata` nor written to (SEC-2), and with `errorHandler`, so a damaged picture or a missing language rejects its reading instead of ending the process (NODE-1); it is handed PNG bytes only. The languages are gathered when the parts are assembled, so a package missing or a Forma folder that cannot be written is an error then, naming it; gathered only at the first reading, as they were, every page went without its text and the report was made on the path NODE-3 forbids, with one line on stderr (the wave-7 review's NODE7-OCR-QUIET). A page OCR still cannot read is said in the result's notices ("OCR could not read the text of ..., so the AI was sent its picture alone"), never in the log alone. One worker reads at a time; a reading stopped ends it, asks nothing more of it (it checks it was not stopped before each recognition, since one asked of the worker being ended was an unhandled rejection inside tesseract.js, NODE7-ABORT-UNHANDLED), and an idle one ends after a minute on a timer that never holds the process open. Its output reaches the parent through `process.stdout`, which the guard sends to stderr; Tesseract's own native messages go to stderr already. Where it differs: PaddleOCR's picture is enlarged as the measuring scripts enlarge it (`resizeRgb`), where the browser's canvas smooths it; no handwriting is read; and the text sent with the request still says it was read "in the browser" (`layoutText`), a prompt the browser shares.
- **Forma's models.** The box reader and Forma's own model are read from `assets/model` in the clone, through the same checks the browser's loaders make (`boxReaderFrom`, `formaModelFrom`), when the parts are assembled: a model that is missing or unreadable is an error then, naming the file, never a report quietly made without Forma's draft, which is what the browser's loaders, given a relative URL in Node, did (NODE-3).
- **Measured text.** @napi-rs/canvas is handed to `lib/textMeasure.ts` (`measureOn`), so the print check, the fit to the page and the box reader's widths measure text where the browser measures it (NODE-11). Its widths were held to the parity rows before it was turned on: "AVATAR Wave To LT Yo" at 20pt measured 311.822 units in Arial unkerned and 293.349 kerned, against the 311.822 and 293.342 DevExpress printed, and Times New Roman, Trebuchet MS and row 53's turned line within 0.04 units. The canvas finds a family among the fonts the machine has, and until the CLI and Forma Designer work's wave 1 (2026-11-24, GAP2-1) nothing else: WSL's Ubuntu 24.04 measured Arial and Times New Roman alike in DejaVu (325.982 units for that line), so the two faces a page's sizes are read in (`ocrLayout.ts`) became one, and a host with no fonts measured every width as 0, so no line wrapped and nothing grew: the print check could find no report printing on more pages than its page, and Forma re-asked about none. GitHub's ubuntu-24.04 runner most likely measured the three right by accident: Google Chrome's package depends on `fonts-liberation`, and with Liberation installed the canvas found Arial, Times New Roman and Courier New through an alias it does not document (measured on such a host, not on the runner). Now `nodeFonts.ts` registers, for each of five families the machine lacks, a metric-compatible face under its name before the canvas is handed in: Liberation Sans, Serif and Mono from `assets/pdf-fonts` for Arial, Times New Roman and Courier New, Carlito and Caladea from `assets/metric-fonts` for Calibri, Office's default body font and the one a Word or Excel template that names none is read in, and Cambria (owner decision OC7; Caladea 1.002, under Apache-2.0, since the OFL Caladea Google Fonts ships has its own widths, not Cambria's: the folder's README). Each face goes in with its own weight and style: registered bare, the last face of a family measured every style (GAP2-2). So the five measure alike on any machine, with nothing for the person to install: four with the same widths, and Cambria in Caladea to within 0.015 em a line unkerned and 0.049 em kerned (the folder's README); Windows in its own fonts, Linux in Forma's, with the host's fonts or none. `nodeGeneration.test.ts` holds the parity rows unconditionally, on CI's Linux too, where it.runIf skipped them until then, Courier New's among them, and Trebuchet MS's where it is installed; since the wave-1 review (FONTS-R3, FONTS-R4) `nodeFonts.test.ts` holds every face of the table to its family's widths on Windows, in each style, and `nodeGeneration.test.ts` shows assembling registers them, with a family no host has, since on Windows nothing is registered and with Liberation installed the canvas finds Arial and Times New Roman without it. A canvas that still measures nothing is an error when the parts are assembled, never a quieter report. Any other family the machine lacks (on Linux Tahoma, Segoe UI or Verdana; on Windows a name the canvas does not find, such as Arial Black) is measured in a fallback face, and a report made or redesigned through the core says so: `standInFamilies` asks the canvas for each face the report names twice, once with Courier New behind it and once with Times New Roman, and measures each letter, figure and stop of a sample alone: a character the face has measures alike both times, so a family counts as found when any one does, and one the canvas does not find measures every character differently; the result carries a notice and names the families under `fromFile.standInFonts`, since they are the report's text (GAP2-4). Compared as a whole line, as at first, an installed face lacking some of the sample's characters was named: a Code 39 barcode font, with no lowercase, whose "*12345*" measures in it exactly (the wave-1 review's FONTS-R2). The check is advice, so it never ends a job: a font's name is decoded by `lib/xmlEscape.ts`'s `unescapeXml`, which leaves `&#x110000;` as written where a decoder of `nodeFonts.ts`'s own threw on it and lost a report its AI had made, and `genJobs.ts` asks inside a guard that logs a failure and leaves the notice out (FONTS-R1). A runner that needs another family exact needs it installed.
- **The paper.** From the locale the server is given, never the operating system's: Node's `navigator.language` is the machine's, and with none given a report with nothing to say otherwise goes on Letter, DevExpress's own default. A redesign is worked out with the open report laid over the stored settings, as the workspace's `detectFor` lays it, so it is asked in the report's own version, unit and paper (the wave-7 review's W7R-2).
- **The model Gemini answers with.** Probed once a day for a key and kept in `model-choice.json` in Forma's folder by the key's 32-bit tag, never the key, through the same reader the browser keeps it in `localStorage` with (`keepModelChoiceIn` in `lib/modelCache.ts`); a model the server is told (`model`) is pinned and probes nothing (NODE-7).
- **The AI.** Handed in as the core's `ask`: geminiService's `analyzeReportDesign` by default; with `mock`, geminiService's own mock answer, the mock invoice, and mock mode's translation as the core's `translateTexts` (`mockTranslations`), so no request is made even where the words name a language (NODE-6, PROTO-8). Until the wave-7 review (W7R-1) the mock swapped `ask` alone, and a report asked "in French" went to a real AI to be translated, with whatever key or Local AI the settings held. The switch, the pinned model and the locale are read from the server's environment in `stdio.ts` alone, since wave 8 (`FORMA_MCP_MOCK`, `FORMA_MODEL`, `FORMA_LOCALE`). geminiService reads its mock switch from Vite's environment only, and no environment read was added to it.
- **What it keeps of the person.** Nothing: no memory, no kept reports, no report library, no shared database, no vision model or page reader on a Local AI server, no learning event, and no read of `localStorage` or `sessionStorage`, which Node 26 defines and throws on (TST-12; `nodeMakeReport.test.ts` and `nodeGeneration.test.ts` count every read).

**Forma's folder** (`formaUserFolder`) is the user's own and outside any repository and the user's project: `AppData\Local\Forma` on Windows, `Library/Caches/Forma` on macOS and `.cache/forma` elsewhere, under the user's home. It holds `tessdata/`, the gathered languages, and `model-choice.json`, and Forma's code writes nothing else outside the folders in effect. One more thing is written, by tsx, which runs the clone's TypeScript: its compile cache, the clone's own modules transformed, in the system's temp folder (`tsx-<user>`, under `%TEMP%` on Windows); nothing of the user's is in it. Until wave 10 this sentence said nothing else was written anywhere: its end-to-end probe, with the home and the temp folder scratch ones, found the cache, and `stdio.test.ts` now holds both, the AI tools writing nothing in the home but the languages and nothing in the temp folder but `tsx-` folders.

**The dependencies stay where they are.** @napi-rs/canvas, onnxruntime-node and tsx are devDependencies; the site's bundle and `npm start` never load them, and the server already runs from a clone after a full `npm ci`, which installs them (`package.json`, `comment:mcp`). onnxruntime-node's install script stays denied, costing it only the Linux CUDA binaries. `npm run fetch:paddle` is the step that gives Node the browser's English reading; without it Node reads with Tesseract, measurably worse on DevExpress prints ([app-shell.md](app-shell.md) — *PaddleOCR reads an English page*).

Steps that are the owner's, never a session's:

- **Registering the server in a host.** `claude mcp add` writes the owner's `~/.claude.json`; a session may do it only when the owner says so, in local scope, and never with a key unless the owner says so. A registered server with an AI set up spends that AI's quota on every `generate_report` and `revise_report` call, as `npm run bench:fidelity` does.
- **Allowing a tool without a prompt.** No tool of Forma's goes into `.claude/settings.json` unless the owner says so, and never one that spends quota. `npm run mcp` is already allowed through `npm run *`; it waits on stdin, so it is a long-lived process like the dev server.
- **Whether the server gets a release area of its own** (and its GitHub label, through `scripts/github-setup.mjs`) (DOC-12). The release note itself is written: 1.7.0's entry in `releases.ts` (2026-11-24) files the server under `site` meanwhile, and the deploy that publishes it is the owner's.
- **Publishing** the server as an npm package, which is a distribution decision, not made.
