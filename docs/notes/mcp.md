## What the server is, and why it is not generation server-side

Forma's MCP server is a program the user runs on their own computer, from a clone of the repository. Their AI host (Claude Code, Visual Studio 2022's Copilot, VS Code, Claude Desktop, any MCP client) starts it and talks to it over its stdin and stdout, and nothing else talks to it: it opens no port, has no hosted origin, and nothing of it is built into `dist/`, so the live site never runs it and a deploy never sends it. It was asked for in discussion #1 on GitHub; on 2026-10-28 the owner welcomed it for after the command line, and on 2026-11-23 chose it first, on one Node core that the command line reuses since 2026-11-24 (*The command line is a second entry beside the server*, below).

[`docs/PRD.md`](../PRD.md) section 6 rules out moving generation server-side, and the server does not break that rule, for the reason the rule exists. A server holding every user's key would be custodian of every user's third-party credential, the exposure section 5 records as resolved. This process is the user's own program, started by their own host on their own machine; it holds only that user's files and, for its two AI tools, that user's key, read from that process's own environment. No other user can reach it, because it has no listener: a server on 127.0.0.1 would be reachable by everyone signed in to the PC, which is what Forma Designer had to be guarded against (section 5). So a remote transport for it is out of scope too, and `boundaries.test.ts` refuses any listener in `src/mcp` and requires `serveStdio` in its entry (SEC-12).

Replacing the browser's direct call to the AI with MCP stays out of scope for the reasons section 6 gives. The server is the other direction: other programs calling Forma.

## The host runs one command, from a clone

The command is `node <clone>/src/mcp/run.mjs`, with the clone's full path, from any working folder. `run.mjs` is plain JavaScript that registers tsx's loader, resolved from the clone's own `node_modules`, and imports the entry, `stdio.ts`. It names the clone's own `tsconfig.json` for that loader, as both worker threads do, because tsx otherwise applies the one in the folder the host started it in, the user's project, whose `paths` reach every package Forma's sources import (each bare specifier, zod and the SDKs among them, whatever its `include` says; no relative import) and whose compiler settings reach those sources when that project's tsconfig takes the clone in, as a CI job's checkout inside it can (tsx 4.23.15 applies them only to the files a tsconfig includes; CLI-8 of the command line's design audit, `DevFiles/forma-audit/cli-designer-2026-11-24-findings.md`; `stdio.test.ts` starts the server from a folder whose `tsconfig.json` sends zod and @napi-rs/canvas, which the thread that answers and the AI tools' thread load on start, to a stub that throws; since the command line's wave 2 the report tools' thread names no package on start, so no `paths` reaches it, and the test's control says so; so no spawned case shows that thread ignoring the folder's `tsconfig.json`, and its pin, which matters there only for compiler settings, none of which breaks a module on its way today, is held by `boundaries.test.ts` alone, as the wave-2 review's EQ-1 found). Three forms came before it, and each failed:

- **The tsx CLI** (`node <clone>/node_modules/tsx/dist/cli.mjs <clone>/src/mcp/stdio.ts`), the first form documented, runs two processes: the CLI spawns the server as a child and listens on a named pipe for its own messages, parsing each frame unguarded. The process the host started had opened a listener, and one malformed frame from any process of the same Windows user ended it (PS-8, measured in the wave-3 review). Registered as `run.mjs` does it, tsx opens no listener; `stdio.test.ts` checks that the process it spawned is the server itself.
- **`npm run -s mcp`.** `npm run mcp` writes npm's banner to stdout, where only protocol messages may go (DOC-2), which is why the plan moved to `-s`, and `-s` does remove the banner. It still failed: a host starts the server in the user's project, so npm runs the `mcp` script of the nearest `package.json`, the user's own (PS-9), and on Windows npm is `npm.cmd`, which a host cannot spawn without `cmd /c` (T5). `npm run mcp` stays as a developer's command in the clone, never a host's.
- **`npx tsx`.** Outside the clone it fetches an unpinned tsx, because npx assumes yes when stdin is not a terminal.

**There is no bundle.** The design had `npm run build:mcp` writing `dist/forma-mcp.mjs`, and the audit found three things wrong with it (PROTO-2, DOC-1, TST-1): esbuild could not bundle the pipeline as `build-server.mjs` bundles `server.ts`, Firebase Hosting publishes everything in `dist/` on both sites, where the file would also break `check:size`, and every `npm run build` empties `dist/` first. So the server runs from the clone through tsx, and tsx is a devDependency: the clone needs a full `npm ci`, and `npm ci --omit=dev` leaves a server that cannot start. `package.json`'s `comment:mcp` says why its two dependencies, `@modelcontextprotocol/server` 2.4.0 and zod 4, are pinned exactly and why the v1 SDK already in the tree is not used.

The command is restated in every copy the Facts table of `CLAUDE.md` lists for it: `run.mjs`, `stdio.ts`, `CLAUDE.md`, `README.md`, the Docs page, `/self-host`, the PRD (§2.5, §3 and §6), `SECURITY.md`, `CONTRIBUTING.md` and this note. `stdio.test.ts` spawns exactly it, from a folder outside the clone, so the code side is held; `publicClaims.test.ts` holds the Docs article, the README section and `/self-host` to it and refuses an npm or npx form there; the PRD, `SECURITY.md`, `CONTRIBUTING.md`, `CLAUDE.md` and this note are kept by hand.

## stdout is the protocol, and nothing else writes there

On stdio the spec says a server must not write anything to stdout that is not an MCP message, and Forma's pipeline was written for a browser, where logging is free. `geminiService.ts` calls `console.log`, `console.info` and `console.debug` on every generation, Node sends all three to stdout, and Tesseract.js's workers reach the parent through `process.stdout.write` (PROTO-1). One stray line between two messages and the host drops the connection.

So the entry's first act, before anything else is loaded, is `installStdoutGuard` (`stdoutGuard.ts`): its only static import is the guard, and everything else is imported dynamically after it, because static imports run before the body. The real stdout is kept for one Writable, `protocolOut`, which only the SDK's transport is given. Every other write, every console method and stdout's `end` go to stderr, with any key taken out on the way (a host keeps a server's stderr in its logs, Claude Desktop in `mcp-server-<name>.log`). An unhandled rejection is logged and the server keeps serving, since Node 24 would otherwise exit and Claude Code marks an exited stdio server failed until someone presses Reconnect; an uncaught exception is logged and the process exits non-zero, because Node's own docs say a process is not safe to resume after one.

What the guard cannot cover was measured in the wave-3 review (PS-7): a synchronous write to file descriptor 1, a child process that inherits this one's stdout (spawned with its stdio inherited, or forked), and `process.stdout.end(chunk)`, whose last chunk goes through the stream's internal write rather than the property the guard replaced. The last is now covered; the first two are refused by `boundaries.test.ts` in `src/mcp` and in every module it can load. `stdio.test.ts` spawns the server with a test-only switch that writes through every route the guard covers, keys included, and reads stdout line by line for anything that is not JSON-RPC.

Start-up is kept light for a related reason (PROTO-10): no pipeline module is imported on the thread that answers the host at all, since the report tools' work runs in a worker thread that loads each module when a job first needs it (the section on that thread, below), so the server answers its first request in well under a second. Claude Code's docs say it may skip asking a stdio server for the newer protocol for seven days, for example after the server exits when asked.

## Both protocol eras, from one factory

MCP's revision of 2026-07-28 broke with the 2025 revisions: no initialize handshake, `server/discover` instead, and capabilities in each request's envelope. Hosts are on both. `serveStdio`, from the SDK's v2 package, serves both from one factory, `createFormaServer`, which it may call more than once for a connection, so the factory registers everything and keeps no state beyond its own connection.

**The era is the connection's, never the request's** (PS-1). The first version read it from each request's envelope, and a 2025-era client that put the 2026-07-28 keys in its `_meta` was then treated as modern: `forma_status` misreported it, and the server asked for its roots in a way the SDK's legacy shim either refuses or turns into a `roots/list` with no timeout. `eraOf` (`toolShape.ts`) reads the revision the connection negotiated.

**The tool list never changes after start-up**, and the server says so (`tools.listChanged: false`): Visual Studio resets every approval a person gave to a server's tools when the server says its list changed (GAP3-5), so a tool switched on or off later would cost every approval. The two tools that need an AI are listed always and refuse without one, rather than appear once one is set up.

## The folders a tool may use

A tool reads and writes the user's files only inside the folders in effect (the server's own cache in Forma's folder aside, and tsx's in the temp folder: *What Node makes a report with*, below, its paragraph on Forma's folder), taken in this order, the first that answers winning (`roots.ts`):

1. `FORMA_MCP_ROOTS`, full paths separated by `;` on Windows and `:` elsewhere, set in the server's entry in the host. While it is set it is the only source, so a mistake in it refuses every file tool in words that name the entry, rather than falling through to a folder nobody chose.
2. The client's roots, when the client declared that it has them. Claude Code's docs say it answers with the folder it was started in and every `--add-dir` folder; other hosts may answer with the open solution or workspace. Whether Claude Code's newer runtime answers the 2026-07-28 form of the question on a plain tool call is not yet measured, which is one reason the third source stays.
3. `CLAUDE_PROJECT_DIR`, which Claude Code sets for the servers it starts.
4. None: every file tool refuses, and the message gives each host's recipe (`noRootMessage`), which `forma_status` also returns.

The design had only the first and third, and the audit found that only Claude Code would then have a folder (GAP3-1): Visual Studio 2022, VS Code and Claude Desktop set no `CLAUDE_PROJECT_DIR`, and Visual Studio documents no variable for the open solution. Roots are deprecated in the 2026-07-28 revision, with the twelve months the spec keeps a deprecated feature, and they are the one source those hosts may send; VS Code's default Copilot harness does not promise them, so its recipe sets `FORMA_MCP_ROOTS`.

**Asking for roots is gated by hand, because the SDK does not gate it the same way in both eras** (GAP3-2, measured). On a 2025-era connection the SDK sent `roots/list` to a client that had declared no roots, and a client that never answers then holds the tool call for the SDK's 60-second default. On a 2026-07-28 request, asking a client that did not declare roots fails the whole call (-32021), and `getClientCapabilities()` is undefined there, so the request's own envelope has to be read. So a 2025-era connection is asked only when its initialize capabilities name roots, with a 5-second timeout, and the answer (or the failure) is kept until the client says its list changed; calls made in parallel share the one request, since Claude Code runs read-only tools side by side and each used to send its own and wait its own 5 seconds (PS-10). A 2026-07-28 client is asked through an `input_required` result only when its envelope declares roots. A failure to list never fails the tool; it moves on to `CLAUDE_PROJECT_DIR`.

**Some folders are refused as roots, whatever their source.** A whole drive; the home folder or any folder holding it, such as `C:\Users` or `/home` (PS-3: only the home folder itself was refused at first, so `C:\Users` let a tool reach every profile); a dot-folder such as `.git`, `.claude` or `~/.ssh`, and any folder inside `.git`, `.ssh`, `.gnupg` or `node_modules` (PS-4: the rule that keeps tools out of dot-folders only looks below a root, so a root that was one switched it off). A folder further inside another dot-folder is kept, so a Claude Code worktree under `.claude/worktrees` works, with its own `.git` and `.claude` still refused below it. A client's root is converted from its `file:` URI with `fileURLToPath`, never by slicing the string: building it from `new URL(u).pathname` gives `X:\C:\...` on Windows, a reported host bug.

**Each root is held twice** (PS-2): as the host or the user spelled it, and as it really is once links are followed. Comparing a path as spelled against the root's real path refused every path spelled the user's way under a junction, a subst drive or an 8.3 name.

## Full paths only, judged before the disk is touched

A path argument must be fully qualified: `G:\Reports\invoice.repx` on Windows, `/home/me/reports/invoice.repx` elsewhere (`paths.ts`). Nothing is resolved against a root, the server's working folder or the home folder, because an MCP server cannot see the shell its host's model ran `cd` in (GAP2-1): a relative name resolved against `CLAUDE_PROJECT_DIR`, as Claude Code's docs suggest, opens a different file of the same name at the root, and a repair then writes its output beside the wrong file with no error. The forms a model on Windows actually writes were measured in the audit: `path.win32.isAbsolute('/g/DevFiles/x.repx')` is true while resolving it gives `G:\g\DevFiles\x.repx`, `/c/Users/...` lands on the current drive, `~/x.repx` becomes a folder literally named `~`, and `G:x.repx` is relative to the drive's current folder. Each is refused, and where the intended path can be worked out (a Git Bash `/g/...` path, a `file:` URL, `~`) the refusal hands it back, never acts on it (GAP2-3). This departs from Claude Code's own Read tool, which accepts all of them, on purpose.

The order of the checks is the security of it:

1. **The string, raw, with no file-system call.** A UNC path in any spelling (`\\host\share`, `//host/share`, the mixed `/\host`, and the Git Bash slip `//g/...`, all UNC to Windows) is refused here (GAP2-2), because a realpath of one opens an SMB connection, which sends the Windows sign-in to answer it. So are device names, a `:` after the drive letter (an alternate data stream) and a name ending in a space or a dot. A path on a drive in Windows' long or device form (`\\?\C:\...`, `\\.\C:\...`, which tools print for long names) is refused here too, with the plain path handed back; until the CLI work's wave-2 review (SEC-W2-6) it was refused as a path on another computer, which it is not.
2. **A lexical check against the roots**, so a path spelled outside them never reaches the file system. `paths.test.ts` proves it with a file system that records every call (T1: the first version had one that threw when touched, inside checks that catch what throws, so the test could not fail).
3. **Every existing component lstat'd from the drive down**, which never follows the component itself. A link's target is read as written and refused when it names another computer, never followed to find out (PS-6): a directory symlink to a share, which a cloned repository or an extracted archive can carry, would otherwise be followed by the first lstat below it.
4. **`realpathSync.native`** on the nearest existing ancestor, and the result checked against the roots' real paths. The extension is judged again on the real path, so a link named `x.repx` leading to any other file is refused (PS-5). A hard link is a file in its folder by the file system's own meaning and is read as one: making one takes access to the file already, and refusing every file with a second name would refuse what backups hold. That is out of these checks' scope, and `paths.ts` says so.

A tool never reads from or writes into a dot-folder or a dot-file, never writes into `node_modules`, and never opens a file named as credentials (the patterns `.gitignore` keeps out, and `.env*`, `.mcp.json` and `firebase-applet-config.json`; since the wave-8 review, W8C-5, the files a .NET project keeps its connection strings in, `appsettings*.json` and `local.settings.json`, and a `connections*.txt`, which `generate_report` would otherwise send to the AI as data; since the CLI and Forma Designer work's wave-7 review, W7-MCP-2, a `connections*.tsv`, the name of Forma Designer's own store, `%LOCALAPPDATA%\Forma\connections.tsv`, each line a connection's server and its encrypted sign-in, which a root covering that folder or a copy in a project would have sent to the AI as a data file, where Forma Designer's verbs never print either). It reads at most 20 MB, the web app's own limit for one file. A file is never replaced unless the call asks (only `repx_edit` can), and that holds at the moment of writing, not only when it was checked: the bytes go to a temporary file, which is then hard-linked to its name, since a link fails when the name exists where a rename would silently replace it, on Windows too.

Every function takes the platform's path module and the file-system calls it may make, so the Windows rules run on CI's Linux runners as well as here (TST-4), and the roots themselves pass the same full-path test before any file-system call.

**The command line's mode** (since 2026-11-24, the CLI and Forma Designer work's wave 2; findings CLI-3 and SEC-4 of its design audit, `DevFiles/forma-audit/cli-designer-2026-11-24-findings.md`). The same functions judge the paths of the command line, which that work's wave 4 built on them, so its rules stay one copy: it hands `paths.ts` its working folder where the server hands its roots (`PathScope`). A person or a CI step sees the folder the command runs in, so a relative path is resolved against it once, before anything else; every other form above is refused as it is for a model, in a person's words ("give" where a model is told "send", "Forma" where it is told "this server"), and every step after the string runs unchanged. The working folder passes the same tests first: one named by a UNC path, or reached through a link to another computer, refuses every path. A mapped network drive is not told apart: its letter is the person's own mapping, so a working folder or a path on `Z:\` is used as any drive is, over the share the person mapped (the wave-2 review's SEC-W2-5; refusing one would take asking Windows for the drive's type, the owner's call). There are no roots, and the named files' folders are not made into a list of them. Each path has one folder it must really be in, decided by where it really is, never by how it was spelled (SEC-W2-2: until the review a path spelled through another name for the working folder, a junction or symlink to it, a subst drive, an 8.3 name, or the shell's logical `$PWD` against Node's physical working folder, was judged as named outside it, and a link the checkout carried out of it was followed). No link that really is in the working folder (its own folder's real path, and its name) may lead out of it, so a directory link a checkout carries out (SEC-1's way to send a CI runner's files to the AI) is refused, and so is a file link; a path whose folder is really in it must land in it; and a path whose folder is elsewhere must land in that folder, since a person may name any file on their own computer, but a file link planted beside it is refused too. A directory link on the way to a folder elsewhere is followed as the person's own, and so, by design, is one in a folder above the working folder that a command run in a subfolder reaches by `..`. A list of the named folders could catch none of these, since the link sits in the named folder's own path, and one named folder's link could reach another's. Dot-folders and `node_modules` are looked for below the working folder, for a path that lands in it, or below the drive otherwise, so only the folder the command runs in may itself be one: the person chose it.

**What a write does with a taken name is the caller's** (`IfExists`, CLI-6): the server writes beside it as `<name> (2).ext`, since no person can be asked; the command line refuses, saying `exists` and writing nothing, so a rerun in CI never piles up copies and a resume can skip what was made, or to replace when the person says so. Whether the name is taken is decided at the write, by the hard link failing, never by a look beforehand, so a file that appears after its path was judged is found then and kept. A replace links first too, so it says `written` only when the name was free; until that wave it looked first and renamed after, and a file that appeared between the two was replaced under a `written`.

## What a tool returns

Every tool goes through `defineTool` (`toolShape.ts`), so each rule holds for all of them rather than for the ones someone remembered:

- **All four hints are set.** The spec's defaults are destructive and open-world, so a tool that set only `readOnlyHint` would advertise itself as both. Claude Code runs `readOnlyHint` tools in parallel, so a read-only tool keeps no shared state. `repx_audit` and `repx_outline` are read-only and idempotent; `repx_repair` and `repx_pdf` write a new file and never replace one, so a repeat finds the same bytes and says `unchanged`, which makes them idempotent and not destructive (PROTO-6); `repx_edit` can replace a file when asked and an `add` made twice adds two labels, so it is destructive and not idempotent (GAP3-5).
- **The result is a file and a summary, never the XML or the PDF** (PROTO-5). The text stays under 40,000 characters, below the 50,000 at which Claude Code saves a result to a file instead of showing it.
- **The same data twice**: `structuredContent` for the hosts that read it, and the same JSON in the text under a one-line summary, because a host on an older revision may hand its model only the text (GAP3-5: the SDK sends structured content to every revision, and nothing promises the model sees it).
- **Text read from a file is data.** A report made by someone else controls its strings, and the host's model may have a shell. Such text is returned only under `fromFile`, each string clipped and its whitespace folded, with a note beside it that it is data, never instructions; never in a summary, a description or an error (SEC-6).
- **Errors are results, in plain words**, keys taken out, under 2,000 characters; a refusal is written for the model and says what to do instead. Any other error's message goes to stderr only, and the result says an internal error stopped the tool (the wave-4 review's REV4-2): a library's message can quote the file it was reading, as a regular expression built from a report's `Ref` once quoted the report, so it was a way around `fromFile`.

`toolList.ts` is the list in its order, each tool's name, whether it is read-only, whether it needs an AI and, since the CLI and Forma Designer work's wave 7 (MCP-1 of its design audit), whether it is open-world, as a pure module with no SDK import, so a test of the pages can read it without starting a server (DOC-5). `formaServer.test.ts` holds the registered tools and their hints to it, every name in the instructions too, and `publicClaims.test.ts` holds every name, and which need an AI, to the Docs page's article and the README. The open-world hint was pinned to `needsAi` until then, which left a tool that reaches a SQL Server through Forma Designer and calls no AI no honest hint; it is the list's own field now, true for the two AI tools and for `repx_edit` and `repx_convert`, which take `connection`, and false for `database_connections`, whose list Forma Designer reads from a file on this computer. **The instructions are budgeted**: the audit found 21 of their 1,500 characters to spare, and wave 7 named its two tools and the layout script by saying the other lines in fewer words, keeping the cap, since a host loads that text into every session that has the server; 10 are left.

**A refusal can carry text from a file** (the same wave, D1-10). A refusal about a layout's names (a pinned query the layout lacks, sample rows of another database) or SQL Server's words through Forma Designer names none of it in its words, which are the server's: `ToolRefusal`'s `fromFile` (`caller.ts`) carries it, across a worker thread's boundary too (`jobFailure`, the pools), and `errorResult` gives it as a result gives its own, keys out before the clip, under `FROM_FILE_NOTE`, in the text alone, within the error's 2,000 characters or left out and said so. Never as structured content: the wave's implementer gave it there too, and the review (W7-MCP-1) ran the host command through the TypeScript SDK's own client, whose `callTool` checks structured content against the tool's output schema on an error as on a result, as the spec says it must match; `{ fromFile, fromFileNote }` lacked every field the schema requires, so each such refusal reached that client as a protocol error, `-32602`, and its words, with the next step they give, never reached the model. An error result carries no structured content at all now, and the tests' clients hold that of every error. Only the server's voice makes one; a person at the command line reads such a refusal whole, as before.

## The report tools run the web app's own modules

`repx_audit`, `repx_outline`, `repx_repair`, `repx_edit` and `repx_pdf` (2026-11-24, the fourth wave) each run the module the web app runs, so a fix there reaches both: `auditRepx`, the chat's `reportOutline`, `repairRepx` in `REPAIR_ORDER`, the chat's `applyEdits`, and the draft PDF that `scripts/repx.ts` drew, moved to `src/lib/draftPdf.ts` so the script and the tool share it. The chat's edit words and its list of edits moved into `src/lib/editLanguage.ts` for the same reason: the chat's prompt interpolates them, and its text was compared byte for byte before and after the move. `repx_edit` takes every edit the chat makes, and its schema is checked by `tsc` against the chat's own type, so an edit field added there fails to compile until the tool has it; until the CLI and Forma Designer work's wave 7 it left out `data`, which needed a database layout the server did not hold, and since then it makes it with one a call gives (*The server's database arguments, and the person's two switches*, below). `forma_status` says what the server is and which folders are in effect.

What reading a report means here, in `reportFile.ts`:

## A report costs one call, never the server

The report tools read files someone else made, with modules written for a report a person is looking at in a browser tab. The wave-4 review (REV4-3) measured what that cost on one thread: a well-formed 1.3 MB report of 12,000 overlapping labels ran the server out of memory, and the process ended with every tool in it, so the host lost Forma until someone reconnected; malformed files of a few kilobytes held the thread for minutes, while no other request was answered, `forma_status` included, and a cancellation changed nothing. The 20 MB limit on a file bounds neither.

So a tool's work runs in a worker thread (`workerPool.ts`, which starts `worker.mjs`, which runs `pipeline.ts`), and the thread that answers the host only judges paths, reads and writes files and shapes results:

- **Bounds**: 512 MB of heap, a 4 MB stack and 30 seconds a call (`PIPELINE_LIMITS`). Passing one, or the call's cancellation, ends that worker, and the call gets a refusal in plain words (or the wrapper's "Stopped"); nothing is written, and the server goes on. The reviewer's 12,000 labels now get the memory refusal in about four seconds, with `forma_status` answered meanwhile; the malformed files are refused by the shape check before any pattern runs.
- **One worker kept idle**, unref'd so it never holds the process open; calls made at once each get their own, since Claude Code runs read-only tools side by side. A worker that failed in a way that is not a refusal is ended, never reused.
- **The worker's stdout and stderr are its own** (`stdout: true`, `stderr: true`), read by the pool and sent to the server's log on stderr: otherwise Node pipes a worker's stdout into the process's own, where only protocol messages may go. `boundaries.test.ts` refuses a `Worker` started without that.
- **tsx again**: a new thread starts with none of its parent's loaders, so `worker.mjs` is plain JavaScript that registers tsx itself, as `run.mjs` does; `stdio.test.ts` runs the report tools through the real launcher and its worker.
- **Where it is measured**: v8 coverage does not follow a worker, so `pipeline.ts`'s jobs also run in the tests' own thread (`inThread` in `testClient.ts`); `reportTools.test.ts` runs every tool through the real worker too, and holds the deadline, the memory limit and the cancellation with workers of its own that never answer or never stop allocating.

## The command line in CI

Since the CLI and Forma Designer work's wave 7 (2026-11-25; findings SEC-3, SEC-8, LEGAL-1, CLI-8, GAP1-2 and GAP2-5 of its design audit) the README and the Docs page give a GitHub Actions recipe, the use Pedro asked for (point 3 of discussion #1: "a CLI over the same pipeline, for batch migrations and CI"). Each line of it is a decision:

- **Forma at a release tag, in a dot-folder of the checkout** (`actions/checkout` with `repository`, `ref` and `path: .forma`, then `npm ci` there). A tag, so a run never changes under the person. The Docs page's copy names the release the page ships in, and `publicClaims.test.ts` holds its `ref` to `package.json`'s version, as it holds the Docs page's clone line, so the release wave that raises the version moves it with it. The README's names none, only `<tag>`, which its words explain (a release that has the command line; the first is the one the changelog lists it under): the README is published with every push to `main`, before the owner deploys and tags, and its first copy named `v1.7.0`, a tag that did not exist, while the newest that did, v1.6.5, has no command line (the wave-7 review's W7R-2); the test holds that copy to `<tag>`. A dot-folder, because the batch walk leaves dot-folders out, so Forma's own fixtures are never taken for the person's reports. The checkout puts the clone inside a project that may have a `tsconfig.json` of its own, whose `paths` or compiler settings would reach Forma's sources through tsx; every launcher names the clone's own (CLI-8, *The host runs one command, from a clone*, above).
- **A check every pull request runs, with no secret** (GAP1-2). A fork's pull request is given none, and `audit`, `repair`, `convert`, `pdf`, `outline` and `bind` never look at the AI's settings, so the job gates the reports anyone proposes: `audit reports`, the reports committed directly in that folder, since `audit` reads no subfolder (a folder of its own is a step of its own), and skipped by `hashFiles` when the folder holds none, since `audit` refuses a missing or empty folder, exit 4, which would fail every pull request of a repository that commits no reports (the wave-7 review's W7R-1: the first recipe audited the batch's output folder, which a pull request, making nothing, found missing wherever no reports were committed there).
- **The key in one step, on a push, never `pull_request_target`** (SEC-3). The key goes from the repository's secrets into that step's `env`, never onto the command line, where a log or a process list shows it, and the step runs on `push` alone (`github.event_name == 'push'`, an equality, so a trigger added later is not let in; the first words also offered `workflow_dispatch`, which the recipe neither declares nor lets through, W7R-5). `pull_request_target` runs with the repository's secrets on the base's workflow, and a job that checks out the fork's changes there hands them the key.
- **What a push makes is the run's artifact** (W7R-1). A hosted runner starts empty and is gone when the job ends, so the batch writes into a folder of its own that `actions/upload-artifact` keeps, under `!cancelled()`, so a batch step that failed (stopped at a limit, or ended with a file that failed, exit 4 after the rest were made) still keeps what it made; the first recipe kept nothing. For the same reason `--skip-existing` resumes nothing there, the next run making every file again and spending the quota again, so the recipe leaves it out, and the words say it carries on only where the reports are still there: a folder they are committed to, or a runner of the person's own.
- **Held as YAML** (W7R-3). `publicClaims.test.ts` reads each copy's YAML block on its own, by its structure, its keys and steps by their indentation (no YAML parser is a dependency of Forma's, and the two in the tree come only through firebase-tools), never the prose around it, which names `pull_request_target` to forbid it: the triggers exactly `pull_request` and `push`, in the block form, with `pull_request_target` and `workflow_run` nowhere in it; every step that names a secret or a `FORMA_` variable guarded by the push equality; the key from a secret into that step's `env`, on no `run:` line; each `--out` a batch writes uploaded under `!cancelled()`; and each `audit` guarded by `hashFiles` on its folder. Until the review the case looked for a `pull_request_target:` key alone, and the reviewer's mutation, `on: [push, pull_request_target]` with the push guard dropped, passed it.
- **The runner is the CI provider's computer** (SEC-8, LEGAL-1). Every page said the server runs "on your computer", and the key is kept "in your assistant's settings file or your own environment", both still true of the server; on a hosted runner the files and the key are on the provider's machine for the job, under its terms. So the privacy policy has a section of its own for the command line (`legalDisclosure.test.ts` holds it while a command asks the AI), the PRD's §6 says why a CI runner is still not generation server-side, and the server's sentences stay as they were.
- **The exit code is the gate**, 1 on audit errors, 4 on an input that failed, 5 at an AI's limit; a step that wraps the command in a shell `exec`s it, so the SIGINT a cancel sends reaches node (*What the command line prints, and how it ends*, above). The batch comes before the audit and the audit runs under `!cancelled()`, so on a push a batch stopped at a limit still has the committed reports checked.
- **Fonts on a Linux runner** (GAP2-5). Arial, Times New Roman, Courier New, Calibri and Cambria measure in the metric-compatible faces `nodeFonts.ts` registers where the runner lacks them (*What Node makes a report with*, below); any other family is measured in a stand-in, which the result names, so a person installs that family on the runner when it matters. The README and the Docs say both.

The recipe follows GitHub's documentation and has not been run as written in a workflow; `commandLine.test.ts` spawns the exact command from a folder outside the clone on CI's Linux runners, which is the nearest run there is.

## The server's database arguments, and the person's two switches

## What Node makes a report with

**`make` must never run on the thread that answers the protocol.** pdf.js parses and draws a PDF on the thread that calls it, and nothing bounds what a small PDF asks of it. The wave-7 review (NODE7-PDF-HEAP, each case in a process of its own from an empty folder) measured a 611 KB one-page PDF whose one stream holds 20,971,520 `cm` operators ending the process in about 67 seconds, V8's heap out of memory (exit 134, beyond the stdout guard's handlers), a 1 MB PDF inflating to 1 GB taking 42 seconds at 2.4 GB with the event loop stalled up to 13.8 seconds at a time, and eight pages of it still running at the 180-second deadline. On the protocol thread one such attachment stops the server answering every client, cancellation included, or ends it. The same PDF in a `worker_threads` worker with `resourceLimits: { maxOldGenerationSizeMb: 512 }` ended that worker out of memory after 31 seconds with the host alive at 484 MB, so the AI tools run `make` in such a worker, with 2 GB of heap and a deadline sized for a generation, 15 minutes (`GEN_LIMITS` in `generator.ts`), not `workerPool.ts`'s 30 seconds; `resourceLimits` bounds V8's heap alone, not ArrayBuffers or native memory, which is why the deadline and the picture budget below stand beside it. A stop reaches the intake: `makeReport` hands the request's signal to `ingestFile`, which takes no file in once stopped, stops a PDF between its pages and destroys its document (`withNodePdf`), but cannot interrupt pdf.js inside a step.

What it reads with, and where that differs from the browser:

- **Files.** `lib/repxIntake.ts` draws on what it is handed (`Drawing`): the browser's OffscreenCanvas and DOM in `lib/browserIntake.ts`, moved there unchanged, and @napi-rs/canvas in `nodeIntake.ts`, so straightening a scan, the `MAX_IMAGE_EDGE` downscale and the redraw of a type the AI does not take are one piece of code (NODE-2), and a fix to one is a fix to both: wave 10's parity gate found the straightening laying a straight form on its side, in Node and in the browser alike (`lib/deskew.ts`, [app-shell.md](app-shell.md) — *Foreign reports, templates and crooked pages at intake*). A PDF is opened with pdf.js's legacy build, its worker given as a file URL and run in the same thread, and the standard fonts, character maps, colour profiles and wasm decoders taken from the installed pdfjs-dist, so a PDF that names Helvetica without embedding it still draws. A File built from a path is typed by its extension, as a browser types a dropped one. `checkRepx` reads a report itself where there is no DOM (`readXml` in `lib/repx.ts`), where every `.repx` was told "This XML could not be checked." A picture is decoded only when its header (PNG, JPEG, GIF, WebP or BMP) names a size within `MAX_PICTURE_PIXELS`, 100 million, and its pixels are let go once it is drawn: the review measured a 257 KB PNG 46,000 pixels square costing 2.1 GB to decode, and two 40,000-pixel ones taken in one after the other peaking at 3.2 GB, native memory no heap limit bounds (NODE7-PICTURE-MEMORY). One past it, or of another kind, goes as it came where the AI takes its type and is told where it had to be drawn, and OCR does not read it; a 48-megapixel photograph and an A3 page scanned at 600 dpi are inside it.
- **OCR.** The browser's rule, in one place for both (`lib/ocrRead.ts`): English by PaddleOCR when `vendor/paddle` holds the three pinned models, each checked by SHA-256 against `scripts/fetch-paddle.mjs`'s pins, through onnxruntime-node (`nodePaddle.ts`, the reader the measuring scripts now share); by Tesseract otherwise, and for a page outside PaddleOCR's script; then the page's own language (NODE-5, owner decision OD2 as revised). Tesseract's languages come from the installed `@tesseract.js-data` packages, which the lockfile pins, gathered into Forma's folder, each checked against the installed file before a worker starts: no fetch step and never a CDN (NODE-10, TST-7). Every worker starts with `cacheMethod: 'none'`, so the working folder is neither read for a `./eng.traineddata` nor written to (SEC-2), and with `errorHandler`, so a damaged picture or a missing language rejects its reading instead of ending the process (NODE-1); it is handed PNG bytes only. The languages are gathered when the parts are assembled, so a package missing or a Forma folder that cannot be written is an error then, naming it; gathered only at the first reading, as they were, every page went without its text and the report was made on the path NODE-3 forbids, with one line on stderr (the wave-7 review's NODE7-OCR-QUIET). A page OCR still cannot read is said in the result's notices ("OCR could not read the text of ..., so the AI was sent its picture alone"), never in the log alone. One worker reads at a time; a reading stopped ends it, asks nothing more of it (it checks it was not stopped before each recognition, since one asked of the worker being ended was an unhandled rejection inside tesseract.js, NODE7-ABORT-UNHANDLED), and an idle one ends after a minute on a timer that never holds the process open. Its output reaches the parent through `process.stdout`, which the guard sends to stderr; Tesseract's own native messages go to stderr already. Where it differs: PaddleOCR's picture is enlarged as the measuring scripts enlarge it (`resizeRgb`), where the browser's canvas smooths it; no handwriting is read; and the text sent with the request still says it was read "in the browser" (`layoutText`), a prompt the browser shares.

- **What it keeps of the person.** Nothing: no memory, no kept reports, no report library, no shared database, no vision model or page reader on a Local AI server, no learning event, and no read of `localStorage` or `sessionStorage`, which Node 26 defines and throws on (TST-12; `nodeMakeReport.test.ts` and `nodeGeneration.test.ts` count every read).

**Forma's folder** (`formaUserFolder`) is the user's own and outside any repository and the user's project: `AppData\Local\Forma` on Windows, `Library/Caches/Forma` on macOS and `.cache/forma` elsewhere, under the user's home. It holds `tessdata/`, the gathered languages, `model-choice.json` and, once a limit has parked a model, `model-parks.json`, and Forma's code writes nothing else outside the folders in effect. One more thing is written, by tsx, which runs the clone's TypeScript: its compile cache, the clone's own modules transformed, in the system's temp folder (`tsx-<user>`, under `%TEMP%` on Windows); nothing of the user's is in it. Until wave 10 this sentence said nothing else was written anywhere: its end-to-end probe, with the home and the temp folder scratch ones, found the cache, and `stdio.test.ts` now holds both, the AI tools writing nothing in the home but the languages and nothing in the temp folder but `tsx-` folders.

**The dependencies stay where they are.** @napi-rs/canvas, onnxruntime-node and tsx are devDependencies; the site's bundle and `npm start` never load them, and the server already runs from a clone after a full `npm ci`, which installs them (`package.json`, `comment:mcp`). onnxruntime-node's install script stays denied, costing it only the Linux CUDA binaries. `npm run fetch:paddle` is the step that gives Node the browser's English reading; without it Node reads with Tesseract, measurably worse on DevExpress prints ([app-shell.md](app-shell.md) — *PaddleOCR reads an English page*).

Steps that are the owner's, never a session's:

- **Registering the server in a host.** `claude mcp add` writes the owner's `~/.claude.json`; a session may do it only when the owner says so, in local scope, and never with a key unless the owner says so. A registered server with an AI set up spends that AI's quota on every `generate_report` and `revise_report` call, as `npm run bench:fidelity` does.
- **Allowing a tool without a prompt.** No tool of Forma's goes into `.claude/settings.json` unless the owner says so, and never one that spends quota. `npm run mcp` is already allowed through `npm run *`; it waits on stdin, so it is a long-lived process like the dev server.
