## Persistence: two divergent shapes

| | Signed in | Signed out |
|---|---|---|
| Store | Firestore `users/{uid}/reports/{reportId}` | IndexedDB `forma-projects` (`lib/projectStore.ts`; `localStorage['savedReports']` until 2026-11-11, and still where IndexedDB is missing) |
| `timestamp` | `number` (epoch ms) | ISO string |
| `messages` / `result` | JSON **strings** | live objects |

**Signed-out projects live in IndexedDB (2026-11-11, the full audit's PR-15, batch BW2).** They were one JSON string under `savedReports`, five megabytes for the whole site and synchronous: four projects with pictures filled it, and every autosave rewrote every project on the main thread. `forma-projects` has two stores: `projects`, one record per project under its id, and `order`, the list's order as one array of ids under `ids`. App asks `projectStore.ts` for operations, never lists (a project put at the top or where it was, projects deleted, the device's list read), and each runs in **one transaction that reads the stored order and writes the new one**, so two saves close together, or two tabs, cannot write back a list missing the other's project, which rewriting the whole list could. A failed transaction (the browser out of room) is rolled back whole, so a failed save never costs the projects already kept. The first read moves the old `savedReports` list in, adding what the store lacks, and removes the key once it is stored; where IndexedDB is missing or refuses (some private windows), the same operations run on the `localStorage` list as before. A sign-out does not delete the store: these are the signed-out person's own projects, as the list was, and the privacy policy names it (`legalDisclosure.test.ts` holds the name).

That divergence is *on disk only*. The `onSnapshot` handler converts back on read — `timestamp` to an ISO string, `messages`/`result` through `JSON.parse` — so the in-memory `SavedReport` shape is identical on both paths and `handleLoadReport` needs no branch.

`firestore.rules` enforces the flat-string cloud shape (`isValidSavedReport` requires exactly `id, name, timestamp:number, messages:string, result:string, userId == auth.uid`). It uses `hasOnly` as well as `hasAll`, so **any new field written by `persistProject` must be added there or the write is rejected** — the earlier `keys().size() >= 6` accepted arbitrary extra fields and no longer does. `timestamp` is additionally bounded to `> 0 && < 4102444800000`, so a modified client cannot write a far-future value that permanently pins one report to the top of the list. Reads convert back in the `onSnapshot` handler.

**A cloud save is size-budgeted, and it degrades rather than failing.** The transcript carries the user's uploads inline as base64 data URLs, and one alone can dwarf an entire Firestore document — measured, a detailed 2048px photo at the intake's own JPEG quality is ~4.7 MB against Firestore's 1 MiB ceiling. Writing it produced an opaque backend rejection and the save simply failed. `persistProject` (`handleSaveReport` until 2026-11-05) now checks `messages` + `result` against **`CLOUD_SAVE_BUDGET_BYTES` (900_000)** — deliberately under 1 MiB, since the limit counts the encoded document, not the JSON string length this approximates it with — and:

1. over budget → re-serialise with `images` stripped from every message, and set `imagesDropped`;
2. still over budget → don't write at all; tell the user the project is too large to sync and that saving while signed out keeps it on this device.

Those two steps are `cloudPayload` in `App.tsx` since 2026-11-06, shared by the save and the title menu's **Duplicate**, which writes the open session as a new project the same way (a new id, "Copy of …", where a save would keep it). The copy carries the conversation and the report, not the original's revisions, which stay with the original's id.

A saved report without its source thumbnails still reopens and still exports, so keeping the spec, layout and REPX is strictly better than losing the save. The signed-out path (`forma-projects`, above) has no such budget. If you add anything to the saved payload, it lands inside this budget — and remember `firestore.rules` must gain the field too.

**Saving updates the open project, and happens on its own (2026-11-05).** One of the chat gaps the owner asked to be built: the conversation was lost on a reload unless Save had been pressed, and every press of Save minted a new `reportId`, so saving twice listed the project twice. `handleSaveReport` became **`persistProject(quiet)`**, the one save path, and:

- **it saves into `openReportId`** when a project is open, and gives a session with none an id that it keeps from then on. Firestore takes it as an `update`, which the rules already allowed with the same six fields; signed out, the project's earlier save is replaced and moved to the top (in `localStorage` then, in one `forma-projects` transaction since 2026-11-11). `persistRevisions`' read of what is stored, which waited for exactly this, now writes only the versions the collection lacks. **`projectName`** keeps a project's name once it has one and names an untitled one from the report's title or the first line said, as ChatGPT names a chat;
- **it runs on its own** 1.2 s after the session changes, while Forma works too since 2026-11-07 (a message is saved as soon as it is sent, and a page closed or hidden runs a waiting save at once; see the batch A bullet of 2026-11-07 in app-shell.md), whenever **`sessionSignature`** (`lib/savedReport.ts`) has moved: a hash of every message's words, its rating, failure and answered questions, and of the report's spec and REPX, because a control dragged from x=10 to x=20 changes no length. The quiet save shows no notice, teaches the memory nothing (`rememberKept` is the person's Save alone), and says a failure once per project (`autosaveFailedFor`) rather than after every turn. The Save button reads **Saved**, disabled, while the signature matches the last save, and Save otherwise;
- **New report and opening another project run a waiting save at once** (`flushAutosave`) rather than drop the last turn; **signing out and an account change drop it**, so one person's conversation is never saved where the next person signs in;
- **every way of leaving a session goes through `leaveSession(keep)`** (2026-11-06, the workspace audit): New report, opening a project or a batch result, deleting the open project (from the title's menu, its row or Clear all), signing out here or in another tab. Until then each cleared what it remembered to and none stopped a run, so a report or reply still on its way landed in the session opened next and was saved under its id; a batch result kept the open project's id and was saved over it; the last project's revisions and undo history stayed to be restored onto the next, and after a sign-out the next person could see them; and the open project deleted from its row came back on its next save. It stops the run first (both abort controllers, and a session counter, `sessionId`, for work with no signal, such as Test data). `save` keeps the session as it stands, a run cut short marked "Stopped." as Stop marks it (`persistProject` takes the session to keep for this); `drop` keeps nothing, for a project being deleted and a sign-out. Then it clears the session's history, revisions, the changes its replies can undo, the queue, the description's brief, the settings worked out for its request, the Preview's selection and zoom, and an open Export panel or Share dialog. A save still in flight when the session changes no longer marks the next one Saved (`saved` checks the open id);
- **a reload opens the project that was open**, from its id in `sessionStorage` (`forma:openProject`, per tab, an id only), once the list holding it has arrived and only into an empty workspace.

Checked in the owner's Chrome against a mock-mode server, signed out: two messages made one project, "hello there (4)", the button read Saved, a reload brought back all four messages, and New report then a message made a second project beside it. `leaveSession` was checked the same way on 2026-11-06: a message sent and another project opened through Ctrl+K before the reply came left the first project saved with the message and "Stopped." and the second untouched; New report emptied the Revisions panel; the open project deleted from its row cleared the workspace and stayed deleted.

Outcomes reach the user through **`saveNotice`**, a separate state from `error`: it carries "Saved to your projects." or the longer "…the uploaded images were too large to sync" variant, and an effect clears it on a timer. Since 2026-11-06 it shows as a toast at the bottom right of the workspace, with a × (`wb-toast` in `App.tsx`), not in the bench bar. Failures use `setError` via `reportFirestoreFailure` (see below). Keep the two channels distinct — a degraded save is a success, not an error. A stale `firebase-blueprint.json` used to sit in the root documenting a *different* `SavedReport` entity (`targetFormat`, `repxContent`, `layout`, `content`) matching neither the rules nor the code; it was removed, and is recoverable at `9e92b86~1:_not_required/firebase-blueprint.json`.

Firestore is reached via `getFirestore(app, firebaseConfig.firestoreDatabaseId)`, and **the `databaseId` in `firebase-applet-config.json` and `firebase.json` must stay identical** — a mismatch silently talks to the wrong database.

**`firebase.json` gained a `hosting` block on 2026-09-08, and its headers are derived rather than written.** Firebase Hosting is the deployment target (README, *Deployment*), and a static host cannot run `server.ts` — so the entire security header set, `connect-src` included, exists a second time in that file. That is a duplicate of the app's central security claim, so it is pinned: `src/server/hostingConfig.test.ts` builds the expected headers from `securityHeaders.ts` and `staticCache.ts`, asserts `firebase.json` matches exactly, and prints the JSON to paste back when it does not. **Edit the policy in `securityHeaders.ts` and let the test drive `firebase.json`, never the reverse.** Verified by mutation: dropping one origin from `connect-src` in `firebase.json` fails the test with both policies printed side by side. Note the test asserts `securityHeadersFor({ https: true })`, because Firebase always terminates TLS — that is the condition under which HSTS may be sent at all, and it is why the deployed set has one header the local server omits.

**What the free Hosting allowance really buys (2026-11-11, the full audit's SA-02).** The Spark plan serves 360 MB a day across both sites, and README's figure of about 730 cold visits a day is right for a visit that reads the pages and opens the workspace. It is not the number that binds. The first time a person attaches a picture, the browser downloads the picture readers' models from this site's versioned folders, about **18.6 MB** (measured on the live site that day; cached afterwards), so the allowance is about **19 new picture readers a day**, and past it both sites stop serving until midnight Pacific time with no warning to anyone. The owner checks Hosting usage in the Firebase console once a week. If it nears the cap, the two free answers (owner decision 8 of that audit) are to load PaddleOCR only when Tesseract is unsure of a page, measured first with `scripts/model/ocrCompare.ts` because it changes reading quality, or to serve the versioned model folders from a second free static host, which adds an origin to the CSP and ends "never a CDN".

As of 2026-08-09 the project is **`forma-201ba`** on the **`(default)`** database, Standard edition. It was previously the AI Studio project `gen-lang-client-0000000000` on a named Enterprise database; that project had no Firebase enabled and could not be administered, which is why Google sign-in always failed with `auth/unauthorized-domain` (see below). Two consequences of the move: `firebase.json` no longer carries `edition`/`dataAccessMode`, which are Enterprise-only and break a Standard deploy; and **`.firebaserc` is the file that decides the deploy target** — `firebase use <id>` sets only the CLI's own per-directory state, so a stale `.firebaserc` will happily deploy to the old project from a fresh shell or CI. It was stale exactly this way once.

**`firebase-applet-config.json` commits a real `AIzaSy…` string, and that is correct — do not "fix" it.** A Firebase Web API key is a public project identifier, not a secret: it ships in every Firebase web app by design, and `firestore.rules` plus the authorized-domain list are what actually protect the data. It is *not* the same kind of value as the Gemini key whose leak is described in [`gemini.md`](gemini.md), and the two must not be conflated — removing it or moving it behind an env var breaks Firebase init for no security gain. The rule that matters is the narrower one: no **Gemini** key in any committed file, `.env` included.

**There is no auth fallback, and reintroducing one is not an option.** A failed sign-in is a failure. Until 2026-08-09 both sign-in paths fabricated a user with `uid: 'local-dev-user-id'` / "Local Developer" on two Firebase error codes — `auth/unauthorized-domain` (Google) and `auth/configuration-not-found` (email) — handing out a workspace session with **no credential check of any kind**. It has been removed outright: from `LoginPage.handleGoogleSignIn`, from `LoginPage.handleSubmit`, and from `App.handleLoginSuccess`, which is where the session was actually manufactured. `local-dev-user-id` now survives in `src/` only inside one comment above `handleLoginSuccess` recording what was removed, and grepping the production bundle for it returns nothing.

The history is worth keeping because the same mistake has been made twice here in escalating forms:

1. The email path once matched on **message text** — `err.message?.includes('configuration') || err.message?.includes('network')`. Firebase's `auth/network-request-failed` message contains "network", so **any dropped connection during sign-in signed the visitor in regardless of the password they typed.** That was narrowed to exact codes.
2. Exact codes were still a bypass. `auth/unauthorized-domain` is precisely what a *deployed* site returns when its domain is missing from Firebase's authorized-domain list — so one configuration slip would have let every visitor who clicked "Sign in with Google" into the workspace. Gating it to `import.meta.env.DEV` was considered and rejected: a credential-free path is a liability whether or not it ships, because it trains the codebase to treat auth failure as recoverable.

Both configuration codes now map to real text in `AUTH_MESSAGES` so a misconfigured project *says so* rather than papering over it. The single `loginModal` definition in `App.tsx` (rendered as `{loginModal}` in both the landing and workspace trees) remains the right structure — two copies drifted once, one restoring `lastViewHash` and the other hardcoding `#workspace`.

**Signing in returns you where you were; it is not a door into the workspace.** `handleLoginSuccess` navigates to `lastViewPath || '/'`, the same expression the modal's cancel path uses — it used to hardcode `/workspace`, so somebody who signed in from `/docs` to save a project was moved somewhere they had not asked to go, and the two adjacent paths disagreed about the same question. Anyone who *does* want the workspace has an explicit "Go straight to the workspace" control on the sign-in screen, which calls `navigate('/workspace')`; before this it was decoration and did nothing. Note when testing that reaching `/login` by a full page load resets React state and so resets `lastViewPath` to `'/'` — exercise the in-app control, or you will be measuring the test rather than the code.

Because that uid can no longer exist, the `user.uid !== 'local-dev-user-id'` guards that used to sit in `handleSaveReport`, `handleDeleteReport`, the `onSnapshot` fetch effect and `canUseVault` are gone too. The branch is simply **signed in → Firestore, signed out → the device** (`localStorage` then, IndexedDB `forma-projects` since 2026-11-11), and save and delete must keep the same shape as each other so a report is always removed from wherever it was written.

**Signing out clears the documents, not just the credential.** `handleLogOut` used to drop the API key and vault state but leave `messages`, `result`, `previews` and `attachmentTexts` in place — so the next person at that browser saw the previous user's uploaded design, the text extracted from their PDFs, and the generated report. It now calls `handleClearChat()` as well. The same clearing runs from the `onAuthStateChanged` listener when a session ends **elsewhere** (another tab, a revoked token); `previousUidRef` distinguishes that from the initial `null` every signed-out visitor gets on load, which must not wipe their work.

**Form validation lives in one pure `validate(mode, values)` in `LoginPage.tsx`**, returning a `FieldErrors` record rendered under each input, not in the single banner it used to share. Three things about it are deliberate:

- The form carries **`noValidate`**. `required` and `type="email"` are still on the inputs for their `aria-required` / semantic value, but the browser's native bubbles are suppressed so two mechanisms cannot disagree about the same field with different wording.
- **Nothing renders `err.message`.** Firebase codes go through the `AUTH_MESSAGES` map; the raw message is the `Firebase: Error (auth/…)` envelope, and on sign-in it distinguishes `auth/user-not-found` from `auth/wrong-password`. Both map to one string, and `sendPasswordReset` swallows `auth/user-not-found` entirely, so neither path becomes an account-enumeration oracle. Keep any new code you add to that map on the same side of that line.
- Checks are ordered so a too-short password reports its own length problem rather than surfacing as "passwords do not match" against a half-typed confirmation, and `validate` is pure so the submit path and any future on-blur path cannot drift.

Email and display name are trimmed **at submit, not in `onChange`** — trimming per keystroke makes the space bar look broken. A whitespace-only display name is rejected rather than reaching `updateProfile` as a blank.

**`handleFirestoreError` re-throws, so never call it bare from a UI handler.** `src/services/firebase.ts` exports it as the shared Firestore error handler, and it does two things worth knowing before you call it: it `console.error`s a JSON blob that includes the signed-in user's uid and email, and then it **throws a new `Error` whose `message` is that same JSON string**. So it is a rethrow, not a swallow.

`handleSaveReport` and `handleDeleteReport` used to call it directly from `catch` blocks in `async` handlers with nothing above them, so a rules rejection became an unhandled promise rejection and the user saw nothing at all — the save just silently didn't happen. Both now go through **`reportFirestoreFailure(err, operation, path, userMessage)`** in `App.tsx`, which wraps the call in its own `try/catch` to absorb the rethrow (the logging is the point; the throw is not) and then `setError(userMessage)` with plain language. Use it for any new Firestore call site, and **never render `err.message` in the UI** — it is a JSON dump containing the user's email, which is exactly why the wrapper takes a separate `userMessage`.

**There is no longer a permission error on load, and that is the fix rather than a regression (2026-09-01).** `src/services/firebase.ts` called a `testConnection()` at import time which read `test/connection` — a path no rule matches, so the global deny in `firestore.rules` rejected every one. This note used to tell you that error was expected. It was: a Firestore round-trip **guaranteed to fail**, once per page load, for every visitor including those who only ever read the landing page. What it bought was a single `console.error` in the one case where the failure message contained "the client is offline"; every other failure, the denial included, was caught and dropped.

It is gone. Recover it with `git log -S'testConnection' -- src/services/firebase.ts`, and read the comment left at the removal site before you do. **Do not add a connectivity probe back:** a misconfigured project announces itself on the first genuine read, through `handleFirestoreError`, which knows the operation and the path a probe cannot. Note `tests/firestore.rules.test.ts` still asserts `test/connection` is denied — that test is about the global deny rule, which is still the security boundary, and never depended on the app reading that path.

**Firebase is loaded on demand, and three modules had to move together (2026-09-01).** `App.tsx` opened with `import { auth, db, … } from './services/firebase'` plus a direct `firebase/firestore` import, which put the SDK in the eager bundle: **471.91 kB raw, 110.52 kB gzipped, 42% of the entry chunk**, downloaded and parsed before anything rendered — in front of every visitor to the landing page, the features page and the privacy policy, none of which can sign anyone in. The app is fully usable signed out, and generation never touches Firebase at all.

`src/lib/firebaseClient.ts` now loads it, in the same shape as `lib/pdf.ts` and `lib/genai.ts`. Three things had to move at once, because **any one of them left behind pulls the whole SDK back in**:

- `services/firebase.ts` — the app singleton, `auth`, and `db` until 2026-11-01 (below).
- `firebase/firestore` — the operations `App.tsx` called directly.
- `lib/accountData.ts` — the path builders, which import `collection` and `doc`.

A fourth was subtler. **`OperationType` is an `enum`, so `OperationType.GET` is a *value* reference**, and while that enum lived in `services/firebase.ts` a single one of those in `App.tsx` was enough to drag the SDK back into the entry chunk after everything else had been deferred. It now lives in `src/lib/firestoreOps.ts` with no `firebase/*` import at all, and must stay that way; `services/firebase.ts` re-exports it so existing callers are unaffected. `LoginPage` and `AccountDialog` became `React.lazy` for the same reason and not for their own size — both import `services/firebase` directly, and a static import of either undoes the deferral on its own.

**What it bought, measured:** the entry chunk fell from 1,121,920 B to 619,376 B — **502,544 B, 45%, off the critical path**, 118 kB of it gzipped. What it cost: `dist/` grew 148,489 B, because the same modules spread across more chunks tree-shake and dedupe less well than they did in one. Grouping the SDK with `manualChunks` was tried against that and recovered about 3 kB, so the cost is inherent to splitting rather than a chunking mistake; the grouping was kept anyway, for one request instead of two and an artifact `check:size` can hold a budget against. Both budgets moved in the same commit and say why.

**Then auth was split from Firestore, because "on demand" had come to mean "on every page" (2026-11-01).** The repository audit found the deferred chunk fetched by every page: the header shows the signed-in state, so `App.tsx` called `loadFirebase()` on mount, and that brought the database with it. Every visitor, signed in or not, downloaded and parsed **395 kB of Firestore** to learn whether they had an account. `loadAuth()` now loads `services/firebase.ts` alone, which no longer imports `firebase/firestore` or `lib/accountData.ts` and no longer opens `db`. `loadFirebase()` adds both and opens the database as `client.db`, from the app and `firestoreDatabaseId` the service exports, and `App.tsx` calls it only once `user` is set. `deleteAccountAndData` imports what it needs when it runs. The `manualChunks` grouping kept above could not survive this, because one chunk would put the database back in front of everyone, so it now makes two: `firebase-` (169,880 B, every page) and `firestore-` (449,408 B, signed in). They come to 227 B more than the one chunk did, and both budgets were retuned to about 94% in the same commit. `src/lib/firebaseClient.test.ts` pins the split, and checks the source for the static imports that would quietly undo it, which no size budget would catch, because the bytes stay in their own chunk and only the order they load in changes. **What a signed-in user sees has not changed:** the projects list and the key vault waited for the loaded client before, and they still do, now behind one more `await` that starts the moment `user` arrives.

**The one behavioural change: session restore is a tick later.** `onAuthStateChanged` subscribes after the loader resolves rather than on first render, so a returning signed-in user is briefly `user === null` — the same state every signed-out visitor is in, and the same state everyone was in before Firebase answered anyway. What changed is how long it lasts, not that it happens. Anything reading `user` must already tolerate null; if you add something that cannot, gate it on the loaded client rather than reintroducing a static import.

**Deleting an account deletes its data first, and the order is not interchangeable (2026-08-15).** `deleteAccountAndData` in `services/firebase.ts` re-authenticates, then removes every document under `users/{uid}/reports` **and the `versions` subcollection beneath each of them**, then `users/{uid}/vault/geminiKey`, and only then calls `deleteUser`. Those documents live behind rules that only admit the signed-in owner, so deleting the account first would strand them: nobody could ever reach them again, including the person who asked to be forgotten. The vault delete tolerates failure — most accounts never stored a key, and `deleteDoc` on a missing document is a no-op — but a rules edge must not block the deletion the user actually asked for. Verified end to end on 2026-08-15 through the app's own button: reports and vault gone, account gone, session ended. **Since then the list has grown, and two of its steps have an order of their own (2026-11-11, the full audit).** `deleteAccountData` now also removes the shares and their access lists, the projects index, the share count, the learning switches (`users/{uid}/meta/learning`) and the learning events. App Check is started before anything touches Firestore, which refuses a request without it once App Check is enforced. The learning events go **first**, retried once, in pages of 50, one batch a page: 50 rather than Firestore's 500 because an opt-in event may hold 400,000 characters and the web SDK cannot read references alone, and first because if that delete fails the deletion stops before anything else is removed and says so in plain words, rather than leaving an account half deleted. The browser's own copy for that account goes too (`forgetAccountLocally` in `lib/signOut.ts`: `forma.memory:<uid>`, `forma:indexCheckedAt:<uid>`, and the learning switches when they name that account), since a deleted account never signs back in to find them.

**Sensitive account changes re-authenticate, and the branch is by provider.** Firebase refuses a password change, an email change or a deletion without a recent sign-in (`auth/requires-recent-login`). `reauthenticate()` asks a password account for its password and sends a Google account back through the popup — asking a Google user for a password would be a field nobody can fill. Email changes go through `verifyBeforeUpdateEmail`, never `updateEmail`: the address moves only once the *new* inbox has been opened, so a typo cannot lock someone out, and the direct call is refused outright when email-enumeration protection is on.

**`updateProfile` fires no auth-state event, and that cost a visible bug.** It mutates the `User` object in place, so `onAuthStateChanged` stays quiet and React re-renders nothing — measured: renamed to "Renamed Properly", Firebase stored it, and the rail still showed the sign-up name until a reload. `App.tsx` keeps a `profileTick` counter that the account panel bumps, read through the `accountName` memo so the dependency is real rather than a state variable nobody consumes. If you add another profile field, it needs the same treatment.

**The report configuration persists, and the API key must never ride along with it.** `localStorage['reportConfig']` holds the document settings — version, unit, page size, header, footer — because they are a standing preference: someone targeting DevExpress 20.1 targets it every session, and until 2026-08-13 `config` lived in React state only, so every reload silently reset the version to the 23.2 default and the next export went out for a designer that would refuse it. The trap is that `ReportConfig` also carries `customApiKey`, so persisting the object whole would reintroduce the plaintext-key-on-disk problem that `purgeLegacyPlaintextKey()` exists to undo, under a new name. `src/lib/reportConfigStore.ts` therefore uses an **allowlist**, not a blocklist: `toPersistable()` copies five named fields and nothing else, so a field added to `ReportConfig` later is not written until someone adds it there deliberately. `mergeStoredConfig()` refuses to read a key back out even if one appears in storage by hand or by a future bug, and falls back to the defaults on anything malformed rather than throwing. The key is applied to the config object *after* the merge, from `sessionStorage`. Both halves are pinned by `src/lib/reportConfigStore.test.ts`, because a key written to disk is invisible until someone opens devtools.

**A save that fails has to reach the panel the user is actually on (2026-09-08).** Both the local and the Firestore failure paths report through `setError`, and `error` — like `saveNotice` — renders in the Composer, which lives in the **Review** panel. Save is in the bench bar and reachable from every rail panel, so a save attempted from **Projects** wrote its message into a `wb-hidden` subtree: measured at 0x0 with `onScreen: false`. A failed save also adds no card, so from the one panel a person is most likely to be on while managing saved projects, a failure produced no card and no message at all. `handleSaveReport`'s two failure branches now switch the rail back to Review. The *success* path deliberately does not: the new row appearing in the list you are looking at is better feedback than being yanked to another panel to read a confirmation you do not need. Worth knowing before adding a third notice — the Composer is not a global toast, and anything routed through it is invisible from four of the five panels.

`localStorage` keys in use: `savedReports` (only where IndexedDB is missing since 2026-11-11; elsewhere it is moved into `forma-projects` once and removed), `darkMode`, `reportConfig`, plus the UI-state keys the workspace shell added on 2026-08-14 — `reviewWidth`, `reviewWidthEpoch`, `reviewCollapsed`, `railExpanded` (all defined at the top of `App.tsx`) — and `announcementsSeenId` from `src/lib/announcements.ts`. Eight in total; the last five are layout and read-state, deliberately **not** fields in `reportConfig`, which is an allowlist describing the *document* and is read back into what the model is given. See *The review column is resizable and collapsible* in [`app-shell.md`](app-shell.md) for why `reviewWidthEpoch` exists at all — it is the escape hatch for a stored width that has stopped meaning what it meant. (`selectedAiModel` is gone with the model dropdown, and is actively deleted on boot — a stored `gemini-2.5-flash` would pin a retired model and defeat detection.) **`customGeminiApiKey` is gone** — it held the API key in plaintext on disk, and `purgeLegacyPlaintextKey()` now deletes it on boot. The key lives in `sessionStorage['geminiApiKey:session']` instead; see *Where the user's key lives* in [`gemini.md`](gemini.md). Nothing that touches the key may be written to `localStorage`.

**Revision history is persisted for signed-in users, in a subcollection, and the four coupled changes it needed are the point (2026-09-05).** The paragraph that stood here said it was deliberately *not* persisted, and listed what doing it properly would take. That list turned out to be exactly right, so it is worth keeping as the shape of the work: a subcollection under `users/{uid}/reports/{id}/versions`, its own `match` block and validation in `firestore.rules`, its own cases in `tests/firestore.rules.test.ts`, and a change to the account-deletion path.

*Why a subcollection and not a field.* One `result` — markdown, layout and REPX — runs 50–200 kB, so ten revisions inline would exceed `CLOUD_SAVE_BUDGET_BYTES` several times over, and the degradation path above (strip images, then refuse) has nothing useful to strip from a REPX. Each version is its own document with its own 1 MiB ceiling, budgeted separately at `VERSION_BUDGET_BYTES` (700 kB) in `src/lib/revisionStore.ts`; the report document's shape, rules and budget are untouched.

*Ten stored against twenty in memory.* `MAX_REVISIONS` is 20 and `MAX_PERSISTED_REVISIONS` is 10. A save costs one write per version that is not already stored — `planVersionWrites` reads the collection first and plans only the difference, so a save that added one refinement costs one write, not ten. It is idempotent: saving twice with nothing new plans nothing.

*Ten fixed slots, enforced by the rules (2026-11-11, the full audit's SA-01, batch LRN2).* "The newest ten" was the client's promise only: any id was accepted, so a modified client could write versions without end into the free plan every account shares. A version is now written to one of `VERSION_SLOTS`, `v0` to `v9` (`revisionStore.ts`), and `firestore.rules` accepts a version under no other id. A new version takes an empty slot or one holding a version that fell off the end, which is **overwritten rather than deleted**; a stored id from before the slots is deleted at the next save and the revision it held, if still kept, written again into a slot. Since the slot says nothing about which revision it holds, `versionKey` matches stored and kept versions by time and label. The rules must be deployed with the client that writes slots. One gap stays open, the re-audit's R5-01: the rules do not require the parent report to exist, so versions filed under invented report ids are still unbounded (and survive account deletion, which reaches versions only through existing reports).

*Signed out gets nothing, and that is not an oversight.* `localStorage` held every project in one shared 5–10 MB quota, and a megabyte or two of history per report would have evicted the projects themselves — the thing the user actually asked to keep — so the signed-out path keeps revisions in memory for the session. The projects moved to IndexedDB on 2026-11-11, which removes that reason, but keeping signed-out history is a decision nobody has made, so it stays in memory. The panel says which of the two you are getting, because the difference is otherwise invisible until someone comes back the next day.

*Verified end to end on 2026-09-05 through the app itself*, the same way the account-deletion path above was: signed in, generate, refine, Save — the notice reads "Saved to your projects. Its version history came with it." — then reload the page and reopen the project from the Projects panel, and both versions are back, newest first. That last step is the one worth repeating after any change here, because everything before it passes whether or not the load path works. `tests/revisionRoundTrip.test.ts` covers the data path against the emulator; the four lines in `App.tsx` that call it are what this manual pass exists for.

*And the one that is easy to get wrong.* **Deleting a document does not delete the subcollection beneath it.** A report removed with a bare `deleteDoc` leaves its whole history behind, under an account that may go next, reachable by nobody — the precise stranding the delete-order paragraph above exists to prevent, and indistinguishable from a clean delete. So `deleteReportAndVersions` in `lib/accountData.ts` is the only way a report may be removed: versions first, then the report, for the same reason the account order runs the way it does. `deleteAccountData` maps every report through it, `App.tsx`'s delete button calls it, and `tests/accountDeletion.test.ts` asserts the absence from both directions — the only way that failure is ever visible.

`persistProject` persists only `messages` and `result`, never `config` — so the key has never leaked into a saved report, and it must stay that way if you extend what gets saved.

**Shared reports live in `shares/{id}`, a copy and never the project (2026-11-06).** The owner chose Google Stitch's Share dialog that day. Everything above is owner-only under `users/{uid}`, and sharing does not change that: the dialog (`ShareDialog.tsx`) writes a separate document holding the report alone (its title, REPX and layout, `lib/shares.ts`), not the conversation, and the shared page (`SharedReportPage.tsx`, the route `/s/{id}`) reads only that. The copy changes when the owner presses *Update the shared copy*, not on every edit. Five decisions, each in `firestore.rules`' comments and pinned by `tests/firestore.rules.test.ts`:

- *The id is the secret.* 22 random base64url characters (132 bits); "anyone with the link" means anyone who has that. Nothing lists shares but their owner, and only by a query naming them.
- *A restricted share needs a verified address.* It opens for the owner and for a signed-in account whose `email_verified` token is true and whose address is on the share's access list. Without the verification, anyone could read one by creating an email-and-password account under an invitee's address, which Firebase allows unverified.
- *The access list is not on the share (2026-11-11, the full audit's SE-04).* Until then the invitees were an `emails` field of `shares/{id}` itself, the document a link share hands to anyone, so everyone the link reached could read the colleagues' addresses (one REST call with the public key, or DevTools). The list now lives at `shares/{id}/acl/emails`, `{ ownerId, list }` (lower-cased, at most 50), which only the share's owner may read or write, writing it needs a verified address, and `isInvited` in `firestore.rules` reads it for an invitee without handing it over. `isValidShare` refuses `emails` on any write; `writeShare` and `deleteShare` write and delete the share and its list in one batch; `ShareDialog` reads invitees with `readShareEmails`, and the shared page reads only the main document. **A share made before that day still opens through its old `emails`** and moves to the list the next time its owner writes it, which replaces the document whole (owner decision 7: no migration script, which would need a service-account key). **The deploy window:** a tab still running the build from before the change writes `emails`, which the new rules refuse, so from the moment the rules are deployed until that tab reloads, sharing from it fails. The hosting goes out with the rules (`scripts/deploy.mjs`), and a long-open tab looks for a new build every half hour and when it comes back into view, so the update notice (`UpdateBanner.tsx`) asks it to reload soon after. The rules suite proves a link viewer gets no addresses, an invitee opens through the list, a legacy share opens and migrates, and the list's writes are checked.
- *The shape is pinned* with `hasOnly` + `hasAll` like every other document, so the one collection others can read cannot become general storage; the access list is capped at 50 and `result` at a million characters.
- *Forma sends no email.* Sending one needs a server, and Forma has none and stays free; adding someone grants their address, and the dialog says to send the link.
- *Who may make one (2026-11-08, the site audit's batch SH, item 57).* A share puts a report on this site's domain for others to read, and until then any account could make any number, unverified, naming any report id. Now creating or changing one needs `email_verified`; its `reportId` must be a report the account has (`exists()` on `users/{uid}/reports/{reportId}`); and each account carries a count, `users/{uid}/meta/quota` = `{ shares, last }`, which the batch creating a share must raise by one (and `last` name it), capped at 100. The count's own rules let it move only by one and only in the batch that creates or deletes the share `last` names, so it cannot be lowered to make room; it may be deleted only at zero or when absent. Deleting a share lowers it in the same batch while it is above zero; a share from before the count leaves it at zero and goes without. So `writeShare` and `deleteShare` in `lib/accountData.ts` are the only ways to write or delete one, deletions go one at a time, and `deleteAccountData` removes the count after the shares. Stopping a share needs no verified address. The rules suite proves each of these, and `tests/accountDeletion.test.ts` deletes an account whose shares went through the count.
- *Ending someone else's session (item 99).* There is no session list and no second factor: Firebase's multi-factor sign-in needs the paid Identity Platform upgrade. A password or address change revokes every other session's refresh token, so an account ends them by changing its password; a Google account by its Google security page; and the owner can disable an account in the Firebase console (Authentication, Users), which ends its sessions within the hour, then enable it again. The Docs page says the first two and offers the third through the contact page.
- *A share goes with what it came from.* `deleteReportAndVersions` deletes a project's shares first, and `deleteAccountData` every share the account made, including one whose project had already gone; `tests/accountDeletion.test.ts` asserts both. A share left behind would be a copy of someone's report still readable after they asked for it to be gone.

**The projects index (2026-11-08, the site audit's batch SH, item 63).** The list listened to `users/{uid}/reports` itself, so every visit downloaded every project in full, images included, and every autosave (about 1 MB a turn) was sent to every open tab: on the free plan's daily egress, the first limit a real account meets. It listens to `users/{uid}/reportIndex` now, one entry per project, `{ id, name, timestamp, search, notes, userId }` (`StoredReportIndex` in `lib/savedReport.ts`; `search` is the person's words and Forma's questions capped at 4,000 characters, `notes` the message count the row shows), pinned by the rules like the project it describes. Things that keep it whole, each a decision:

- *An entry is not a project.* `fromIndexDocument` lists it with no messages and no result and `stub: true`; `fullReport` in App fetches the project when it is opened or duplicated; and **rename writes the name alone** (`updateDoc`, which the rules check as the merged document) because writing a listed entry back as a project would empty it. Search reads `search` for an entry not yet opened (`projectMatches`).
- *Every save writes its entry after the project*, tolerated: the project saved is what matters, and a missing entry heals at the next reconciliation.
- *A reconciliation*, once a week per device (`forma:indexCheckedAt:<uid>` in local storage) and at once when the index is empty, reads the projects in full as the list did and writes an entry for any without one. That fills the index the first time an account opens the new build, and heals one a save could not write; it is the one full read left, and it is weekly.
- *A fallback.* If the index cannot be read at all, which is the case until the rules are deployed, the list listens to the projects in full as before. Deploy the rules with the hosting, as `scripts/deploy.mjs` does, and nothing degrades.
- *Deletion.* `deleteReportAndVersions` removes a project's entry last, and `deleteAccountData` any entry left, both tolerated, since the index is a copy of what they already removed. The rules suite proves the shape and ownership, and `tests/accountDeletion.test.ts` the removal.

Signed out, nothing changes: the device's projects are kept in full, in `forma-projects` (above).

## What one account may write (2026-11-11)

Until the full audit's batch LRN (5c6f6a8), nothing limited what one account could write, and every account shares the one free plan (1 GiB stored, 20,000 writes a day). `users/{uid}/meta/usage` now holds counts that `firestore.rules` moves **in the same batch as each write they count**, so a client cannot write without counting:

- *Projects: at most 1,000.* `writeReport` raises `reports` (and names the project in `report`) when it creates one, and `deleteReportAndVersions` lowers it; the rules check both against the count before the write. A project the client guessed was new but the account already holds still saves at the limit, because `writeReport` retries as an update on `ReportLimitError`. The person is told "An account can keep up to 1,000 projects. Delete one to save another."
- *Learning events: at most 300 a server day, two seconds apart*, each needing a verified address, an edit event carrying 40 operations or fewer and a whole report at most 700,000 characters. The day and `at` must be the server's (`request.time`), so a made-up time is refused. Sends run one at a time through a module-level chain, so two started together no longer compute the same wait and have one refused for spacing.
- *Version slots* and *shares* have their own caps: ten slots a report (above) and 100 shares an account (`meta/quota`, *Who may make one*).
- *Deletion leaves counts, never ids.* The usage document may be deleted only at zero projects, and its two ids are cleared through an `idsCleared` rule allowed only then, so after an account deletion on a day an event was sent, only the day's counts and the time of the last one stay behind. Settings → Learning and the privacy policy say so in one sentence each.

**These caps bound one account, not the plan (the re-audit's R5-05, recorded rather than fixed).** A thousand projects at up to ~900 kB each is about the whole free storage, 300 events a day of up to 700,000 characters is about 210 MB a day per verified account, and a report update has no rate bound against the 20,000 writes a day. **The real gate against an abusive client is App Check**, on since 1.1.1 with reCAPTCHA Enterprise and to be enforced once its traffic is well inside the free quota (README, *Settings only the owner can apply*): an enforced App Check refuses a request that does not come from Forma's own page, which is what a scripted flood would be. Lowering the per-event whole-report size, or counting bytes per day, is the change that would bound the worst case in the rules themselves; lowering the project cap matters less. Each is the owner's decision.

**The rules have to be deployed for sharing to work on the live site**, and only the owner deploys: until `npx firebase deploy --only firestore:rules` runs, the global deny refuses every read and write of `shares`, the dialog reports that it could not share, and a link opens the page saying it does not open a report.

## Learning from use (2026-11-10, the full audit)

The owner's ask: the more Forma is used, the more its own model learns. So every report generated, every edit made in the chat, every translation and every rating of a reply becomes a **learning event** (`src/lib/learning.ts`), on two tiers the person chooses under Settings > Learning (`LearningSettings.tsx`):

- **Structure**, on by default and said in the privacy policy: the report's skeleton (`reportSkeleton.ts`, paper, bands, every control's kind, place, size, font, alignment, borders and the role of its text, never the text), the request's kind and source, which kind of AI answered, the edits' names and the checks' counts, and the thumbs. `scrubSkeleton` is the guard against a defect upstream: any string in a skeleton that is not one of its fixed words is stripped, the same promise `unexpectedStrings` makes for the shipped model.
- **Full reports**, off until turned on: the whole REPX and the person's words with it.

**Where it lives.** IndexedDB `forma-learning` on the device, the last 500 events, which Settings shows (counts by kind) and deletes, and which a sign-out deletes with the other device stores (`SIGNED_OUT_DATABASES`). Signed in, each event goes to Firestore `users/{uid}/learning/{id}` through `writeLearning` in `lib/accountData.ts`, created only in the shape `firestore.rules` pins (`isValidLearning`: every field present and no other, the id it is filed under, a known kind, sizes that keep a document far under 1 MiB) and never changed; the owner may list and delete the collection, `deleteLearning` is Settings' Delete, and `deleteAccountData` removes it with the rest (`tests/accountDeletion.test.ts`). The rules suite proves all of it.

**The switches follow the account (2026-11-11, the full audit's batch PRIV).** They lived in the browser, so the next person to sign in there inherited them: a whole-report switch one person turned on stayed on for the next, and turning learning off on one computer left it on everywhere else. They are now `users/{uid}/meta/learning`, two booleans (`structure`, `full`) that the rules let only the owner read and write and nothing else into, deleted with the account. The browser's copy (`forma:learning`) names its account, and another account's copy gives the defaults. An explicit off is kept from a copy written before this change or signed out, so an off chosen before signing in reaches an account with no copy yet instead of the more-sharing default; a change the account has not received is marked pending and sent at the next sign-in, and whole reports wait until the account's copy is known. Neither the sign-in settle in App nor the Settings section writes an older account copy over a switch changed meanwhile.

**Events are an outbox, and a refused one is read back.** Each event is kept with its account and a sent mark, and `flushLearning` sends what that account made on this device, on load and on sign-in. The rules allow create and never update, so an event that reached the account but was never marked sent (the tab closed in between, or two sends raced) used to be refused at every later flush, and since it sorted first it held back every newer event for good. `writeLearning` now reads a refused event back and **treats it as sent when the account has it**, and `flushLearning` passes over any event the account refuses, stopping only on other failures such as no connection. Recording an event cannot fail the generation that made it (the import and every step run fire-and-forget); a mock session keeps and sends nothing; with both switches off nothing is kept.

**The memory is per account too (same batch).** `lib/memory.ts` keeps it under `forma.memory:<uid>`, with `forma.memory` as the signed-out bucket, so the next person at a shared browser reads their own and the last person finds theirs again on signing back in; a plain sign-out leaves it, and only an account deletion removes it (`forgetAccountLocally`). Before this, everyone wrote the one `forma.memory` key, signed in or out, so on a shared browser it may still hold an account's lines; `retireLegacyMemory` clears it once, at the first sign-out after a signed-in session, and marks that done (`forma.memoryRetired`).

**What a sign-out removes from the browser (`lib/signOut.ts`).** The session keys (`SIGNED_OUT_SESSION_KEYS`: drafts, the queue, the open project, a reply's Undo); the device's databases (`SIGNED_OUT_DATABASES`: `forma-databases`, `forma-batch`, `forma-learning` and, since 2026-11-11, `forma-library`, the report library); and, since the same day, the local keys that name the last person's work (`forgetLocal`: `forma:pinnedProjects`, `forma:archivedProjects`, `libraryCanonical`, the library's house-style ticks, and every `forma:indexCheckedAt:` stamp by prefix). **Signed in, Firestore keeps its own copy in the browser** (batch SAAS, 2026-11-11), so a change made offline or just before the tab closed is sent the next time it opens; a sign-out closes that database and clears it (`closeFirebase`), and `forgetDevice` also deletes every IndexedDB whose name starts `firestore/`, for a copy left by a tab no longer open.

**How the owner uses it.** `npx tsx scripts/model/pull-learning.ts --key <service-account.json> --out <dir>` on the owner's own PC (never this shared server: the key is a credential) pulls every account's events over the Firestore REST API with no dependency (the service account's key signs a JWT in `node:crypto`), writes `events.jsonl`, `skeletons/*.json` in the shape `train.ts` takes through its new `--skeletons`, and for the opt-in tier `repx/*.repx` and `prompts/*.txt`, and prints counts only. From there: `npm run model:train -- --skeletons <out>/skeletons --data <set>` retrains Forma's own model; the opt-in reports feed the box reader's set, the library's examples and the chat judge's cases by hand, since each needs a person's look. The pull is the owner's cadence, a week at a time (`--since`).

**The pipeline as rebuilt (2026-11-11, the full audit's batch LO; the testable parts are `src/lib/learningPipeline.ts`).** The credential is read by `scripts/admin/google.mjs`: gcloud's application default credentials or a service account's key, viewer-only (`roles/datastore.viewer`) for a pull, with `roles/datastore.user` only for a `--reconcile` run that deletes. What changed, each a decision:

- *Pages by cursor, on an index.* The pull read page after page by `offset`, which Firestore bills as every skipped document read again, ordered by `at` with a filter on `day`, which no index served. It now orders by `day` then `at` and pages by the last event's `at` and document name, over the collection-group index `firestore.indexes.json` declares, which `scripts/deploy.mjs` deploys with the rules (`firestore:indexes`). It counts first and refuses to read more than 35,000 documents without `--force`, as `backup.mjs` does, because the live site shares the free plan's daily reads.
- *The resume rule.* The browser writes `at` and the rules accept any short string, so a cursor taken from the last event read could be frozen for everyone by one event dated 9999, and an event that synced late would be skipped for good. A weekly pull resumes from the latest event time it can trust (an ISO time no later than the pull's own start) less a 30-day lookback; events already in `events.jsonl` are not recorded or judged twice, and an event with a made-up time is refused and counted.
- *One account cannot poison it.* Each skeleton is scrubbed again, rebuilt from its known keys and held to the vocabulary, the page and the public fonts; only verified, existing accounts and real AI answers count, without audit errors, bad ratings or undos; an account adds one copy of a skeleton and at most twenty a pull, and a font is learned only when three accounts use it.
- *Deletion reaches every copy.* Each pull removes the files and lines of events that are gone; `--forget <uid> --reconcile <dir> ...` removes an account from the owner's folders with no credential; and `train.ts` empties and **rebuilds `set/skeletons` and `set/held-out` on every run**, so a person removed from the pull leaves the set the gate measures against as well.
- *A gate before it ships.* `train.ts` writes a candidate with an id and its counts; `scripts/model/gate.ts` passes it only when the leak check is clean, its fonts are public or already shipped, none of the six described fidelity cases (`scripts/fidelity/cases/described/`) scores lower, and the held-out skeletons sit no further from its archetypes.
- *Once a week, on the owner's PC.* `scripts/model/learn-week.ts --data <dir>` runs the pull, the training and the gate in a row and, on a pass, copies the model into `assets/model/` with a counts-only `model-card.json`, keeping every shipped model under `--models` by id; committing and deploying stay the owner's, and the job prints both commands. **Its pull is made without `--reconcile`**, so the weekly credential can be viewer-only; deleting a deleted account's events from Firestore is a run the owner makes on purpose. In Task Scheduler, with a weekly trigger and "Start in" the repository folder, the program is `cmd.exe` (npx is `npx.cmd` on Windows, which Task Scheduler cannot start by that name) and the arguments are `/c npx tsx scripts/model/learn-week.ts --data <the job's folder> --reports <the owner's reports>`.
- *Counts for the owner, and orphans.* `scripts/admin/stats.mjs` prints usage as counts only; `scripts/admin/orphans.mjs` lists every `users/{uid}` whose account Firebase Authentication no longer has, and changes nothing.

**What is not collected.** A user's description of a control (`AccessibleDescription`) is text and never reaches a skeleton; the companion's live rows, a database's layout and a Gemini key are never part of an event; mock mode's events say `mock` for the AI and are of no use to training.

**Which reports were kept, and the `kept` event (2026-11-11, batch LRN, 5c6f6a8).** A report is *kept* when it is exported, saved (after the save succeeds) or opened in the designer: one App helper, `exportThroughPreview`, records it and sends the export, and the Export panel, the command menu and the chat's export tool all go through it. The event carries how it was kept, the reply it came from, its distance from the first answer and the project; a chat Undo of a generation is an `undo` event. The skeleton travels only with a generation and a kept report; an edit event carries its operations and the kind of part each touched; a translation, a rating or an undo carries none. A reply carries `message.learning {id, ai}`, so a rating names the turn and AI it rates. The rules accept `source`, `request`, `ai`, `how`, `draft` and `dropped` only from fixed lists, and a test checks that every `LEARNING_*` list in `learning.ts` appears in `firestore.rules`.

## The reports a person keeps teach the next one (2026-11-11)

The part of the owner's "the more it is used, the more it learns" a person sees, built by the full audit's batch LRN2 (0cec241). The style, the library and the ledger are kept in the browser and nothing is sent to build them; what leaves is the kept example quoted to the AI on a first report (below), and, separately, the counted `kept` learning event above, which a signed-in, verified account writes to Firestore:

- *The style.* A kept report leaves its scrubbed skeleton in the memory (up to thirty), and once two are kept `memory.personalStyle` learns the person's margins, faces, sizes, bold and record row height. It goes into the house-style brief of a described report, and Forma's own report from words (`offlineGenerator`) takes each role's weight, the margins and the row height from it. Kept skeletons are read into hundredths of an inch through `parseReportStructure`'s own conversion (`memory.skeletonInHundredths`), because one read in its own unit turned a millimetre report's 1 cm margins into 1 inch. `run.ts --forma --style <file>` measures it: on `fastreport-employees`, Arial 8.75pt became the source's Segoe UI 9pt.
- *The library.* The report also joins the person's own report library, a `kept` store in `forma-library` (version 2), stripped by `chunkRepx` as an added file is (*Strip the data on the way in* in `docs/proposals/rag.md`), never embedded, the newest twenty. Kept records carry their owner, are read and listed for that owner only, and another owner's records are dropped when a report is kept, because this can be a shared browser and only a sign-out deleted the database. The Library panel lists them as *You kept this*, with Remove.
- *The example on a first report.* On a first report, the kept report nearest the draft Forma makes first is quoted to the AI as a formatting example, after the memories, behind a fence saying the source wins (`lib/learningLoop.ts`). Nearest is by shape features in the shipped model's scale, so the search sends nothing anywhere. The reply says "Laid out like your X report." only when the result's face and title size match it. What the example does to the AI's answers has not been measured; it needs the owner's key.
- *Learned from your changes.* What the person changes in a report Forma made is counted in a ledger (`lib/corrections.ts`), once per report, a chat Undo counting against a change and a Redo taking that back. A change two reports agree on becomes a memory in plain words, under Settings → Memory, *Learned from your changes*, with its own switch and a Forget; it is told to the AI, applied by Forma's own model and written into the house-style brief.
- *On until switched off, and forgotten whole.* `learnFromKept` and the house style are on by default. **The privacy policy does not say so yet**: on `0cec241` `LegalPage.tsx` still describes the library as "the stripped reports you add" and names neither the kept example quoted to the AI nor the corrections ledger. That is re-audit R4-01, still open with the public pages' batch, and its wording is the owner's to approve; until it lands, do not read this consent model as covered by the policy. Both Forget buttons take the account's records out of the `kept` store as well as the memory: until review caught it, forgetting cleared only the memory and the library went on quoting the reports.

The kept-report, offline-design and house-brief code lives in the lazy `lib/learningLoop.ts`, which took about 7.7k characters out of `App.tsx`.

## Answering a data request (2026-11-11, the full audit's SA-20)

The privacy policy promises an answer within 30 days to a request the workspace does not handle itself (a copy of the data, or its deletion for someone who cannot sign in), sent through the contact page. Every step here is the owner's, on the owner's own PC, because each needs a credential that can read every account; none runs on the company's shared server.

1. **Find the uid.** `npx firebase auth:export accounts.json --project forma-201ba` writes every account with its uid and address (the Firebase console's Authentication tab shows the same, searchable by address). Delete that file when done: it is everyone's addresses.
2. **A copy.** The person can take one themselves from Settings → *Download everything (.zip)* when they can sign in. Otherwise, read `users/<uid>` and its subcollections and the shares whose `ownerId` is that uid in the Firestore console, and send what is there.
3. **Deletion, when they cannot do it themselves.** `npx firebase firestore:delete users/<uid> --recursive --project forma-201ba` removes the projects, their versions, the index, the key vault, the share count, the learning switches and the learning events. Then each share they made: find them in the console with a filter on `ownerId` equal to the uid, and remove each with `npx firebase firestore:delete shares/<id> --recursive --project forma-201ba`, which takes its access list with it. Then delete the account in the console's Authentication tab.
4. **The owner's own copies.** `npx tsx scripts/model/pull-learning.ts --forget <uid> --reconcile <each pull folder>` removes that account's learning events from every folder the owner pulled, and the next `learn-week.ts` run rebuilds the training set without them.
5. **Check.** `node scripts/admin/orphans.mjs` lists any `users/{uid}` left without an account; the deleted uid should not be among them.
