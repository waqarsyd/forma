It is incident history — the reason a thing is the way it is, which the code cannot tell you. **Nothing here is loaded automatically**: `CLAUDE.md` routes to this file, and reading its one-line summary of this area is not a substitute for opening it before you change that area.

## Styling and motion

Tailwind v4 via `@tailwindcss/vite` — no `tailwind.config.js`. Design tokens live in `src/index.css` under `@theme`: semantic `--color-background`/`--color-card`/… (whose light/dark values are the `:root` / `.dark` custom properties in `@layer base`), plus a Material-style landing-page palette and `--font-*` / `--text-*` scales. Dark mode toggles the `dark` class on `document.documentElement` — but *how* that class gets there is a four-part mechanism, below. Path alias `@/*` resolves to the repo root, not `src/`.

**Theme resolution spans four places that must change together.** `document.documentElement.classList.toggle('dark', …)` is the easy half; the rest is not obvious from any one file:

- **`index.html` carries an inline pre-paint bootstrap.** It reads `localStorage['darkMode']`, falls back to `matchMedia('(prefers-color-scheme: dark)')`, and sets the class before the bundle loads. It is inline and dependency-free on purpose — a module import runs *after* first paint, which is exactly the flash of light theme it exists to prevent. `App.tsx`'s `useState` initialiser mirrors that same resolution order; if you change one, change both or the app will repaint on hydration.
- **Persistence lives in `setTheme` (the user's action), never in an effect.** StrictMode double-invokes effects in dev, so an effect-based write would persist the *system-derived* value on mount and permanently detach the user from `prefers-color-scheme`. The syncing effect toggles the class and nothing else.
- **The OS is followed for as long as the user has never chosen.** A `matchMedia` `change` listener updates the theme only while `localStorage['darkMode'] === null`. An explicit choice writes the key and ends the following, which is why the listener re-reads storage rather than capturing a flag.
- **`isFirstThemeRun` suppresses the transition on mount.** The bootstrap already painted the correct theme, so animating on the first effect run would animate a change that never happened. Only a genuine toggle animates.

**`src/components/landing/icons.tsx` is the icon set — use it for all new work, anywhere.** Inline hairline SVG at the same stroke weight as the sheet's rules, which is the point: these surfaces are drafting sheets and a filled glyph reads as a different family beside them. It carries 66 exports behind one `Svg` wrapper taking `size` / `className` / `strokeWidth` (1.8 default), three of which — `IconGitHub`, `IconLinkedIn`, `IconDiscord` — are brand marks rather than hairline icons. **Add icons here rather than starting a second set, and match the default stroke** — a heavier icon in a toolbar is obvious next to a lighter one in the same row. The file was the landing page's private set until the workspace was rebuilt on the same design language; the "keep using Material Symbols elsewhere" instruction it used to carry is **reversed and gone**.

`lucide-react` **has been removed** — `App.tsx` was its last consumer and it is out of `package.json`, `package-lock.json` and `node_modules`. Do not reintroduce it.

**Material Symbols survives in exactly two files: `SiteHeader.tsx` and `MobileNav.tsx`** (two uses each; the `.material-symbols-outlined` `font-variation-settings` rule in `index.css` serves those four and nothing else). `App.tsx` was the last other consumer and lost its 40 ligature spans in the 2026-08-12 workspace port. Those four uses are the only reason the `material-symbols-outlined` Google Fonts `<link>` in `index.html` still has to be there, and migrating them would let both it and that CSS rule go — worth doing, but it changes the marketing chrome, so it needs the same before/after render check the pages get. While it stays, remember those glyphs render as **literal ligature text** if the `<link>` fails, which is the tell.

One trap the migration removed rather than carried across: `material-symbols-outlined` ships its own `display` from an *unlayered* `<link>`, which beat Tailwind's layered `hidden`, so responsive classes on those spans silently never applied — `App.tsx` had two comments recording dead `lg:hidden` classes. Inline SVG has no such problem, so `hidden sm:inline` on an icon now does what it says.

**Silhouette is what carries at toolbar sizes, not detail.** There is deliberately no `IconRocket`: three attempts at one all reduced to the same triangle-plus-crossbar shape as `IconRuler`'s compass sitting in the next card at 22px. The card means export, so it uses `IconDownload`. When adding an icon, render it at 14/20/34px next to its neighbours before keeping it.

Three token sets are duplicated by hand and must be changed together:

- **Motion** — `--ease-*` and `--duration-*` in `src/index.css` mirror `EASE` / `DURATION` in `src/lib/motion.ts` (CSS in ms, Framer Motion in seconds). Both files say so at the top. `--ease-spring` had no counterpart in `EASE` for a while; it does now (`EASE.spring`, with `DURATION.snap` / `--duration-snap` beside it, used by `snapInVariants` for the landing page's detection boxes). If you add one side, add the other — that drift is exactly what these two bullets exist to prevent.
- **Landing palette / typography** — the `@theme` block mirrors the YAML frontmatter in **`docs/design/DESIGN.md`**, which is the design source of truth. There is now one copy: it lived at `public/LoginPage/DESIGN.md` with a byte-identical twin under `Contact&InquirePage/`, so every edit had to be made twice. Both were also inside `public/`, meaning Vite copied them into `dist/` and **served the design docs on the live site** — verified in a build. The duplicate was removed, and is recoverable at `991095a~1:_not_required/public/LoginPage/Contact&InquirePage/DESIGN.md`.
- **Fonts** — `--font-title-md`, `--font-body-lg`, `--font-code-sm` etc. name Hanken Grotesk / Inter / JetBrains Mono, which are loaded by `<link>` in `index.html`, not by the `@import` in `index.css` (that one only pulls Roboto).

  **The weights in that `<link>` are measured, and were wrong in both directions until 2026-08-29.** Inter and JetBrains Mono stopped at 600 while Tailwind's `font-bold` resolves to **700** against whichever family is in effect — so with no 700 face to use, the browser *synthesised* one by thickening the regular weight. That was happening on **22 elements across five marketing pages**: every `<b>` in body copy, the geometry callouts in the scanner figure, the `INVOICE` label, and the byline in the footer. Faux bold is not just heavier, it is **wider** — thickening each stem adds advance width the designer never drew, so it moves line breaks too. Meanwhile Hanken Grotesk was asking for 400/500/600 and painting them on **zero** elements; the display face is only ever used at 700 and 800.

  Correcting both cost **nothing**. All three families are served as *variable* fonts — one woff2 per family spanning the whole weight axis — so the `wght@` list decides which `@font-face` blocks appear in the CSS, not which binaries exist. Four request variants were fetched and weighed at exactly **116,280 B each**; only the CSS moved (22.5 → 25.0 KB, gzipped in transit). The total font payload is **113.6 KB across three files**, which is *less* than the images.

  **So: do not add a weight without checking something paints it, and do not remove one without checking nothing does.** Neither question can be answered by reading source, because the family/weight pairing only exists at render time. The method, if it needs redoing: load each route and read `document.fonts` for what the browser actually downloaded, then computed style on every element containing visible text for what the page actually paints — the disagreement between those two lists is the answer. Commits `b2ed3aa` (measurement) and `1563593` (fix) carry the numbers.

**The sheet palette is a whole scoped token set, not a few overrides**, because the home page was matched pixel-for-pixel to an external design and that design has its own tokens. It is split across **two selectors, and which one you reach for matters**:

- **`.sheet, .landing`** is the token layer — the `--color-*` remaps plus `--ground-2`, `--ink-faint`, `--accent-deep` / `--accent-wash` / `--accent-line`, `--ok-*` / `--bad-*`, `--paper-rule`, the `--code-bg` / `--code-rule` / `--code-ink` trio for the XML pane (`--code-bg` sinks a step darker in dark mode — hardcoding the light value left the pane visibly wrong in dark), and `--shadow-sm` / `--shadow-md` / `--shadow-lg` / `--inset-hi`. The most consequential remap is `--secondary`: it is `#a04100`, a dark brown, app-wide, and the sheet's accent is `#fe6b00`. **Use those shadow variables on any sheet surface rather than Tailwind's `shadow-*` scale** — it is a different ramp, and matching by eye put every panel a step too heavy.
- **`.landing` alone** carries four page-only declarations that must never move into `.sheet`: `text-rendering: optimizeLegibility` (the source sets it on `body`; without it kerning differs and every glyph lands a fraction off), `overflow-x: clip` (the source's `body { overflow-x: hidden }`, containing the oversized decorative glows — `clip` rather than `hidden` so the element does not become a scroll container and stop the header sticking), and `--spacing-container-max: 1180px` / `--spacing-margin-desktop: 32px`. Those last two are the reason the split exists: **spacing variables scope at the element** rather than resolving once at declaration, so leaking them to a full-bleed surface narrows it to the marketing measure.

So a new sheet-styled surface takes `class="sheet"`; the six marketing pages keep `class="landing"` and match the shared selector, which is why the split needed no markup change to any of them. The workspace root is the only `.sheet` consumer so far. Verified as a no-op when introduced: all five pages rendered byte-identical at 1440px in both themes, ten of ten hashes unchanged.

**A third block on that same selector carries the ARTIFACT TOKEN ALIASES**, and it is what lets `src/workspace.css` stay verbatim — see the port's own rules in [`app-shell.md`](app-shell.md). The artifact named its tokens `--surface` / `--panel` / `--panel-2` / `--track` / `--ink` / `--ink-2` / `--rule` / `--rule-strong` / `--accent`, plus `--display` / `--body` / `--mono` for the three families; each alias points at the `--color-*` or `--font-*` token the sheet scope already defines, so **they are indirection, not a second palette** — nothing needs adding to the dark twin, because custom properties resolve where they are *used* and the aliases pick up whichever `.dark .sheet` value is in scope. Two entries are not aliases and say so in place: `--on-accent: #ffffff` (the artifact never flipped it) and `--warn: #d9a95f`, which the artifact only ever had as the fallback half of a `var(--warn, #d9a95f)` for the processing pip, having never declared the variable at all. If you add a `--color-*` token that the workspace needs, alias it here rather than editing the ported file.

**`@import "./workspace.css"` sits immediately after `@import "tailwindcss"`, and the order is load-bearing.** Those rules are plain CSS rather than utilities, so they are unlayered and would otherwise lose to preflight on the properties preflight resets — which is exactly the class of collision the PREFLIGHT COMPENSATION block ([`app-shell.md`](app-shell.md)) exists to handle for the cases importing late cannot fix.

A `.landing sub` rule undoes Tailwind's preflight, which rewrites `<sub>` to `position: relative; line-height: 0` so it no longer grows the line box.

**Do not use `text-body-lg` (or any `--text-*` token) as the base size on a surface being matched to a design.** Those tokens carry a *fixed pixel* line-height — `--text-body-lg--line-height: 24px` — and line-height inherits, so every descendant that does not set `leading-` explicitly gets 24px regardless of its own font size. The landing root uses `text-[16px] leading-[1.62]` instead, a unitless value that scales per element as the source does. This single line was worth ~25px of cumulative drift down the page and its absence is invisible until you measure.

**The logo goes through `src/components/Logo.tsx` — never an inline `<img>`.** Twelve call sites across `App.tsx`, `ContactPage`, `DocsPage`, `FeaturesPage` and `LoginPage` each used to hardcode the same ~700-character `lh3.googleusercontent.com/aida-public/…` URL. Three rules the component exists to hold:

- **Local asset, not that CDN.** It was an AI Studio-hosted file the project does not own and cannot re-issue. Measured with the host blocked: every logo in the app rendered as a broken image. `public/logo.png` ships in the repo, and was the favicon too until that moved to its own `public/favicon.png` (see below). Do not reintroduce a remote URL for branding.
- **`width` and `height` are always set, and removing them is a visible regression.** With `h-8 w-auto` and no intrinsic size, the box collapsed to the width of its *alt text* until the image arrived — measured at **106.2px instead of 32px**, so the wordmark beside it started ~74px too far right and snapped left on load. Both dimensions are now declared, and the box stays reserved even when the asset never loads.
- **`className` is layout-only — never pass padding or a border to `Logo`.** Because `size` becomes an **inline style** on both the wrapper `<span>` and the `<img>`, `<Logo size={56} className="rounded-xl border p-2" />` produced a 56px border-box whose content area was only 38px: the img kept its inline 56px height but was shrunk to 38px wide as a flex item, so the contact page's maker mark rendered **38×56 — stretched vertically** — and the padding framed nothing. Framing goes on a wrapper (`<span class="grid h-14 w-14 place-items-center rounded-xl border"><Logo size={38} /></span>`), which gives the same 8px inset the design asks for. The component's own prop docs already said this; the fix was to the call site. Every other call site (`App`, `SiteHeader`, `SiteFooter`, `LandingPage`, `FeaturesPage`, `LoginPage`) passes layout-only classes and was unaffected.
- **Dark mode swaps the file via the `dark:` class variant, not `prefers-color-scheme`.** The app toggles `.dark` on `document.documentElement`, so a `<picture>` media query would ignore the in-app theme switch. Both variants render and Tailwind hides one; swapping `src` in an effect would flash the wrong mark on first paint. `logo_white.png` is the dark-surface variant (white triangle instead of navy) and had been sitting unreferenced.

- **`pin` and `fill` exist for surfaces the theme does not reach, and they are the reason there is still no inline `<img>` anywhere** (2026-08-14). `--paper` is identical in light and dark by design, so on the workspace's report sheet and the landing scanner's page the theme-following mark turns white on white paper and disappears. `HeroScanner` had worked around that with a hand-drawn stand-in — a dark rounded square with a clipped triangle — which at 24px read as a blob with an orange corner. `pin="light"` renders that variant alone and the theme cannot touch it; `fill` sizes to the parent box instead of to `size`, because that page is drawn in percentages and scales with its column, where a px `size` would sit still while everything around it moved. The rule above is unchanged: the asset paths stay owned by this file, and a call site that needs a fixed variant asks for one rather than reaching for `/logo.webp` itself.
- **WebP is offered via `<source>`; the `<img>`'s `.png` is the real fallback, not decoration.** Do not collapse the `<picture>` into a bare `<img src=".webp">`. Verified with `*.webp` blocked: the PNG loads and the layout is unchanged.

**`LogoPulse.tsx` is the only place the mark is animated** (2026-08-26), and it animates *around* the logo rather than the logo itself — which follows directly from the last point in this section: there is no vector source, so there is nothing inside the mark to move. It is the workspace generation card's indicator, and the ring around it is the real progress bar; see *Progress* in [`app-shell.md`](app-shell.md) for which parts of it are measurements and which are decoration, and for the reduced-motion exception it carries. If a second animated placement is ever wanted, extend that component rather than starting a third pattern — the rule about the asset paths staying owned by `Logo.tsx` applies to it too, and it obeys it by rendering `<Logo>` rather than reaching for `/logo.webp`.

Assets were downscaled to 256×256 against the largest on-screen use (56 CSS px, with 3× DPR headroom), then encoded to WebP at q=0.94: **3.28 MB → ~18 KB actually served** (8.4 + 9.5 KB), with the 84 KB of PNG retained only as fallback. The lossy step is measurably invisible — the alpha channel round-trips exactly (`maxAlphaDelta 0`) and the large RGB deltas are confined to fully-transparent pixels where RGB is undefined. **There is no vector source and it is not worth manufacturing one**: the mark is gradient/shaded artwork that only ever existed as raster, so an auto-trace would look worse than what ships. WebP is the end of the line for size here.

**The full-resolution originals (659px and 2048px) are no longer in the repository, as of 2026-08-29.** They sat in `assets/source/`, outside `public/` because anything in `public/` is copied verbatim into `dist/` and keeping them there would have shipped 3 MB of unused PNG. Being outside `public/` kept them out of the *build*; it did not keep them out of the *clone*, and that is what changed. The 2048px white mark alone was 2.5 MB — **half the repository** — carried by everyone who has ever cloned it, to back a 256px derivative committed beside it. `assets/source/*.png` is now gitignored; the files remain on the machine that has them.

Two things follow, and the second is the cost of the decision rather than a detail:

- **Nothing that ships depends on them.** No build step reads `assets/`, and `og-card.html` composites `../../public/logo.png` — the shipped 256px file — not a master. The card, the favicon and the `<picture>` sources all derive from `public/`.
- **A new master will exist in exactly one place.** The last committed copies are recoverable (`git log --diff-filter=D --name-only` for the path, `git show <commit>~1:<path>` for the bytes), so nothing is lost from the era when they were tracked. But if the mark is ever redrawn, git will not be holding the original — whoever redraws it owns keeping it. `og-card.html` stays tracked because it is a recipe, not artwork.

**The favicon is `public/favicon.png`, its own 32×32 file, as of 2026-08-29.** It pointed at `/logo.png` until then, which was the right *format* for the one request that happens before any component code runs and the wrong *size* by two orders of magnitude: `/logo.png` is the 256×256 `<picture>` fallback, so **38,075 bytes** were fetched on the first load of every visit to be drawn at sixteen pixels in a tab strip. The dedicated file is **1,406 bytes** — a 96% cut, and the largest single measured saving the 2026-08-28 cleanup produced. Three things about it are deliberate. **32 and not 16**, so a 2× tab strip has real pixels rather than invented ones; 16×16 was measured at 636 B and breaks up on the mark's diagonals. **PNG and not WebP**, because favicon WebP support is still patchy and this is the one request that cannot fall back. And **`logo.png` was left exactly as it was** rather than shrunk in place, because it has two other jobs: the `<picture>` fallback above, rendered at up to 46 CSS px, and the image `assets/source/og-card.html` composites into the 1200×630 card. If the mark is ever redrawn, `public/favicon.png` is a fourth file to regenerate — downscale it from `public/logo.png`, do not hand-edit it.

The animation dependency is **`motion` v12, imported as `motion/react`** — not the legacy `framer-motion` package, which is not installed. "Framer Motion" below means that import. Every animated file uses `from 'motion/react'`; keep new ones consistent or the bundle picks up two copies.

The division of labour for animation is a convention, not a preference: **hover / press / focus / colour go through the CSS helpers** (`.u-transition`, `.u-transition-fast`, `.u-press`, `.u-focus-ring`, `.u-tap`) in `@layer components`; **mount / unmount / reorder / tab switches go through Framer Motion** using the presets in `src/lib/motion.ts`. Do not hardcode durations or easings in components.

**The workspace is the one exception, and it is deliberate.** Its motion is the artifact's own CSS keyframes and transitions in `src/workspace.css` (`wb-rise`, the caret blink, the progress shimmer), because reimplementing them as Framer variants would have meant re-deriving timings the port was supposed to reproduce exactly. `App.tsx` therefore imports **no** `motion/react` and uses no `AnimatePresence`; only `DURATION` survives from `src/lib/motion.ts`, for the theme-transition class timeout. Reduced motion is still honoured — by the `.wb-root`-scoped media query in that file rather than by the app's `<MotionConfig>`. New animation *inside* the workspace follows the file it lives in; new animation anywhere else follows the convention above.

**Not everything the port brought over was worth keeping, and `.wb-glow` is the case that says so** (removed 2026-08-26, reported as *"some yellowness in the Untitled report area"*). It was the landing hero's orange bloom — a 40px-blurred accent radial at 20% — reused behind the workspace canvas at `inset: -90px … auto …` on `.wb-proof-holder`. That offset is the whole problem: the entire visible part of it fell on bare grid **above** the sheet and none of it ever landed behind the paper, so what rendered was a peach smear across the drafting ground rather than light behind an object. Identical in the empty state and with a report loaded, and it read as a stain in both. The hero can carry it because it sits on a graded background it can bloom into; a white sheet on a ruled grid has nowhere to put it, and a glow repositioned to sit properly *behind* the sheet would be hidden by opaque paper — which is very nearly the same thing as not having one. The rule is gone from `workspace.css` and a comment stands where it was, so this is not rediscovered and re-added. **The general point: a value copied faithfully from the port can still be wrong here, and "it came from the artifact" is not on its own a reason to keep something that looks broken on the surface it actually renders on.**

Reduced motion is covered in three layers, and each one only reaches what the others cannot: the `prefers-reduced-motion` media query in `index.css` reaches CSS transitions only; `<MotionConfig reducedMotion="user">` in `src/main.tsx` covers every Framer animation in the app (transform and layout animations dropped, opacity kept, so content still arrives without sliding); and `respectReducedMotion()` collapses individual layout-affecting variants. New animated components inherit the `MotionConfig` for free — don't reimplement it per component.

`src/main.tsx` is otherwise just the mount point: `StrictMode` → `MotionConfig` → a class `ErrorBoundary` → `App`. Any render-time throw anywhere in the tree is swallowed into a full-page "Something went wrong" card with a reload button, so a crashed app looks like that panel rather than a stack trace — check the browser's DevTools console for the real error.
