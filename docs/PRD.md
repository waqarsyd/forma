# Product Requirements Document (PRD)

## 1. Product Overview
**Product Name:** Forma — DevExpress Report Layout Generator (AI-Powered)
**Purpose:** Automate the creation of DevExpress `.repx` report layouts by analyzing reference images, PDFs, or an existing `.repx` file.
**Target Audience:** Software developers, reporting engineers, and UI/UX designers who work with DevExpress controls.
**Distribution model:** Bring-your-own-key. Forma ships with no Gemini API key of its own; each user supplies their own, and their browser calls Google directly with it. There is no application-owned quota, no server-side key, and no per-user cost to the operator.

## 2. Features

### 2.1 Core AI Analysis
*   **Gemini AI Integration:** Uses Google Gemini to analyze visual documents (mockups, scans, PDFs).
*   **Spatial Mapping:** Understands exact layout coordinates (`LocationFloat`) and dimensions (`SizeF`) of UI elements like Labels, Pictures, Barcodes, and Tables.
*   **REPX Generation:** Generates valid, strict XML conforming to the DevExpress `XtraReportsLayoutSerializer` schema.
*   **Surviving a busy or rate-limited provider (2026-09-08):** Both request paths retry a 503 twice with jittered backoff, then **move to the next model the key was already probed to be able to call** rather than losing the turn — the chat path had the retry and not the fallback until this date, so a 503 on the auto-selected model ended the reply with every alternative sitting unused. A model that stays overloaded is then **skipped for a minute**, so a sustained outage is discovered once rather than re-discovered by every subsequent request at the cost of two retries and six seconds. A **429 is handled as the opposite thing**: it is the key's per-model allowance, not the model's capacity, so it is never retried, the model is parked for exactly the delay Google states in the error, and the user is told *"Try again in about Ns"* in place of the provider's multi-paragraph text. None of this creates quota — the free tier is five requests per minute per model, and one chat turn can spend four of them.
*   **One Artifact, Three Views:** One call returns the `repxContent` XML, and Forma reads the in-browser mockup and the written specification out of it (since 2026-11-05; until then the model wrote all three in one JSON answer, and more than half of what it wrote was the two copies). See *The AI writes the REPX, and Forma reads the rest off it* in `docs/notes/gemini.md`.
*   **Automatic Model Selection:** There is no model picker. On the first generation of a session the app probes a preference list (`gemini-flash-latest` first, then the pinned Gemini 3.x Flash ids and a Flash-Lite, since 2026-11-10; a Pro is reached only through Google's catalogue, ranked after every Flash) with a one-token request and uses the first model the user's key can actually call. The winner is cached for the session. If that model becomes unavailable mid-generation, the app re-detects and retries once, silently. *Rationale: Google retires models "for new users", so a hardcoded id keeps working for existing projects while every newly created key gets a 404 — which is what happened to the previous `gemini-2.5-flash` default.*

### 2.2 User Interface
*   **File Upload:** Drag-and-drop or manual selection for images (`.png`, `.jpg`), PDF files, and `.repx` files, with preview thumbnails. Up to 8 PDF pages are read per file; anything beyond that, an unsupported file type, an oversized file, or a `.repx` that fails XML validation is reported to the user rather than silently ignored.
*   **Source-accurate extraction:** For a digital PDF, Forma reads the file's own text layer — every string with its exact position — and converts those coordinates into the report grid before sending them alongside the page image. The model is instructed to treat that extracted text as authoritative for content and position, using the image only for borders, fills, logos and visual structure. An uploaded `.repx` is likewise parsed as real XML and validated on upload. *A scanned PDF has no text layer; this is detected and reported, and the page is read visually unless the user reads it with OCR first (below).*
*   **OCR for images and scans (2026-11-01):** The chat box reads the text of every attached image and every PDF page with no text layer once the message is sent, behind the scenes, Forma's reply saying how far it has got (since 2026-11-03; as it was attached until then, the attachment's chip showing it), with Tesseract.js running in the browser, so nothing an upload holds leaves it. Every word and line comes back with its box and confidence, placed in report units; text that lines up in rows and columns becomes an XRTable, the rest XRLabels, and a word read below 60 is flagged rather than taken silently. The text goes with the message on its own, for the model to build from; the image viewer a sent page's thumbnail opens also offers a review (since 2026-11-04) that draws what was detected over the source, the unsure text listed, from which the `.repx` can be built straight from the layout, with no model involved and after the app's own checks. The engine, about 7 MB, is served from Forma's own site and downloaded once, the first time it runs. **It reads Arabic, Hindi, Urdu, French, German and Spanish too** (2026-11-04), and works out which itself: every page is read in English first, a page English reads confidently is checked for French, German or Spanish words, and one it garbles is probed with Arabic, Urdu and Hindi, the winner reading the page again with English (the user ticked languages in Settings for one day before that). Each language is its own 0.7 to 2.1 MB of Tesseract data, served from Forma's site like English and fetched only when a page needs it. The direction marks Tesseract puts around a right-to-left word are dropped. Checked in the owner's Chrome: a French, an Arabic and a Hindi line read with those languages chosen; French lost its accent and Hindi a number, which is Tesseract's reading, not Forma's. **It reads English handwriting too** (2026-11-04), when a page reads as English with enough lines left unsure: the lines Tesseract read below a confidence of 70 are read again by TrOCR-small-handwritten in the browser. Measured before it was built, on 60 real handwritten lines Tesseract got 47.4% of characters wrong and this 10.6%, with printed lines still exact. The model and its runtime, about 88 MB the first time, are served from Forma's own site, the owner's choice over a CDN: the deployed site serves them when `npm run fetch:handwriting` ran before its build, and without them OCR keeps its own reading. **Since 2026-11-10 an English page is read by PaddleOCR** (PP-OCRv5 mobile, PaddlePaddle's own ONNX models, Apache-2.0), in browser workers on the ONNX Runtime handwriting already loads: measured on the company's private pages, it found 97% of the characters DevExpress printed where Tesseract found 61%, and Forma's box reader put 65% of texts in the right band and role from its reading against 59% from Tesseract's. Tesseract still reads every other language, and any page PaddleOCR reads less than 60% of the text regions of, which is how a page in another script shows. Its 12.7 MB of models are served from Forma's site when `npm run fetch:paddle` ran before the build (`scripts/deploy.mjs` runs it), and fetched by a browser the first time it reads a picture. *Not yet: handwriting in Arabic, Hindi or Urdu, which no free browser model reads.*
*   **Chat Interface:** A real conversational assistant. Messages without an attachment are answered as chat — asking a question or saying hello gets a reply, not a report. A message *with* an attachment, or one the assistant judges to be an actual request to build or change a report, runs generation. Refinement turns send the previous layout and REPX so the model edits the existing report rather than regenerating it. **One composer does both jobs** — there is no separate chat box, and which job runs is decided from whether anything is attached; a message that fails is marked in place with a *Try again* beside it rather than left looking merely unanswered. **The transcript follows the conversation** as of 2026-09-08 (it had not since the 2026-08-12 port, which took the sentinel element the scroll effect pointed at), and it stops following while the reader has scrolled up to re-read something, resuming when they return to the bottom. **A request already in flight refuses a second one** — Enter used to bypass the send button's disabled state entirely, re-entering generation while the first was still writing to the same progress state. **A sent message can be edited or withdrawn** as of 2026-11-04: an edit sends the changed text again from that message on, as *Try again* does, and a withdrawal takes the message and Forma's answers to it out of the transcript, and so out of what the next turn sends; the report a turn built stays. A message sent with pictures is withdrawn but not edited, since an edit sends text only. **The transcript can be searched** from the Chat header: only the messages holding the words are drawn, each match marked. **Since 2026-11-10 the chat works as an agent:** a plain question about the open report's fields, totals, groups, bands, parameters or paper is answered from the file by Forma with no AI and no request; those facts go to the AI beside the outline, and an edit or a reply naming a field the report's data lacks is declined or flagged; a question about Forma carries the Docs articles it is about, which the AI answers from; and three files or nine pages are answered first with a plan, changed and started in the thread, nothing read or sent before. Asked to translate the report into a language, the chat offers a button and, pressed, translates every typed caption and title in one request, the layout untouched, as a revision beside the original (2026-11-10). A question about the data (which row is highest, what the amounts add up to) is held the first time and Forma asks whether the rows the Preview prints may go to the AI, saying how many and which fields; sent, the reply says so, and live rows from the companion never go (2026-11-10). A control's right-click menu has Describe for the AI: a sentence about what the control is for, written to its AccessibleDescription and shown to the AI with the outline, so a request can name the control by what it does (2026-11-10). *Not yet: editing a message sent with pictures.*
*   **Forma's own model (2026-11-02), and the key as the way in (2026-11-05):** Forma learned a house style and 14 kinds of report from the structure of the owner's 359 DevExpress reports, never their text, names, queries or pictures, which stay off the repository. From 2026-11-02 to 2026-11-05 the workspace worked with no key, a request in words designed by that model and an image built from the text OCR read; on 2026-11-05 the owner made the key the entry point again, so with no Gemini key the chat box is locked and Settings asks for one, whichever AI is chosen, and the model stands in only when the AI cannot answer. When it does, a picture's report is OCR's reading put in its bands with each text's role by Forma's box reader (2026-11-04), a small model learned on the CPU, so its records print from bound fields; a page the reader would lose too much of is built as OCR's copy. A free Gemini key opens everything; a local AI or OpenRouter can then design instead of Gemini. See `docs/proposals/own-model.md`. Settings chooses the AI: Automatic (Gemini with the key), a local AI through Ollama or LM Studio, or OpenRouter's free models, each through the same pipeline; Forma Offline and a separate Gemini choice went into Automatic on 2026-11-05. Forma remembers how its user works (2026-11-02): "remember: always use A4" and the style of the reports they keep apply to every report after, in this browser only, listed in Settings to switch off, change or forget. *Not yet: a vision model that reads a page better than OCR does; the box reader is two small networks over OCR's reading, not a model of the picture.*
*   **Learning from use (2026-11-10):** Every report generated, every edit made in the chat, every translation and every rating of a reply is kept as a learning event, structure only by default (the report's skeleton, never its text; the request's kind; which kind of AI answered; the edits' names; the checks' counts) and, on an opt-in switch, the whole report and the words with it. Kept on the device and, signed in, under the account in Firestore, where the person sees and deletes it (Settings → Learning) and the owner pulls it to train Forma's own model (`scripts/model/pull-learning.ts`). The privacy policy says so; see *Learning from use* in `docs/notes/persistence.md`.
*   **Every part of Forma on each request (2026-11-03):** With an AI chosen, a request no longer takes one path. OCR reads the words. Forma's own vision model, when the user runs one on Local AI and names it as a helper, reads the layout, and OCR's words go into its boxes; that draft is told to the AI. Without one, Forma's box reader puts OCR's words in their bands, and that is the draft. For a report described in words, the house style Forma's own model learned is told instead. Both are hints that the picture, the user's preferences and the user's words overrule. The reply names who took part. When the AI cannot answer (a quota, the network, a local server that is off), Forma's own draft becomes the report in place of an error, and the reply says why and what it was made from. See *One request, every part of Forma in its role* in `docs/notes/app-shell.md`.
*   **Prompt-to-Report (2026-10-28; in the chat box since 2026-11-01):** A report from a written description and no source document, modelled on the *AI Prompt-to-Report* page of DevExpress's own Report Wizard, whose pages were read out of its Web Report Designer's scripts with REA rather than taken from the documentation. A report asked for in the chat with no attachment and no report open is designed from the words: an empty conversation shows nothing (it offered six **predefined prompts** as starting points until 2026-11-05, when the owner asked for the chat to show none of that; since 2026-11-06 the same six are on the empty workspace's home instead, as Google Stitch's home offers its suggestions, each putting its description in the box to be edited before sending), and a fenced code block or a `CREATE TABLE` in the message is taken as the **data source** in the Data tab's paste form — a JSON row, a CSV export or a `CREATE TABLE` — whose fields become the only names the report may bind to. A cheap **clarification** call runs first, which may come back with up to three questions, each with a suggested answer, when the description leaves content genuinely open (which columns, what to group by); they are asked in the thread as a form, answered there or by typing a reply, and the answers are appended and generation runs. (Until 2026-11-01 a separate dialog, opened from a button beside the paperclip, did this.) In description mode the prompt opens with the description instead of "analyze the provided image(s)", the optional prompt sections are chosen from the description's words, and **overlapping controls are resolved automatically** after the repairs — DevExpress's `FixLayoutErrors`, applied only here because with a source image an overlap may be faithful to it. A report that still carries audit **errors** is sent back once with the errors listed (DevExpress's `RetryAttemptCount`); warnings never are. *Deliberately not copied: page orientation (`reportGeometry.ts` has no landscape page), a persistent prompt catalogue, and a test-data preview. Not yet measured: no fidelity case exercises this path.*
*   **UI Layout Mockup ("Mockup" tab):** Renders the generated layout as a scaled, fit-to-width page preview, aiming to visually match the uploaded design. Text carries bold, italic, font family, size, colour, alignment, wrapping, and per-side borders. Grids render their real rows and cells. Logos and pictures are cropped out of the user's own upload and shown as the actual artwork. Charts follow the detected chart type and approximate values. *Gauges and barcodes remain decorative placeholders, and charts are stylized rather than drawn by a charting library.*
*   **Specification and XML ("Spec" and "REPX" tabs):** The result pane is a five-way switcher — **Mockup**, **Preview**, **Data**, **Spec**, **REPX** — grown from the three-way switcher of the 2026-08-12 workspace rebuild, which itself replaced two tabs with a nested sub-view. **Spec** renders the model's markdown write-up (component inventory, coordinates, styles). **REPX** shows the generated DevExpress XML itself — re-indented, syntax-coloured, with line numbers, a line/character count, and a one-click **Copy XML** action for pasting straight into the designer. A validity check runs on the XML and reports whether it parses, whether the root element is `XtraReportsLayoutSerializer`, and whether it contains any `<Bands>` — so a malformed generation is visible here rather than surfacing later as a refusal in DevExpress.
*   **Gauges and sparklines:** A dial or a trend line in the source becomes a real `XRGauge` or `XRSparkline`, carrying its value, range and target. Syntax measured with `RepxProbe emit-gauge`, and the reason it exists is the divergence the prompt forbids everywhere else: `gauge` was a valid element type in the `layout` schema all along while the prompt gave no REPX syntax for one, so the model could draw a gauge in the mockup that the exported file would never contain. *The mockup still draws a positioned placeholder rather than a needle — the file carries the control, the picture approximates it.*
*   **Charts and cross-tabs:** A chart in the source document becomes a real `XRChart` with a series bound to the fields the axes name — `ArgumentDataMember` for the categories, `ValueDataMembersSerializable` for the figure — rather than a picture of one built from labels and rectangles. Bar, line, area, scatter and pie are supported; a bar series writes no view type because that is DevExpress's default, and a pie takes no `<Diagram>`. A matrix whose rows *and* columns are both values from the data, with a figure at each intersection, becomes an `XRCrossTab` with its three field collections; a grid with fixed headings stays an ordinary table, and the prompt states that distinction because it is the one that decides between the two. DevExpress will not print a cross-tab written as its fields alone, so `repairCrossTabs` adds the column definitions, row definitions and cells DevExpress generates from those fields, and sizes the grid as DevExpress does. *Syntax measured with `tools/RepxProbe emit-chart` — see the 2026-09-05 section of [`docs/notes/gemini.md`](notes/gemini.md), which also records the pattern four measurements have now confirmed: an item inside a collection carries no `ControlType`.* The **Preview** draws a chart as its **structure and binding, not as invented data** — a bar outline captioned "Amount by Region" — because plotting made-up numbers on a page someone is checking for accuracy would be worse than plotting none, and DevExpress prints a chart as one picture. A cross-tab with up to one field of each kind is drawn over the test data as DevExpress prints it: sums in the data's own type, Grand Totals, its rows growing the control, and the same grid in the CSV and Excel exports. Any other cross-tab, or one with no test data, is drawn as its fields in place. The audit warns about a chart with no series and a cross-tab with no data field, which print an empty frame or a grid of empty cells that reads as "the data has not arrived yet". It reports a cross-tab without the generated layout as an error, because DevExpress cannot print it. **A chart's title, axis titles and legend come from the source** (2026-11-04): the prompt asks for them in the source's words, as the serializer writes them (`RepxProbe emit-chart-titles`, loaded back: `<Titles>` items with no `ControlType`, an axis's `<Title Visibility="True">`, `<Legend>` with its visibility and alignment) and none the source does not show; the Preview draws the title, the axis titles and the legend where the file puts it, or none when it is hidden; the Mockup draws the title and axis titles around its chart from the layout. *Not yet: the Mockup's chart is still Forma's own stylised drawing of the chart, not the picture DevExpress prints.*
*   **Forma's own PDF (2026-11-01, PDF/A 2026-11-02):** Beside **Export PDF**, which is the browser's print of the Preview, **PDF with outline** writes a PDF Forma serializes itself from the Preview's pages: the report's bookmarks become its outline as DevExpress exports them, it is encrypted under the report's own passwords at the level the report names, and when the report's export options ask for PDF/A it is written as PDF/A-1b, 2b or 3b, with the Liberation fonts made to Arial's, Times New Roman's and Courier New's widths embedded, an sRGB output intent and XMP metadata, checked with veraPDF. A report asking for PDF/A and a password is refused with the reason, as DevExpress refuses it, because PDF/A forbids encryption. Pictures (`XRPictureBox`, 2026-11-04) are drawn as DevExpress prints them, in every `Sizing` mode, and the PDF, image, RTF, DOCX and HTML exports carry them; turned text (2026-10-31) prints at its angle. Turned text longer than its box prints the lines DevExpress keeps, a last line ending inside a word included (parity row 54, 2026-11-04). *Not yet: an image bound to data or loaded from an `ImageUrl` (the Preview draws a dashed box saying which).*
*   **Revisions (the "Revisions" rail panel):** Every generation, refinement and binding pass is kept, newest first, with **what it changed** — a structural diff by control name: added, removed, moved, resized, retyped, plus any change in band count. Restore puts an earlier version back. Two things make it useful rather than decorative. *The diff is structural, not textual*: the model rewrites whitespace and attribute order freely between generations, so a line diff of two REPX files is almost entirely noise, and controls are matched by `Name` rather than position so inserting one near the top does not report everything below it as changed. And *restoring is itself recorded*, so returning to an older version does not lose the newer one — otherwise Restore would be the very trap the panel exists to remove. A refinement that changed only the markdown wording pushes nothing, because the report did not change. *Nudging a control is deliberately **not** a revision: the Preview pane has its own undo, one entry per gesture, and duplicating that here would bury the three or four versions somebody wants under forty nudges of a label. Both mechanisms exist because they answer different questions — "take that back" and "what did this report look like before I asked for that".* **Signed in, the newest ten are saved with the project and come back when it is reopened; signed out, they live for the session.** The split is a decision rather than an omission at either end. They are a Firestore *subcollection* rather than a field because a saved report is budgeted at 900 kB (§5, `persistence.md`) and one result can be 50–200 kB, so ten inline would break the budget several times over; each version is its own document with its own ceiling. And they are not written to `localStorage` at all, because that is one shared 5–10 MB quota across every project, and a megabyte of history per report would evict the projects themselves. The panel says which of the two you are getting. *Deleting a report takes its history with it — Firestore does not remove a subcollection with its parent document, so the obvious `deleteDoc` would strand every version and look like it worked; `deleteReportAndVersions` is the only path, and `tests/accountDeletion.test.ts` asserts the absence from both the report and the account direction.*
*   **Batch intake (the "Batch" rail panel):** A folder of legacy reports in, a queue of `.repx` out. Each source document becomes **its own report** — which is the opposite of attaching several files to the composer, where several pages build *one* report. The two are indistinguishable from the files themselves, so the distinction is made by where they are dropped, and the panel's empty state says so. Files and **whole folders** go in through the two pickers or **by dropping them on the panel** (2026-11-04); a folder is opened to its last file, queued in path order, and what the batch cannot read is left out and counted. Files are generated **one at a time** by default: the user's own key carries the quota and forty parallel requests turn a slow success into a fast 429. **At a time** offers two or three for a key whose quota allows it, never more, and a quota failure still stops every file. Each row shows the audit's verdict in the words the REPX pane uses — *clean*, *N warnings*, or *N errors — content will be lost* — because the point of running forty files is knowing which of the forty are worth opening. A finished row opens in the workspace or downloads on its own; **Download as .zip** takes them all at once. A quota, key or permission failure stops the run rather than producing forty identical errors; **Stop** cancels what has not started and leaves the request in flight alone, since it is already billed to the user's key; **Retry** requeues the failed and cancelled files and keeps what succeeded. Since 2026-11-10 the batch is kept in this browser as it goes (its queue, each finished report and the source files), so it carries on after a reload or the next day: each file asks the next AI the user set up when one reaches its limit, and when none is left the batch pauses, kept, and **Retry** carries on from there. A plan in the chat hands it the files of one message, a report for each. A sign-out deletes the kept batch. *The archive is written by `src/lib/zip.ts`, a store-only ZIP in ~150 lines rather than a ~30 kB dependency — verified by opening its output with .NET's own `ZipFile` reader, not only with its own tests.* **This is the migration story, and the one thing a prompt-driven competitor structurally cannot offer**: you can describe one report to an assistant, but not forty you have never read.
*   **Report parameters:** When the source shows the reader being asked something — a "Date range: ___ to ___" line, "Region: All", a filled-in criteria block — the generated report declares a `<Parameters>` collection and uses each one, either in the report's `FilterString` (`?DateFrom`) or in a control's expression (`[Parameters.Region]`). The **Preview** tab lists them above the paper, because DevExpress asks them before the report prints. Over test data each one takes a value there, which wins over the default, and the report's filter keeps only the rows it is true for (2026-10-30, measured against DevExpress). The audit reports both directions of misuse: a `?Name` or `[Parameters.Name]` with no matching declaration (the filter fails at run time and the expression prints nothing) and a declared parameter nobody uses (the reader is stopped and asked a question that changes nothing). *Deliberately a warning rather than an error — the reference scan is a text scan, and `Text="Ready?Now"` is indistinguishable from a filter reference.*
    **A parameter's type is the one thing the model cannot write correctly**, and it fails silently: DevExpress accepts `Type="System.DateTime"` written inline and loads a `System.String` holding the date as text, so the report's date filter then compares strings. The real form is a `#Ref-N` pointer into an `<ObjectStorage>` block at the end of the document, which needs a `Ref` unique across a section the model never sees. So the prompt asks for the readable inline type and `repxParameters.ts` converts it — the same arithmetic-on-the-output shape as the margin lift. Measured with `tools/RepxProbe emit-params`, and the conversion's output was loaded back through DevExpress to confirm the parameter really is a `DateTime`. **A parameter's value is set in the Preview** (parity row 11, 2026-10-30): with test data each parameter has a field above the paper, *Asked before printing*, and the report's `FilterString` and any `?Name` in an expression read what is typed, which wins over the file's default as DevExpress printed in case c07. This sentence said "not yet" until 2026-11-04, a week after it was built. *Not yet: a parameter's lookup values offered as a list, and a multi-value parameter chosen value by value rather than typed.*
*   **Grouped reports:** When the source document breaks its rows into runs by a shared value — a "North Region" heading line inside the table, or a "Region total" subtotal repeating partway down — the generated report carries `GroupHeaderBand` and `GroupFooterBand` with a `<GroupFields>` collection naming the field the rows break on. A per-group subtotal is a cell whose `<Summary>` carries `Running="Group"`, which is the only thing distinguishing it from the grand total in the ReportFooter. The prompt states a **visible test** for grouping rather than leaving it to judgement, and says to omit both bands when the design shows no break: a flat list with one total at the bottom is an ungrouped report, and inventing a grouping changes what the file prints. *The syntax was measured with `tools/RepxProbe emit-group` against the installed DevExpress 20.1 rather than taken from the class reference — see the 2026-09-05 section of [`docs/notes/gemini.md`](notes/gemini.md).* The audit reports the two ways grouping fails silently: a group header carrying no fields (it groups by nothing and prints once, looking like a heading) and a group footer with no header (its subtotal becomes a second grand total). **The grouping field is chosen in the Preview** (2026-11-04): *Grouped by* above the paper lists each group header with the field it breaks on, offering the fields the report binds and the test rows hold. A choice rewrites the band's `<GroupFields>`, and its own `[Old]` bindings follow, so the heading prints what it now groups by; Undo takes it back. A header grouping by nothing gets a field list with a fresh `Ref` (`lib/repxGroupField.ts`). **More than one group previews over test data**: the pages break at each new value and print a header and footer per group, as parity case s19 measured, which the "the preview has no data" this line said until then no longer describes. *Not yet: adding or removing a grouping level, and sorting a group descending, from the UI.*
*   **Direct manipulation (in the "Preview" tab):** Controls are selectable, draggable and resizable, and a label can be retyped by double-clicking it. Arrow keys nudge the selection one report unit at a time, Shift+arrow ten — the precision half, since a drag gets close and one unit at a time gets exact. Every gesture writes straight into `repxContent` by splicing the control's opening tag, so attributes Forma does not model (`Padding`, `StylePriority`, anything a later DevExpress version adds) survive untouched. There is an undo stack with a **Undo** button and Ctrl+Z, one entry per gesture rather than one per mouse move. The toolbar names the selection and its geometry, and **says when a control has been dragged past its band's height** rather than preventing it: that is a real edit with a real consequence — the designer pushes the band taller or drops the control onto a second page — and refusing the drag would be guessing at what was meant. *Editing lives on **Preview**, not on **Mockup**, and that is the point: the mockup draws the layout, which is a picture of the uploaded document kept for comparing fidelity, so an edit there would change nothing about the exported file and there is no reliable way to map a layout element back to a REPX control — they share no identifier. The preview draws the REPX itself, so the thing dragged is the thing downloaded.* Editing the REPX leaves the layout and the specification alone, because they still describe the source document. **Since 2026-11-04 a control can be deleted and a label added, a table cell retyped, and several controls selected.** Shift+click adds a control to the selection or takes it away; arrows, Delete and a drag act on the whole selection as one undo step. **Delete** (the key or the button) declines a control another part of the report names by `#Ref` (a drill-down toggle, a cross-band line's ends) and says why, since a dangling reference can stop DevExpress loading the file. **Add label** puts a label under the selected control, or at the top of the records, in the band's own `Dpi`. Double-clicking a table cell retypes it, and a cell bound to a field is declined, because the binding is what prints. *Not yet: adding controls other than a label, copy and paste, and aligning or distributing a selection.*
*   **Data binding ("Data" tab):** Where the report stops being a picture. The user pastes what they already have — a JSON row or array, a CSV export, a `CREATE TABLE` statement, or a plain list of column names — and the format is detected from its shape rather than chosen from a dropdown. Forma reads the field names, their types and a real sample value, suggests which report column each field belongs to, and lets the user correct every pairing before anything is written. **Apply** writes an `ExpressionBindings` element onto each mapped cell in the Detail band, plus a `TextFormatString` where the column is plainly money or a date; the cell keeps its `Text` as a fallback and unmapped columns are left untouched. Where the ReportFooter has a figure under a money column, Apply also totals it, with the `<Summary Running="Report" />` DevExpress needs and a money format. *Until 2026-10-30 it wrote the total without that element, and DevExpress prints such a total as an empty cell; that was found by printing the file, see `docs/proposals/devexpress-parity.md`.* *This replaces guessing the field name from the column heading, which is what `VITE_FORMA_BIND` did between 2026-09-04 and its removal on 2026-09-05: "Item Description" becoming `[ItemDescription]` is the report's opinion of what the data is called, and against a source whose column is really `DESCR` it produces a file that opens cleanly and fails when it runs.* **Nothing connects to a database**, deliberately and for the same reason as §5's key argument: a live connection means credentials, which means either a server holding them — out of scope per §6 — or a browser reaching a customer database directly. A pasted sample supplies everything binding needs and none of what that would cost. **SQL Server, without a connection (2026-11-08 and 9, the owner's programme, Phase 1):** a read-only script the user runs in SSMS exports the database's layout (tables, views, procedures with their parameters and what they return, keys), and a second one sample rows; both are read in the browser and kept on the device, up to five databases, removed on sign-out. On the Data tab the user browses it, chooses what the report reads (a table or view with the joins its foreign keys suggest, a stored procedure, or custom SQL held to the layout, writable from a sentence), and writes it into the report as DevExpress's own `SqlDataSource`, measured with `RepxProbe` and filled and printed by DevExpress over a made-up LocalDB database: parameters typed and lifted, several values, lookup lists and their cascade, master-detail bands with totals, calculated fields, a result schema, and **the connection by name only**, as the user's application config knows it, so no password is ever written. The AI binds a report to the real columns only when the user shares the layout with it (attaching it, or a switch on the Data tab): it names the query, Forma holds every name to the layout and writes the source. The chat changes what the report reads and groups it, in place. A report's own data source is shown, kept through a redesign, and checked against a newer export, with a fix for each drift; DevExpress refuses to print a report whose query names a column the database no longer has. Binding declines rather than guessing whenever the correspondence between the heading row and the detail row cannot be proved — a differing column count means a merged heading cell — and that decline is rendered as the content of the pane, because it is usually a real finding about the report. A report that is already bound shows what it is bound to; re-binding is declined so a second pass cannot discard work done in the designer. **Prompt-to-Expression (2026-10-28):** a column can be bound to an expression instead of a single field. Describe it in a sentence, a line total as currency, a date in a given format, an Overdue flag, and the model returns a DevExpress criteria-language expression that is checked against the pasted fields before it can be used; a reference to a field the data lacks is reported and blocks the Use button, because such a cell prints blank with no error. DevExpress's Filter and Expression editors carry the same converter.
*   **Print preview and PDF export ("Preview" tab):** The fourth pane, and the only one drawn from `repxContent` rather than from the `layout`. It reads the exported REPX back, applies the band rules — Detail once per record, PageHeader and PageFooter on every sheet, ReportHeader once, ReportFooter after the last record — and lays the result out across real pages at true size. **This is what closes the loop:** until it existed, nothing in the product showed the user their report paginated, and nothing checked the artifact they actually download. A report whose Detail band is the height of the page looks correct in the Mockup and shows itself here immediately, one record per sheet, with a warning naming the measurement. The record count is not synthetic — it is the number of rows the model read out of the user's own document, so the band repeats over their data. **Export CSV** (2026-10-30) downloads the report as DevExpress exports CSV, one line per row of the layout holding the printed text, and matched DevExpress's own files byte for byte. **Export XLSX** (2026-10-30) downloads it as DevExpress exports a workbook: one sheet laid out as the report, numbers and dates kept as values with the format string converted, links kept, cell for cell the same as DevExpress's own. **Export PDF** prints the pages through the browser, which produces a true-to-size PDF with selectable text and vector rules and adds no dependency to the bundle; `@page` is emitted from the report's own dimensions so the paper matches the design. Band tints and labels are screen affordances and are hidden in the printed output. Each control is drawn in the appearance DevExpress itself resolves, not just the attributes it writes: a style sheet beats a control's own value unless the control hands it back with `StylePriority`, and anything unset inherits from the cell's row and table, the panel, the band and the report (2026-10-30, measured by printing through DevExpress). Text grows its control and its record as DevExpress grows them, measured in the browser's own copy of each font, and a record that does not fit is split at a line across the page break, or moved whole when the band says `KeepTogether`; so the pages break where DevExpress breaks them. *There is still no live data source: by default the preview repeats one record's worth of content, so it proves the band structure and the pagination, not the data.* **A SQL Server database's sample rows (2026-11-09):** with the database's layout and sample rows, **Sample rows** fills the Preview from them with no request, the query's joins, sort and filter applied, each field typed as SqlClient hands it to DevExpress (every common type measured against DevExpress's own print, decimal scale and leading zeros included), each detail report's rows nested by its relation, and every parameter asked by its type or from its lookup list. **Test data (2026-10-28):** for a report the Data tab has bound, a **Test data** button asks the model for up to twenty plausible rows keyed by the bound fields, and the Preview prints them into the Detail band, one record per row, so grouping, totals and column widths can be seen before export. DevExpress's designers have the same button beside Design and Preview; Forma's needs bound fields first, because the rows are keyed by them, and the rows are discarded whenever the set of bound fields changes. **Over those rows every binding is evaluated as DevExpress evaluates it (2026-10-30):** expressions, calculated fields, totals, running sums and page totals in their scopes, and each `TextFormatString`, with .NET's arithmetic and rounding. Printed through DevExpress for comparison, an invoice with a calculated line total, page totals and a grand total came out with all 175 of its texts identical, on the same pages. **Groups come from those rows too (2026-10-30):** the records are sorted by the group fields and Detail's sort, each group prints its own header, records and footer, and repeated headers, `GroupUnion` and `PageBreak` behave as DevExpress printed them. Nested groups follow `Level` the way DevExpress does, which is not the file order. An empty set of rows prints the way DevExpress prints an empty data source: one page, the Detail band once and blank, with every header and footer around it. Conditional formatting rules fire per record over those rows, as DevExpress applies them. A subreport that embeds its report is drawn in full inside its box, which grows to hold it; one that loads another file is a labelled box. A detail report prints under every master record. Because the test rows are flat and carry no relation, each master shows it as DevExpress prints a master with no related rows, and the pane says so.
*   **Page margins, declared rather than drawn:** The prompt pins `Margins="0, 0, 0, 0"` with both margin bands at zero, deliberately — it makes a band's coordinate space identical to the paper's, so the model can write paper-absolute coordinates with no subtraction, and asking it for real margins instead hands it arithmetic on every coordinate that fails silently when it goes wrong. The model still reproduces the design's margin; it just *draws* it by pushing controls inward. So `repxMargins.ts` measures the content box after generation and moves that whitespace into `Margins` and the two margin bands, subtracting it back off the coordinates — a pure translation, same ink in the same places, with the structure a printer and a designer both expect. It declines rather than guessing when the content reaches the paper edge, which is what a full-bleed design looks like. **An empty report gets `20, 20, 20, 20` with both bands at 20 (2026-09-08)** — what DevExpress's own designer writes for a new report, checked against a real one — because with nothing placed there is nothing a margin can move or clip. Twenty is safe on that path and nowhere else.
*   **Export:** One-click download of the generated `.repx` file, named after the report title. Falls back to a `.txt` of the specification if the model returned no XML.
*   **Progress Tracking:** Step-by-step status labels, a percentage bar, and a live elapsed timer during generation. The response is streamed, so once the model begins writing, the bar and the character-count readout beside the stage label ("12,480 chars") reflect real output rather than a timer. *The opening phase — model detection and upload — has no signal available and still runs on a simulated cadence; the streamed phase is capped at 99.9% and only `finishProgress` writes 100, so the bar cannot claim completion before the result is parsed. Stop genuinely aborts the in-flight request, but cancellation is client-side, so Google may still complete and bill the generation. Since 2026-11-04 the progress is not drawn: the chat shows Forma's answer as three working dots, the measured progress is read to a screen reader, and Stop is the composer's send button while a generation runs; pause and resume were removed.*
*   **The conversation floats over the report (2026-11-05):** As Google Stitch's workspace does, at the owner's request. The report fills the bench; the conversation floats over it in three pieces: a card at the top left showing one request at a time (the message in a pill, Forma's reply under it, folding to a mark), a log at the bottom left listing every request, and the box as a bar at the foot. The side column holds the other panels only. See *The conversation floats over the report* in `docs/notes/app-shell.md`.
*   **Open in designer and Forma Designer for Windows (2026-11-09):** At the owner's request, a report opened in the designer on a PC without DevExpress asks for it. Open in designer is a dialog (`OpenInDesigner.tsx`, steps decided by `designerStep` in `lib/designerBridge.ts`) that asks the companion only when clicked, from the website too since that day, and says what is missing: Forma Designer (linking `/download`), DevExpress Reporting or a version older than 20.1 (linking only devexpress.com's free trial, as a separate commercial product), the browser's permission to reach apps on the device, or Windows; every step offers Export .repx. The companion is downloadable as Forma Designer, a self-installing per-user exe with no DevExpress file in it, on GitHub Releases, unsigned, with its SHA-256 on the page; it finds whichever DevExpress is installed (measured on 20.1; newer versions load through the same resolver and are the owner's to check). Its readme and code are `tools/RepxDesigner`.
*   **Mobile Layout:** None, deliberately. The workspace is a fixed three-column frame (rail, side column, bench) with no breakpoint behaviour. The earlier build turned the chat and canvas into tabs below `md` and flipped the user to the canvas on a finished result; the 2026-08-12 rebuild ported an approved desktop design that carries no mobile arrangement, and inventing one would not have been a port. A mobile layout is a design task, not a CSS one.

### 2.3 Account and Cloud Storage
*   **Authentication:** Firebase Auth — Google account sign-in plus email/password sign-in and sign-up, in one dialog that switches between the two modes. Escape closes it.
*   **Sign-in validation:** Every field is checked in the browser before a request is spent, and each problem is reported directly beneath the field it belongs to rather than in a single shared banner. Enforced: email format, password present, a 6-character minimum on sign-up, and a matching confirmation. A too-short password reports its own length problem rather than surfacing as "passwords do not match" against a half-typed confirmation. Errors clear as soon as the user starts correcting the field, and switching between sign-in and sign-up clears both the errors and the typed password. Email and name are trimmed on submit, so a pasted address with a leading space is not rejected. Fields carry autocomplete hints so password managers fill them correctly.
*   **Password reset:** "Forgot Password" sends a real reset email to the address entered in the form. It reports the same "if an account exists for that address…" wording whether or not the account is found — see §5.
*   **Account management (the account dialog):** Rename, change password, change email, delete account — reachable only from the workspace rail's account menu, because that is the one place a signed-in person is working. Four rules hold it together. **Sensitive actions re-authenticate**, since Firebase refuses a password change, an email change or a deletion without a recent sign-in: password accounts re-enter their password, Google accounts go back through the popup. **Changing the email verifies the new address first** — `verifyBeforeUpdateEmail`, so the account moves only once the new inbox has been clicked through and a typo cannot lock anyone out. **Deletion is typed out in full** (`DELETE`) and says what it removes, because it discards the saved reports and the encrypted key with the account; the order that deletion happens in is not interchangeable and is described in §5 and in [`persistence.md`](notes/persistence.md). And as of 2026-09-08, **each action asks for its own password, in its own section**: one shared field sat behind all three with inputs in only two, so the email change required a password typed into a field in the other column with nothing saying so, typing a password to change it also filled the delete confirmation, and satisfying one section silently armed the guard on another. The new password is now typed twice, as sign-up already asked, because a typo here sets a password the owner does not know and they find out at the next sign-in on another device. The surface is covered by `AccountDialog.test.tsx`; what a deletion actually removes is proved separately against the emulator in `tests/accountDeletion.test.ts`, because a mocked Firebase can prove neither.
*   **Save:** The open conversation and its report are saved on their own after each turn, into the open project, and the Save action saves at once (since 2026-11-05; until then only Save saved, and each press listed the project again). A reload reopens the project that was open in that tab. Signed-in users write to Firestore under `users/{uid}/reports`, with the report's newest ten versions in a `versions` subcollection beneath it; signed-out users fall back to browser `localStorage`, which takes the report but not its history. Saved reports contain the conversation and the result only — never the API key or the report configuration.
*   **Sharing a report (2026-11-06):** Share, beside Export, as Google Stitch's: a signed-in owner shares a **copy** of the report (its title, REPX and layout, never the conversation) with people added by email or with anyone who has the link, and opens, updates or stops it from the same dialog. The link, `/s/{id}`, opens a read-only page with the Preview and the `.repx` to download. A restricted share opens only for an invitee signed in with that **verified** address; the id is 22 random characters. Forma sends no email (it has no server); the owner sends the link. Deleting the project or the account deletes its shares. Needs `firestore.rules` deployed; see `docs/notes/persistence.md`.
*   **Saved projects and recents:** Two panels on the workspace rail — **Saved projects** lists saved reports to reload or delete, **Recent** lists the current session's history. They replaced a single history sidebar in the 2026-08-12 rebuild; the rail is the whole navigation, and the panel it selects fills the review column.

### 2.4 Configuration & Settings
*   **API Key:** The user pastes their own Gemini API key into the config modal. **It gates the entire workspace** — chat, generation and refinement all require it. Without one the composer is disabled and a banner explains why, rather than letting an attempt fail; any action that needs it opens the modal instead. A "Check key" action validates it by attempting a real one-token generation and reports which model it resolved to. **Clear** removes it from the tab immediately. The modal links to Google AI Studio for obtaining a free key.
*   **Key Storage:** The working copy lives in `sessionStorage` and is erased by the browser when the tab closes. Signed-in users may opt into cross-device sync, which encrypts the key **in the browser** under a user-chosen passphrase (PBKDF2-SHA256, 310,000 iterations, per-record salt and IV → AES-GCM) and uploads only the ciphertext. See §5.
*   **Settings Forma works out (2026-11-04):** none of the following is asked any more; `lib/autoConfig.ts` reads each from what a request brings, in this order: an uploaded or open `.repx`, a PDF page's size or a whole-page picture's shape, the words typed or read, the version and unit learned from the last report the user brought, and last the paper of the user's region. The **header and footer** settings are gone outright: their defaults told the model "Include Company Logo: No" and "Include Page Numbers: Yes" whatever the source showed, and a header and footer are now reproduced from the source or asked for in words. Until then, the **Report Configuration** dialog asked for: DevExpress version (26.1 / 25.2 / 25.1 / 24.1 / 23.2 / 23.1 / 22.2 / 20.1 — the selected version is written into the generated XML's `SerializerVersion` and `Version`, so the file matches whichever SDK will open it — the tag is a label rather than a gate, measured 2026-09-06; 20.1 is present because the ERP this was first built for targets `DevExpress.XtraReports.v20.1`, and it is also the version installed on the development machine. The top three were added 2026-09-07 after checking DevExpress's own release list: v26.1 shipped June 2026 and v25.2 in February 2026, and the picker had stopped at 24.1. Nothing was measured against them — the newest release `RepxProbe` can verify against is the installed 20.1, so a version above that is a label the generator writes, not a guarantee about syntax the newer serializer expects), report unit (`HundredthsOfAnInch` / `TenthsOfAMillimeter` / `Pixels`, every band and control given the matching `Dpi`, without which DevExpress reads its numbers as hundredths of an inch), page size (`Letter` / `A4` / `Legal`), header (include company logo, report title), and footer (include page numbers, custom text).
*   **Dark Mode:** Built-in theme toggling. The rendered report preview deliberately stays on a white sheet in both themes — a generated report must look the same regardless of the app's theme. The Forma mark itself does swap, between a light-background version and a white-on-dark version.
*   **Diagnostics:** The generation path logs a per-phase timing breakdown (model detection / request / total), token usage including the thinking count, and the resolved model — readable in browser DevTools. The token usage is shown in the REPX pane (the status bar until 2026-11-04, which also carried an elapsed-time clock). *An in-app Debug Console previously mirrored `console.*` into a panel; it was removed on 2026-08-09 because it captured output by monkey-patching the global console, which caused two crashes, and DevTools does the same job without that risk.*
*   **Mock mode (development only, not a UI feature):** Setting `VITE_FORMA_MOCK=true` makes the app return a canned invoice after a 3-second delay so loaders and progress bars can be exercised without spending a request. There is deliberately no in-app equivalent. A "Load Test Mockup" action once populated the workspace with a canned report; it was removed because under bring-your-own-key it meant a first-time visitor with no key could receive fake output with nothing to distinguish it from a real generation. This flag is now the only source of canned output in the product.

**Right to left and the stored procedure** (2026-11-04) were set in Settings, under *Direction and data source*, for the day before Forma began working them out: right to left from a report's `RightToLeft` or text mostly in a right-to-left script, the stored procedure from a report's data source or "EXEC …", "CREATE PROCEDURE …" or "stored procedure …" in the words. Both reach the generation prompt, as they always could; right to left is also written on the report root by `lib/repxRtl.ts` wherever a report is made, with a model or without (OCR, the box reader, Forma's own model, the vision model, the stand-in draft), so it means the same with no key, and the Preview prints the report mirrored. Until then the PRD listed these, with a JSON data schema, as "supported by the engine but not yet exposed". **The data schema is deliberately not a setting:** it is pasted in the **Data** tab, beside the report it binds, or in a fenced block in the chat.

Two more joined that list when BUG-001 was fixed, and they are a different kind: the **`Tabloid` page size** and the **`Document` report unit** (1/300", `GraphicsUnit.Document`) are accepted by the persistence layer and correct in `reportGeometry.ts`, but the dialog above offers neither. DevExpress 20.1's `ReportUnit` has no `Document` member, so it should stay out of the dialog. The geometry tables deliberately lead and the dropdowns are a subset of them, because a dropdown *gaining* an option is safe while the reverse silently mis-scales a legitimate stored value — which is precisely what BUG-001 was. Adding either to the UI is a product decision, not a correctness one.

## 3. Technical Architecture
*   **Frontend:** React 19, Vite 6, Tailwind CSS v4 (via `@tailwindcss/vite`, no config file), and the `motion` v12 library (imported as `motion/react`) for animation. Icons are an in-repo hairline SVG set (`src/components/landing/icons.tsx`) drawn at the same stroke weight as the drafting-sheet rules the UI is built on; `lucide-react` was used at one point and has been removed from the dependency tree.
*   **Generation path:** Entirely client-side. The browser calls the Google Generative AI endpoint directly with the user's key.
*   **Server:** Express with Vite in middleware mode for development; the production build is bundled with esbuild and serves the static client. The server exposes only `GET /api/health` and is deliberately key-free — it handles no generation and holds no credentials. Any other `/api/*` path returns a JSON 404 instead of falling through to the single-page app, so a removed endpoint reads as genuinely absent rather than appearing to answer with HTML.
*   **Branding assets:** Served from the app's own origin. An earlier build loaded every logo from a Google-hosted URL the project did not own, so no logo rendered anywhere when that host was unreachable. Shipped as WebP with a PNG fallback and explicit dimensions, so the surrounding layout does not shift while the image loads. There is no vector source for the mark — it is gradient/shaded artwork that only ever existed as raster, so WebP is the practical floor for its size.
*   **Database & Auth:** Firebase — Firestore (project `forma-201ba`, the `(default)` database, Standard edition) and Google plus email/password Authentication.
*   **AI Engine:** `@google/genai` TypeScript SDK.
*   **File Parsing:** `pdfjs-dist` reads each PDF page **twice, for two different purposes**: it rasterizes the page to an image for visual inference, and it extracts the page's own text layer — every string with its position — converting those coordinates from PDF points into the report grid before they are sent. The extracted text is what makes generated coordinates exact; the image alone would mean re-reading known strings back out of pixels. Both are attached, with the text ordered first, and the prompt ranks text above image for content and position while keeping the image authoritative for borders, fills, logos and visual structure (see §2.2). Uploaded images are downscaled and re-encoded before sending; uploaded `.repx` files are parsed and validated as XML in the browser, not rasterized.
*   **OCR:** `tesseract.js` (Apache-2.0) with `@tesseract.js-data/eng` (MIT), its worker, WebAssembly core and English data served from this site's `/ocr/`, never a CDN. It needs `'wasm-unsafe-eval'` in `script-src`, and nothing else in the CSP changed. Since 2026-11-10 PaddleOCR's PP-OCRv5 text detector and English recogniser (PaddlePaddle's ONNX exports, Apache-2.0) from this site's `/paddle/`, on `onnxruntime-web` (MIT) in module workers; no CSP change.

## 4. User Journeys
1.  **First Run:** User opens Forma with no key -> generation prompts for one -> user pastes a key from Google AI Studio -> "Check key" confirms it and names the model that will be used -> user drops an image -> system analyzes using Gemini -> outputs valid `repx` XML with correct column and row widths.
2.  **Quota Exhaustion:** User exceeds the quota on *their own* key -> Forma moves on to the other models the key can use, and when none is left says which limit it was, when it resets (a minute, or midnight Pacific time for the free daily allowance), and that a local AI or OpenRouter can design meanwhile. Since 2026-11-10 the next AI the user has set up answers on its own, OpenRouter then a local AI after Gemini, and the reply says which (src/lib/fallbackChain.ts); a request to a local AI is never sent on, and when every AI gives out Forma's own draft stands in. Never billing (since 2026-11-05): Forma is free, and its users are on the free tier by design.
3.  **Refinement:** User types "Move the picture box 2 inches down" -> Gemini natively updates the `repxContent` X/Y coordinates contextually.
4.  **New Device:** Signed-in user with a synced key opens Forma elsewhere -> enters their passphrase -> the key is decrypted in-browser and cached for that tab.
5.  **Forgotten Account Password:** User cannot sign in -> chooses "Forgot Password" -> the address already typed in the form is used, and Forma confirms a reset link is on its way if that account exists -> user follows the emailed link. *This resets the **account** password only. It has no bearing on the key-vault passphrase, which is unrecoverable by design (§5) — the two are separate secrets and only one of them can be reset.*

## 5. Security & Privacy
*   **No application-owned key.** Forma holds no Gemini credential at any layer — not in the bundle, not in the server, not in an environment variable. The only key in play belongs to the user.
*   **Key in transit:** The user's key goes from their browser straight to Google. It never reaches Forma's server, and it travels in the `x-goog-api-key` header rather than a query string, so it cannot leak into browser history, referrers, or intermediate logs.
*   **Key at rest:** Never persisted in plaintext. The session copy is in `sessionStorage` (browser-guaranteed erasure on tab close); the optional durable copy in Firestore is AES-GCM ciphertext plus its public derivation parameters. A pre-BYO-key build stored the key in `localStorage`; that entry is deleted on boot.
*   **Zero-knowledge sync:** The passphrase never leaves the browser, so the operator cannot decrypt a stored key. The deliberate consequence is that **a forgotten passphrase is unrecoverable** — there is no reset path, because one would mean the operator could read the key. The UI states this wherever a passphrase is set. Cross-device sync requires a secure context (HTTPS or localhost) for WebCrypto and is hidden otherwise.
*   **Secure Auth:** Firebase Authentication ties reports strictly to authenticated user IDs via Firestore Security Rules, which also pin the shape of both the saved-report and encrypted-key documents and reject a PBKDF2 iteration count below 100,000.
*   **Enforced, not merely intended:** the server sends a Content-Security-Policy (added 2026-08-30, audit SEC-001) whose `connect-src` allowlists only the five Google endpoints this app legitimately calls. It is what turns the claims above from architecture into enforcement: the workspace renders model-generated markdown a few components away from a live key in `sessionStorage`, and `connect-src` means injected script that cannot reach an attacker's origin cannot exfiltrate anything. `script-src` carries no `'unsafe-inline'` in production — `index.html`'s single inline theme script is allowed by SHA-256 hash, recomputed from the file by `securityHeaders.test.ts` so the two cannot drift apart silently. Adding an origin to `connect-src` is a change to this guarantee.
*   **The designer companion (2026-11-09):** The website reaches `127.0.0.1:7317` only when the person clicks Open in designer, after the browser asks; the companion answers the website on `/health` and `/open` alone (its SQL Server routes answer only a page served from the PC), and the server process denies report scripts, since a report a page hands over may be one somebody shared. The download holds no DevExpress file.
*   **No account enumeration:** Sign-in returns one message for both "no such user" and "wrong password", and password reset reports the same result whether or not the address is registered. Firebase distinguishes these cases internally; Forma deliberately does not pass that distinction to the user, so the form cannot be used to test which email addresses have accounts. Raw provider errors are never rendered — they carry both the distinction and, for Firestore failures, the signed-in user's own address.
*   **Resolved exposures:**
    *   An earlier build inlined a build-time `GEMINI_API_KEY` into the shipped client bundle — Google's secret scanner detected and revoked that key. The build no longer passes any Gemini variable to the client. A `/api/debug-key` diagnostic route that echoed key material to any caller in production builds has been removed along with the server-side generation endpoint.
    *   **Sign-in could be bypassed entirely.** The dialog fabricated a "Local Developer" session whenever Firebase rejected the sign-in. It first matched on the error *message* — `auth/network-request-failed` contains "network", so a dropped connection admitted the visitor regardless of the password supplied. Narrowing it to the exact codes `auth/unauthorized-domain` and `auth/configuration-not-found` was still a bypass, because the first is precisely what a deployed site returns when its domain is not on Firebase's authorized list. **The fallback was removed outright on 2026-08-09** — a failed sign-in is a failure, and no credential-free path into the workspace exists in any build. Both codes now map to real user-facing text so a misconfiguration reports itself.
    *   Both were verified on 2026-08-04 against the development server and the production bundle. The shipped client was scanned for key-shaped strings; the only `AIza…` value present is the Firebase Web API key, which is a public project identifier by design and is protected by Security Rules rather than by secrecy. **These particular checks are manual** — the project's two test suites (`npm test`, `npm run test:rules`) cover pure helpers and Firestore rules, not the build output, so treat this as a point-in-time result rather than a standing guarantee, and repeat it whenever the key path, the build config, or the server routes change.

## 6. Future Scope
*   Raise or remove the 8-page PDF cap (`MAX_PDF_PAGES`), and support multi-page `.repx` datasets.
*   **Editing by hand on the Preview:** deleting and adding a control, editing a table cell's text, and multi-select. *(Direct manipulation shipped on 2026-09-05 with move, resize, double-click retype, keyboard nudge and per-gesture undo, all writing straight into `repxContent` — §2.2. The chat has deleted and added controls since 2026-11-05, as edits to the open report; what remains is doing it by hand.)*
*   **Real barcodes**, encoded from their value: the Preview draws an `XRBarCode` as a placeholder of bars, and the mockup draws gauges, barcodes and charts as stylized placeholders. *(The exported REPX has never approximated: charts are real `XRChart` elements and value matrices real `XRCrossTab` elements since 2026-09-05, chart titles, legends and axis labels are read from the source since 2026-11-04, and the Preview draws charts, cross-tabs, gauges and sparklines as DevExpress prints them.)*
*   A password-strength indicator at sign-up. *(A new password has needed eight characters since 2026-11-08, a verification email goes out at sign-up, and sharing waits for a verified address; client-side validation, password reset and error-code mapping since 2026-08-04, the auth dialog's focus trap since 2026-08-09.)*
*   Run the report library's evaluation on real reports (`docs/proposals/rag.md`, *How we would know it worked*), which is what moves it from a proposal into the product's notes.

Done since this list was last rewritten, and taken off it on 2026-11-08: Batch takes a dropped or chosen folder and runs two or three at once (2026-11-04); right to left and the stored procedure are worked out from the input rather than set (2026-11-04); the Preview has data, from a data file or the **Test data** button (§2.2); the workspace has a phone arrangement, the sidebar a drawer under a top bar (2026-11-04); and the *opening*-phase progress signal went with the progress bar itself, when the workspace became as minimal as a chat app (2026-11-04). Since then, on 2026-11-08 and 9: a SQL Server database, without a connection, from its layout to the report's data source, the AI's bindings, the Preview's rows and the drift of an existing report (§2.2, and §6's decision on the credential below).

**A database, and who holds its credential (decided 2026-11-08).** This was a boundary to raise "only alongside a decision about who holds the credential", and the owner made it: **the user's own PC, next to DevExpress, and nobody else.** The argument is still §5's: a server holding every customer's database password stays out of scope, and so does a browser reaching a database directly. *Phase 1, shipped 2026-11-08 and 9:* no connection at all. Forma reads a layout and sample rows the user exports with its read-only scripts, writes the report's `SqlDataSource` by connection name, and the user's application, which already holds the connection, supplies it (§2.2). *Phase 2, approved the same day and built on 2026-11-09:* an optional companion on the user's machine, on `127.0.0.1` beside the designer companion, which may connect with Windows authentication or a connection string it keeps encrypted for that Windows user, so a live layout, live sample rows and a live preview never put a credential in the browser, in a request to an AI, or on any server. Out of scope still: a credential anywhere but the user's own machine.

**Explicitly out of scope: moving generation server-side.** It was listed as future scope while Forma owned the key. Under bring-your-own-key it is a regression — the server would become custodian of every user's third-party credential, and it would reintroduce exactly the exposure §5 records as resolved.

**Explicitly out of scope: replacing the direct Gemini call with MCP.** Considered and rejected on 2026-08-02. MCP is a protocol for supplying a model with tools and context; it performs no inference, so it substitutes for nothing — Gemini would still be called for every generation, with a protocol layer added on top. Three specific costs settled it:

*   Gemini's structured-output mode and function calling cannot both be used in one call, so adopting MCP tools would have meant abandoning the `responseSchema` that guaranteed parseable `repxContent`. *(This constraint was not verified against current Gemini documentation. Since 2026-11-05 generation asks for the REPX as plain text with no `responseSchema` at all, so this first cost has gone; the other two stand.)*
*   A browser cannot spawn a subprocess, so the stdio transport and the entire local MCP server ecosystem are unreachable. Only remote Streamable HTTP servers qualify, and those require a hosted origin with CORS and OAuth 2.1 — against §3's key-free, near-serverless design.
*   Forma's flow was one image in, one structured JSON out, and is one request in, one REPX out since 2026-11-05. There is no external state to read and no tool loop for the model to run, which is the situation MCP exists to serve.

Note that MCP would *not* endanger the key: the browser would still call Google directly and merely relay tool calls. The objection is cost and complexity, not §5.

Two narrower uses remain defensible if MCP is ever revisited, both additive rather than replacing anything: an MCP server exposing the user's real database schema to populate the `dataSchema` / `spName` options above, and Forma itself acting as an MCP server so other hosts can call its REPX generation. Neither requires changing the existing generation path.
