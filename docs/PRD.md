# Product Requirements Document (PRD)

## 1. Product Overview
**Product Name:** Forma — DevExpress Report Layout Generator (AI-Powered)
**Purpose:** Automate the creation of DevExpress `.repx` report layouts by analyzing reference images, PDFs, or an existing `.repx` file.
**Target Audience:** Software developers, reporting engineers, and UI/UX designers who work with DevExpress controls.
**Distribution model:** Bring-your-own-key. Forma ships with no Gemini API key of its own; each user supplies their own, and their browser calls Google directly with it. There is no application-owned quota, no server-side key, and no per-user cost to the operator.

## 2. Features

### 2.1 Core AI Analysis
*   **Gemini AI Integration:** Uses Google Gemini to analyze visual documents (mockups, scans, PDFs).
*   **Spatial Mapping:** Understands exact layout coordinates (`LocationFloat`) and dimensions (`SizeF`) of UI elements like Labels, Pictures, Barcodes, and Tables.
*   **REPX Generation:** Generates valid, strict XML conforming to the DevExpress `XtraReportsLayoutSerializer` schema.
*   **Single Structured Response:** One call returns all three artifacts — a markdown specification, a `layout` JSON for the in-browser mockup, and the `repxContent` XML — enforced by a response schema.
*   **Automatic Model Selection:** There is no model picker. On the first generation of a session the app probes a preference list (`gemini-flash-latest` first, then pinned 2.5/2.0 ids, with pro tiers as fallback) with a one-token request and uses the first model the user's key can actually call. The winner is cached for the session. If that model becomes unavailable mid-generation, the app re-detects and retries once, silently. *Rationale: Google retires models "for new users", so a hardcoded id keeps working for existing projects while every newly created key gets a 404 — which is what happened to the previous `gemini-2.5-flash` default.*

### 2.2 User Interface
*   **File Upload:** Drag-and-drop or manual selection for images (`.png`, `.jpg`), PDF files, and `.repx` files, with preview thumbnails. Up to 8 PDF pages are read per file; anything beyond that, an unsupported file type, an oversized file, or a `.repx` that fails XML validation is reported to the user rather than silently ignored.
*   **Source-accurate extraction:** For a digital PDF, Forma reads the file's own text layer — every string with its exact position — and converts those coordinates into the report grid before sending them alongside the page image. The model is instructed to treat that extracted text as authoritative for content and position, using the image only for borders, fills, logos and visual structure. An uploaded `.repx` is likewise parsed as real XML and validated on upload. *A scanned PDF has no text layer; this is detected and reported, and it falls back to reading the page visually.*
*   **Chat Interface:** A real conversational assistant. Messages without an attachment are answered as chat — asking a question or saying hello gets a reply, not a report. A message *with* an attachment, or one the assistant judges to be an actual request to build or change a report, runs generation. Refinement turns send the previous layout and REPX so the model edits the existing report rather than regenerating it.
*   **UI Layout Mockup ("Overview" tab):** Renders the generated layout as a scaled, fit-to-width page preview, aiming to visually match the uploaded design. Text carries bold, italic, font family, size, colour, alignment, wrapping, and per-side borders. Grids render their real rows and cells. Logos and pictures are cropped out of the user's own upload and shown as the actual artwork. Charts follow the detected chart type and approximate values. *Gauges and barcodes remain decorative placeholders, and charts are stylized rather than drawn by a charting library.*
*   **Specification View ("Specs & REPX" tab):** Two sub-views. **Specification** renders the model's markdown write-up (component inventory, coordinates, styles). **REPX XML** shows the generated DevExpress XML itself — re-indented, syntax-coloured, with line numbers, a line/character count, and a one-click **Copy XML** action for pasting straight into the designer. A validity check runs on the XML and reports whether it parses, whether the root element is `XtraReportsLayoutSerializer`, and whether it contains any `<Bands>` — so a malformed generation is visible here rather than surfacing later as a refusal in DevExpress.
*   **Export:** One-click download of the generated `.repx` file, named after the report title. Falls back to a `.txt` of the specification if the model returned no XML.
*   **Progress Tracking:** Step-by-step status labels, a percentage bar, and a live elapsed timer during generation. The response is streamed, so once the model begins writing, the bar and the "KB received" readout reflect real output rather than a timer. *The opening phase — model detection and upload — has no signal available and still runs on a simulated cadence; the bar holds at 95% until the result is parsed. Pause and Stop genuinely abort the in-flight request, but cancellation is client-side, so Google may still complete and bill the generation.*
*   **Mobile Layout:** Below the `md` breakpoint the chat and canvas become tabs; a finished result switches the user to the canvas automatically.

### 2.3 Account and Cloud Storage
*   **Authentication:** Firebase Auth — Google account sign-in plus email/password sign-in and sign-up, in one dialog that switches between the two modes. Escape closes it.
*   **Sign-in validation:** Every field is checked in the browser before a request is spent, and each problem is reported directly beneath the field it belongs to rather than in a single shared banner. Enforced: email format, password present, a 6-character minimum on sign-up, and a matching confirmation. A too-short password reports its own length problem rather than surfacing as "passwords do not match" against a half-typed confirmation. Errors clear as soon as the user starts correcting the field, and switching between sign-in and sign-up clears both the errors and the typed password. Email and name are trimmed on submit, so a pasted address with a leading space is not rejected. Fields carry autocomplete hints so password managers fill them correctly.
*   **Password reset:** "Forgot Password" sends a real reset email to the address entered in the form. It reports the same "if an account exists for that address…" wording whether or not the account is found — see §5.
*   **Save:** Reports are saved on demand via the Save action (not auto-saved). Signed-in users write to Firestore under `users/{uid}/reports`; signed-out users fall back to browser `localStorage`, with a prompt to sign in and sync. Saved reports contain the conversation and the result only — never the API key or the report configuration.
*   **History Sidebar:** Shows previously saved reports with the ability to reload or delete a past session.

### 2.4 Configuration & Settings
*   **API Key:** The user pastes their own Gemini API key into the config modal. **It gates the entire workspace** — chat, generation and refinement all require it. Without one the composer is disabled and a banner explains why, rather than letting an attempt fail; any action that needs it opens the modal instead. A "Check key" action validates it by attempting a real one-token generation and reports which model it resolved to. "Clear from this session" removes it immediately. The modal links to Google AI Studio for obtaining a free key.
*   **Key Storage:** The working copy lives in `sessionStorage` and is erased by the browser when the tab closes. Signed-in users may opt into cross-device sync, which encrypts the key **in the browser** under a user-chosen passphrase (PBKDF2-SHA256, 310,000 iterations, per-record salt and IV → AES-GCM) and uploads only the ciphertext. See §5.
*   **Report Configuration:** DevExpress version (24.1 / 23.2 / 23.1 / 22.2), report unit (`HundredthsOfAnInch` / `TenthsOfAMillimeter` / `Pixels`), page size (`Letter` / `A4` / `Legal`), header (include company logo, report title), and footer (include page numbers, custom text).
*   **Dark Mode:** Built-in theme toggling. The rendered report preview deliberately stays on a white sheet in both themes — a generated report must look the same regardless of the app's theme. The Forma mark itself does swap, between a light-background version and a white-on-dark version.
*   **Diagnostics:** The generation path logs a per-phase timing breakdown (model detection / request / total), token usage including the thinking count, and the resolved model — readable in browser DevTools. The elapsed-time readout on the progress card is real wall-clock. *An in-app Debug Console previously mirrored `console.*` into a panel; it was removed on 2026-08-09 because it captured output by monkey-patching the global console, which caused two crashes, and DevTools does the same job without that risk.*
*   **Mock mode (development only, not a UI feature):** Setting `VITE_FORMA_MOCK=true` makes the app return a canned invoice after a 3-second delay so loaders and progress bars can be exercised without spending a request. There is deliberately no in-app equivalent. A "Load Test Mockup" action once populated the workspace with a canned report; it was removed because under bring-your-own-key it meant a first-time visitor with no key could receive fake output with nothing to distinguish it from a real generation. This flag is now the only source of canned output in the product.

**Supported by the engine but not yet exposed in the settings UI:** right-to-left layout, stored-procedure name, and a JSON data schema for data bindings. All three are honoured by the generation prompt when set, but nothing in the current UI sets them.

## 3. Technical Architecture
*   **Frontend:** React 19, Vite 6, Tailwind CSS v4 (via `@tailwindcss/vite`, no config file), Lucide icons, and the `motion` v12 library (imported as `motion/react`) for animation.
*   **Generation path:** Entirely client-side. The browser calls the Google Generative AI endpoint directly with the user's key.
*   **Server:** Express with Vite in middleware mode for development; the production build is bundled with esbuild and serves the static client. The server exposes only `GET /api/health` and is deliberately key-free — it handles no generation and holds no credentials. Any other `/api/*` path returns a JSON 404 instead of falling through to the single-page app, so a removed endpoint reads as genuinely absent rather than appearing to answer with HTML.
*   **Branding assets:** Served from the app's own origin. An earlier build loaded every logo from a Google-hosted URL the project did not own, so no logo rendered anywhere when that host was unreachable. Shipped as WebP with a PNG fallback and explicit dimensions, so the surrounding layout does not shift while the image loads. There is no vector source for the mark — it is gradient/shaded artwork that only ever existed as raster, so WebP is the practical floor for its size.
*   **Database & Auth:** Firebase — Firestore (project `forma-201ba`, the `(default)` database, Standard edition) and Google plus email/password Authentication.
*   **AI Engine:** `@google/genai` TypeScript SDK.
*   **File Parsing:** `pdfjs-dist` reads each PDF page **twice, for two different purposes**: it rasterizes the page to an image for visual inference, and it extracts the page's own text layer — every string with its position — converting those coordinates from PDF points into the report grid before they are sent. The extracted text is what makes generated coordinates exact; the image alone would mean re-reading known strings back out of pixels. Both are attached, with the text ordered first, and the prompt ranks text above image for content and position while keeping the image authoritative for borders, fills, logos and visual structure (see §2.2). Uploaded images are downscaled and re-encoded before sending; uploaded `.repx` files are parsed and validated as XML in the browser, not rasterized.

## 4. User Journeys
1.  **First Run:** User opens Forma with no key -> generation prompts for one -> user pastes a key from Google AI Studio -> "Check key" confirms it and names the model that will be used -> user drops an image -> system analyzes using Gemini -> outputs valid `repx` XML with correct column and row widths.
2.  **Quota Exhaustion:** User exceeds the quota on *their own* key -> app shows an explicit "exceeded your Gemini API quota" message pointing at their plan and billing.
3.  **Refinement:** User types "Move the picture box 2 inches down" -> Gemini natively updates the `repxContent` X/Y coordinates contextually.
4.  **New Device:** Signed-in user with a synced key opens Forma elsewhere -> enters their passphrase -> the key is decrypted in-browser and cached for that tab.
5.  **Forgotten Account Password:** User cannot sign in -> chooses "Forgot Password" -> the address already typed in the form is used, and Forma confirms a reset link is on its way if that account exists -> user follows the emailed link. *This resets the **account** password only. It has no bearing on the key-vault passphrase, which is unrecoverable by design (§5) — the two are separate secrets and only one of them can be reset.*

## 5. Security & Privacy
*   **No application-owned key.** Forma holds no Gemini credential at any layer — not in the bundle, not in the server, not in an environment variable. The only key in play belongs to the user.
*   **Key in transit:** The user's key goes from their browser straight to Google. It never reaches Forma's server, and it travels in the `x-goog-api-key` header rather than a query string, so it cannot leak into browser history, referrers, or intermediate logs.
*   **Key at rest:** Never persisted in plaintext. The session copy is in `sessionStorage` (browser-guaranteed erasure on tab close); the optional durable copy in Firestore is AES-GCM ciphertext plus its public derivation parameters. A pre-BYO-key build stored the key in `localStorage`; that entry is deleted on boot.
*   **Zero-knowledge sync:** The passphrase never leaves the browser, so the operator cannot decrypt a stored key. The deliberate consequence is that **a forgotten passphrase is unrecoverable** — there is no reset path, because one would mean the operator could read the key. The UI states this wherever a passphrase is set. Cross-device sync requires a secure context (HTTPS or localhost) for WebCrypto and is hidden otherwise.
*   **Secure Auth:** Firebase Authentication ties reports strictly to authenticated user IDs via Firestore Security Rules, which also pin the shape of both the saved-report and encrypted-key documents and reject a PBKDF2 iteration count below 100,000.
*   **No account enumeration:** Sign-in returns one message for both "no such user" and "wrong password", and password reset reports the same result whether or not the address is registered. Firebase distinguishes these cases internally; Forma deliberately does not pass that distinction to the user, so the form cannot be used to test which email addresses have accounts. Raw provider errors are never rendered — they carry both the distinction and, for Firestore failures, the signed-in user's own address.
*   **Resolved exposures:**
    *   An earlier build inlined a build-time `GEMINI_API_KEY` into the shipped client bundle — Google's secret scanner detected and revoked that key. The build no longer passes any Gemini variable to the client. A `/api/debug-key` diagnostic route that echoed key material to any caller in production builds has been removed along with the server-side generation endpoint.
    *   **Sign-in could be bypassed entirely.** The dialog fabricated a "Local Developer" session whenever Firebase rejected the sign-in. It first matched on the error *message* — `auth/network-request-failed` contains "network", so a dropped connection admitted the visitor regardless of the password supplied. Narrowing it to the exact codes `auth/unauthorized-domain` and `auth/configuration-not-found` was still a bypass, because the first is precisely what a deployed site returns when its domain is not on Firebase's authorized list. **The fallback was removed outright on 2026-08-09** — a failed sign-in is a failure, and no credential-free path into the workspace exists in any build. Both codes now map to real user-facing text so a misconfiguration reports itself.
    *   Both were verified on 2026-08-04 against the development server and the production bundle. The shipped client was scanned for key-shaped strings; the only `AIza…` value present is the Firebase Web API key, which is a public project identifier by design and is protected by Security Rules rather than by secrecy. **These particular checks are manual** — the project's two test suites (`npm test`, `npm run test:rules`) cover pure helpers and Firestore rules, not the build output, so treat this as a point-in-time result rather than a standing guarantee, and repeat it whenever the key path, the build config, or the server routes change.

## 6. Future Scope
*   Raise or remove the 8-page PDF cap, and support multi-page `.repx` datasets.
*   Expose the RTL, stored-procedure, and data-binding schema options (and therefore `ExpressionBindings` generation) in the settings UI.
*   Render real gauges and barcodes in the mockup, and draw charts with a real charting library rather than the current stylized approximation. *(Table cells, text styling, and logo cropping were completed on 2026-08-02.)*
*   Sign-in hardening partly done: no password-strength indicator and no email-verification gate after sign-up. *(Client-side validation, password reset and error-code mapping were completed on 2026-08-04; the auth dialog's focus trap on 2026-08-09.)*
*   Find real signal for the *opening* phase of generation — model detection and upload — which still runs on a simulated cadence. *(Streaming already replaced the simulated cadence for the output phase: once the model starts writing, the bar and the "KB received" readout reflect output actually received. §2.2 describes the current behaviour.)*

**Explicitly out of scope: moving generation server-side.** It was listed as future scope while Forma owned the key. Under bring-your-own-key it is a regression — the server would become custodian of every user's third-party credential, and it would reintroduce exactly the exposure §5 records as resolved.

**Explicitly out of scope: replacing the direct Gemini call with MCP.** Considered and rejected on 2026-08-02. MCP is a protocol for supplying a model with tools and context; it performs no inference, so it substitutes for nothing — Gemini would still be called for every generation, with a protocol layer added on top. Three specific costs settled it:

*   Gemini's structured-output mode and function calling cannot both be used in one call, so adopting MCP tools would mean abandoning the `responseSchema` that guarantees parseable `repxContent`. *(This constraint was not verified against current Gemini documentation — confirm it before revisiting.)*
*   A browser cannot spawn a subprocess, so the stdio transport and the entire local MCP server ecosystem are unreachable. Only remote Streamable HTTP servers qualify, and those require a hosted origin with CORS and OAuth 2.1 — against §3's key-free, near-serverless design.
*   Forma's flow is one image in, one structured JSON out. There is no external state to read and no tool loop for the model to run, which is the situation MCP exists to serve.

Note that MCP would *not* endanger the key: the browser would still call Google directly and merely relay tool calls. The objection is cost and complexity, not §5.

Two narrower uses remain defensible if MCP is ever revisited, both additive rather than replacing anything: an MCP server exposing the user's real database schema to populate the `dataSchema` / `spName` options above, and Forma itself acting as an MCP server so other hosts can call its REPX generation. Neither requires changing the existing generation path.
